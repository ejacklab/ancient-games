# Ancient Games state — 2026-09-19

## Graph engineering versus loop engineering

Graph engineering designs how tasks, agents, dependencies, and execution states
connect. Loop engineering designs how an agent repeatedly acts, checks results,
adjusts its approach, and stops. The two can be combined: a task graph can contain
an implement → verify → repair loop within each branch.

## Current capability

Ancient Games does **not currently have a built-in policy that determines whether
a task should favor graph coordination or iterative looping**. It has useful
foundations, but the strategy decision remains with the caller or external agent.

| Capability | Current implementation |
|---|---|
| Repeated execution and feedback | An observe → choose → check → execute → journal loop, with call limits and replanning after failed proof. |
| Agent allocation | Gate counts caller-supplied independent capabilities or perspectives and splits large groups. |
| Next-action selection | A supplied chooser callback or external chooser command selects the next tool call. |
| Task dependency scheduling | No built-in graph-versus-loop strategy selector or task dependency scheduler was found in the inspected code. |
| Delegation | Dispatch records delegation; an external orchestrator runs the worker, and `ingest_return` imports its results. |

### Evidence from the implementation

- [`TaskInput` and `decision_tree()`](ancient_games/stages.py): task assessments
  arrive as caller-supplied values. `decision_tree()` returns the number of
  capability entries. Difficulty is advisory and does not affect that count.
  Gate splits capability lists exceeding three into smaller groups; this does
  not analyze task dependencies or estimate the benefit of parallel execution.
- [Runtime loop](ancient_games/hybrid/loop.py): `choose(obs, tools)` selects each
  action. The default sequence is Gate → Guard → Corroborate → Filter → Prove,
  offered as guidance rather than enforced ordering. A proof returning
  `RETURN_TO_PLANNER` resets the suggested sequence to Corroborate → Filter → Prove.
- [Supervisor](ancient_games/hybrid/supervise.py): `command_chooser()` accepts an
  external program that receives an observation and returns one tool call.
  `drive()` repeats execution while checking journal-derived run state and budget.
- [Project overview](PROJECT_OVERVIEW.md), “How a run works” and “Review workflow”:
  documents the external worker orchestration boundary and an example of a
  graph-organized review. It explicitly distinguishes that review graph from the
  project's observe/choose/execute runtime loop.
- [Knowledge graph design](docs/KNOWLEDGE_GRAPH_DESIGN.md): describes provenance
  queries over claims, evidence, artifacts, and dispatches. This design document
  does not establish an implemented task-strategy selector or workflow scheduler.

An external LLM chooser could reason about when to coordinate independent branches
or iterate on one task. That would be the external agent's judgment, rather than
an explicit, testable Ancient Games routing policy.

## Proposed extension — not implemented

Add a planning decision before execution that assesses task structure and selects
an appropriate combination of coordination and iteration:

| Favor | Task characteristics | Example |
|---|---|---|
| Graph coordination | Separable branches, explicit dependencies, independent expertise or review, and useful parallel work. | Implement API and interface independently, then integrate and review. |
| Iterative loops | Each next action depends on feedback from the previous attempt, with a measurable completion condition. | Diagnose a failing test, apply a fix, rerun it, and adjust. |
| Combined execution | Independent branches each require their own feedback cycle before a shared integration step. | API and interface branches each implement, verify, and repair before integration tests. |

The decision should record its rationale, dependencies, verification conditions,
and execution bounds so it can be reviewed and tested. Choosing graph coordination
does not require replacing the existing runtime loop: dependency-aware scheduling
could supply actions to that loop.

## Graph engineering versus agent swarms

Graph engineering makes task dependencies, communication paths, state, and
execution conditions explicit. In the swarm pattern described by
[Strands](https://strandsagents.com/docs/user-guide/concepts/multi-agent/swarm/)
and [AutoGen](https://microsoft.github.io/autogen/dev/user-guide/agentchat-user-guide/swarm.html),
specialized agents share context and decide when to hand work to another agent.
A swarm does not necessarily execute agents simultaneously; these implementations
support sequential handoffs.

Graphs, swarms, and loops can operate together. A swarm can investigate a problem
inside a larger graph with fixed review and completion gates, while individual
agents use verification loops. See
[Strands' pattern composition discussion](https://strandsagents.com/docs/learning/multi-agent-patterns-agent-swarms/).

### Current capability

Ancient Games does **not currently have a built-in policy that evaluates a task
and chooses dependency-driven graph execution versus agent-directed swarm
collaboration**.

| Capability | Current implementation |
|---|---|
| Determine how many specialists are needed | Gate counts capabilities supplied by the caller; it does not discover them itself. |
| Schedule work from task dependencies | No built-in task dependency graph scheduler was found. |
| Let agents choose and hand off directly to peers | No built-in swarm handoff mechanism was found. |
| Decide the next action | An external chooser supplies each tool call. |
| Record delegation and evaluate returned evidence | Implemented; worker execution is handled externally. |

The relevant implementation boundaries are:

- [`decision_tree()`](ancient_games/stages.py): counts supplied capabilities,
  without assessing dependencies or choosing a coordination pattern.
- [`command_chooser()` and `drive()`](ancient_games/hybrid/supervise.py): delegate
  next-action selection to an external program and execute its returned tool call.
- [`dispatch`](ancient_games/hybrid/tools/dispatch.py): writes a delegation record
  and returns an agent identifier; it does not run a worker or transfer control
  between peers.
- [`ingest_return`](ancient_games/hybrid/tools/ingest_return.py): imports worker
  results and validates their claims and checks through the existing writers.

An external agent could make the graph-versus-swarm decision today, but Ancient
Games would not independently assess or validate whether the selected
coordination pattern suits the task. Its existing delegation and verification
controls are foundations for this capability, not an implementation of it.

### Proposed extension — not implemented

Assess two separate planning dimensions:

1. **Task structure:** which dependencies, parallel branches, and verification
   checkpoints should be explicit?
2. **Routing authority:** should a scheduler, a central planner, or individual
   agents decide who works next?

This could support structured graph execution for known dependencies, bounded
swarm collaboration for exploratory work, or a combination. Record the rationale,
permitted handoffs, completion evidence, and execution bounds so the decision
and its execution can be reviewed and tested.

These are proposed design directions, not implemented behavior. A single
graph-versus-swarm-versus-loop switch would obscure that task structure, routing
authority, and feedback cycles can be combined.

## Sequential, parallel, and loop agent execution

Sequential execution runs agents in a specified order; parallel execution runs
independent branches concurrently; loop execution repeats agent steps until a
termination condition or iteration limit is reached. These patterns can be
combined within one workflow. See Google's ADK documentation for
[sequential](https://adk.dev/agents/workflow-agents/sequential-agents/),
[parallel](https://adk.dev/agents/workflow-agents/parallel-agents/), and
[loop](https://adk.dev/agents/workflow-agents/loop-agents/) workflows.

### Current capability

Ancient Games does **not automatically assess a task and determine how much
sequential, parallel, or repeated agent work it needs**. It provides some relevant
execution controls, while selection remains with the caller or external chooser.

| Pattern | Current implementation | Missing selection capability |
|---|---|---|
| Sequential | Executes tool calls one at a time; scripted runs follow a supplied order. | Dependency analysis that determines which agents must finish before others start. |
| Parallel | Tracks outstanding delegations and enforces a concurrency cap. External orchestration runs the workers. | Analysis that identifies independent work and schedules it concurrently. |
| Loop | Repeatedly observes, chooses, and executes; supports replanning after failed proof and limits total calls. | A policy that selects which agent group should repeat, evaluates useful progress, and assigns its iteration budget. |

The distinction between tool execution and worker execution matters: serial tool
calls do not establish a sequential agent pipeline, and tracking live dispatches
does not itself launch or schedule parallel workers. Likewise, the existing
runtime loop does not automatically select a repeated sub-agent workflow.

### Evidence from the implementation

- [`run()`](ancient_games/hybrid/loop.py): calls the supplied chooser, executes
  one selected tool call, records results, and repeats within the call budget.
  A proof returning `RETURN_TO_PLANNER` resets the suggested planning stages.
- [`scripted()`](ancient_games/hybrid/loop.py): consumes a caller-supplied queue
  of tool calls in order and can resolve inputs from earlier successful results.
- [`i5()`](ancient_games/hybrid/invariants.py): checks outstanding delegations
  against the concurrency cap. It does not decide which tasks can run together.
- [`dispatch`](ancient_games/hybrid/tools/dispatch.py): records delegation;
  the external worker execution boundary is documented in
  [the project overview](PROJECT_OVERVIEW.md), “How a run works.”
- [`decision_tree()`](ancient_games/stages.py): counts caller-supplied capability
  entries. It does not discover dependencies, determine task independence, or
  assess whether repeated refinement is needed.

### Proposed extension — not implemented

Make execution-pattern selection explicit for each part of a task:

- **Sequential:** the next task requires an earlier result, or concurrent changes
  would conflict.
- **Parallel:** tasks have independent inputs and can produce separate outputs
  for later integration.
- **Loop:** another attempt should depend on verification feedback, with clear
  success and stopping conditions.

Record dependencies, shared-resource conflicts, expected outputs, verification
criteria, and execution bounds to make these decisions reviewable and testable.
Apply the decision per task segment rather than assigning one pattern to an
entire run: a task might research in parallel, implement sequentially, and repeat
verification and repair. This selection capability remains unimplemented.

## Agent communication mechanisms: shared state, delegation, and explicit invocation

Google's ADK describes three ways agents communicate. With shared session state,
one agent writes a result to a common state object that later agents read. With
LLM-driven delegation, a coordinator reasons about a request and transfers it to
the best-suited sub-agent. With explicit invocation, one agent is wrapped as a
tool and called like a function, and the caller keeps control and receives the
result. See Google's
[multi-agent guide](https://cloud.google.com/blog/topics/developers-practitioners/building-collaborative-ai-a-developers-guide-to-multi-agent-systems-with-adk)
and the ADK [collaboration documentation](https://adk.dev/workflows/collaboration/).

### Current capability

Ancient Games does **not currently have a built-in policy that assesses a task and
chooses which communication mechanism its agents should use**. It uses one fixed
pattern: delegation under a contract, with a structured return that MAIN writes
into an audited shared journal.

| Mechanism | Current implementation | Missing selection capability |
|---|---|---|
| Shared state | The JSONL journal and `Ctx` are shared by MAIN and the tools. Workers never write to them directly; `ingest_return` imports a worker's return and mirrors its claims and checks. | Always on rather than selected. No analysis of which agents should share which state. |
| Delegation | Gate decides whether to delegate: zero capability entries means MAIN executes, one or more means dispatch, and more than three are split into groups. `dispatch` writes a delegation record; an external orchestrator runs the worker. | The capability list is caller-supplied and difficulty is not read. No reasoning about which agent suits the task, and no transfer of control. |
| Explicit invocation | `loop.step` calls tools explicitly, but those are tools rather than agents. Dispatch and return is the closest equivalent: MAIN keeps control and receives a structured return. | No agent-as-tool call and no peer handoff mechanism was found. |

Two dispatch-contract rules restrict sharing rather than select a mechanism.
`ISOLATION` and `INTERFACE_MAP` require a worktree per agent and a map of the
shared interface when more than one agent is dispatched and
`touches_shared_files` is set; that flag is caller-supplied. `READ_SCOPE.deny`
denies sibling agents each other's output paths to prevent herding, so that
sources stay independent for corroboration.

### Evidence from the implementation

- [`decision_tree()` and `gate()`](ancient_games/stages.py): the agent count is
  the number of caller-supplied capability entries. `execution_status` becomes
  `dispatched` when that count is at least one, otherwise `main_executes`.
- [`dispatch`](ancient_games/hybrid/tools/dispatch.py): records the delegation
  and returns an agent identifier. It does not run a worker, call an agent as a
  function, or transfer control.
- [`ingest_return`](ancient_games/hybrid/tools/ingest_return.py): validates a
  worker's return, then writes the return event and its mirrored claims and
  checks to the journal on the worker's behalf.
- [Dispatch field table](ancient_games/schema.py): `INTERFACE_MAP`, `ISOLATION`,
  and `READ_SCOPE.deny` are conditional contract fields driven by `Ctx` values.
  They constrain shared surfaces; none chooses a communication mechanism.

An external chooser could apply different mechanisms per task today. That would
be the chooser's judgment, rather than an explicit, testable Ancient Games policy.

### Proposed extension — not implemented

Record a communication decision per task segment, alongside the structure and
routing decisions proposed above: which state is shared and by whom, which
handoffs are permitted, and who holds control after each call. Record the
rationale so the decision can be reviewed and tested.

One constraint is specific to this project. Letting workers share state or hand
off to each other conflicts with the source independence that corroboration
counts on (see F1 in [the project overview](PROJECT_OVERVIEW.md) and
`READ_SCOPE.deny`). A selector would need to forbid those mechanisms wherever
claims are meant to be independent sources.

## Assessment scope

This assessment comes from reading the current implementation and project
documentation. No runtime behavior was changed, and no tests were run for this
documentation-only assessment. The proposed planning policy, dependency scheduler,
swarm handoff mechanism, per-segment execution-pattern selection, and
communication-mechanism selection remain future work. The linked web documentation
informs terminology and design proposals; the local source files establish the
current implementation assessment.
