## Options

### A. Harvester: read what the engines already record (no instrumentation)
- **Captures.** Nothing new is written while a run is going. After the run, one script (e.g. scripts/harvest_run.py --run <id>) reads the records that already exist and writes runs/<id>/feedback.jsonl plus a digest of about 20 lines. Per engine: (1) Workflow tool: the run JSON ~/.claude/projects/<proj>/<session>/workflows/<runId>.json, with status, durationMs, totalTokens, logs[], and per agent the state, attempt, tokens, toolCalls, durationMs, model, startedAt and queuedAt (local:CC5). I checked this myself: 6 such files exist, and one agent entry reads state=done, attempt=1, tokens=53515, durationMs=86857, model=claude-sonnet-5-5. The input/output/cache split per subagent comes from agent-<id>.jsonl message.usage (local:CC2, CC6). (2) Claude main session (COO): the session JSONL, which has usage on every assistant line, tool_use/tool_result with is_error, turn_duration records and cost-state totals (local:CC1-CC3). (3) codex: rollout JSONL task_complete duration_ms/error and token_usage_record, or the state_5/thread_history SQLite opened read-only (local:CX2, CX3). (4) qwen: usage_record.jsonl per session, token-usage-YYYY-MM.jsonl per call, and chats with tool_call success/error and duration_ms (local:QW2, QW3). (5) agy: transcript_full.jsonl step status/error/created_at, conversation_summaries.db, and the latency_ms lines in cli-*.log (local:AG2).
- **Engine blind spots.** agy: no readable token counts, because usage sits in a protobuf blob (local:AG2). Linking a codex/qwen/agy session to the run and node that started it has to be done by matching time window and cwd, since none of their records holds our run_id. This is fragile when two calls overlap. COO main session: there are tokens per turn but no node boundaries, so main-session cost cannot be split by node. Workflow agents replayed from cache have no tokens or durationMs (local:CC5). The thin journal.jsonl adds nothing (local:CC4, methods:F1). Not captured at all: verifier pass/fail per attempt, which artifact went to which node (hand-offs), which brief variant (with or without an example) a node received, and EJ interventions. state.md has no schema (local:RP1).
- **Answers.** Where wall time and tokens go, per Workflow node and per COO turn. Which Workflow nodes ran more than once (attempt>1) and how often the script's own loop rounds happened, read from logs[], e.g. 'Plan round 1/3 rejected' (local:CC5). Which codex/qwen calls failed or were aborted (task_complete.error, turn_aborted, qwen success=false). Projected vs actual cost for the ledger's Actual cost column (local:RP2). It cannot answer hand-off cost or whether the example/template raised first-try validity, because nothing records a check result or a brief variant.
- **Cost.** One Python script of a few hundred lines, standard library only (json and sqlite3). It runs in seconds per run and makes no model calls. Upkeep risk: every file format it reads is internal and undocumented (Claude Code 2.1.287, codex 0.159.3, qwen 0.24.7, agy 1.2.14), so an upgrade can break a parser without warning. Each parser needs a check that fails loudly when expected keys are missing.
- **Privacy.** Nothing leaves the machine. The repo is public on GitHub, though, and I checked that runs/ is tracked (453 files in git). So the harvester must write only numbers, ids and status into runs/<id>/, never prompt or response text, previews (promptPreview/resultPreview) or stdout. Raw joins should stay outside the repo or in a gitignored path.
- **Smallest trial.** Run it on the existing run wf_fc2ffa51-890 (status completed, result plan_rejected; see memory). Pass if (a) the sum of per-agent tokens equals the run JSON's totalTokens, (b) the per-agent durationMs values add up to something consistent with the run's durationMs given its sequential phases, and (c) the digest names the slowest node, the most expensive node and every node with attempt>1. (Critic: this trial run and check (a) are flawed; see Critic.)

- **Fit.** Good. Scripts over prose, a cheap check, no polling, and the COO reads only the digest. Nothing changes in config or settings, so Rule 6 approval is not needed. It is n=0 and makes no claims about quality.

### B. Run-written event log in one schema, plus the harvester for tokens (A + explicit events)
- **Captures.** Option A, plus a few events that the run writes itself into runs/<id>/events.jsonl at the moment they happen, using the methods:F13 schema. (1) A thin wrapper (e.g. scripts/runlog.py exec --run <id> --node <n> --attempt <k> --brief-variant <v> -- codex exec ...) for every codex/qwen/agy call. It writes start/end/status/exit code and the artifact paths, saves the engine's own machine output next to the result (codex exec --json and -o; qwen -o stream-json or --json-file; agy --output-format stream-json and --log-file, per local:CX1, QW1, AG1; tools:F3, F5), and records the engine's session id if the stream prints one. (2) Workflow scripts call the same logger: one line per node verdict with check name and pass/fail (validate_result.py, design_gate.py), attempt number, and the artifacts consumed and produced. Hand-offs come from these artifact links (methods:F4). (3) Optional, later: Claude Code hooks SubagentStop / PostToolUseFailure / SessionEnd append a line each (local:CC9). Their payload fields are unverified, and they need a settings.json change, which is a Rule 6 approval for EJ.
- **Engine blind spots.** agy tokens are still missing; only status and latency are available (local:AG2, tools:F5). Inside a codex/qwen/agy call, its own sub-steps (tool calls, sub-agents) are visible only through the saved stream or rollout, not in our schema. Any call that skips the wrapper is invisible, so this depends on discipline. A grep check over runs/<id> (every result file has an end event) is needed to make a missed call fail loudly.
- **Answers.** Everything A answers, plus: which node retries and why (verifier fail vs engine error vs timeout); which engine fails most, per call; first-try validity by brief variant (check pass at attempt 1, with vs without example/template); this directly tests the n=1 brief-template trial in commit 7081d5e; hand-off cost (time and tokens between artifact produced and artifact consumed, and how often a consumer rejected an input); and design vs actual for an after-action review: projected cost and graph from workflow-design.md against the events (methods:F10). The same file is the input that process mining and an eval set need later (methods:F3, F6, F7).

- **Privacy.** Local. Same public-repo rule as A: events.jsonl carries ids, paths, numbers and status only. Raw stream-json, rollouts and transcripts stay where the engines put them or go in a gitignored runs/<id>/raw/. Never commit prompt or response text.
- **Smallest trial.** Pick one real upcoming small run that already uses at least two engines and a verifier, e.g. the next brief-template style trial. Pass if: (1) every result file in runs/<id>/ has exactly one start and one end event, which the completeness check confirms; (2) every Bash engine call in the COO transcript matches a runlog event; (3) token totals per node match the engines' own records (the rollout token_usage_record and the qwen usage line); (4) the digest gives, for that one run, first-try pass/fail per node with its brief variant. A sabotage check: delete one wrapper call and confirm the completeness check fails.
- **Schema.** One JSON object per line: {run_id, node_id, event: start\|end\|verdict\|handoff, ts (ISO), engine: claude-main\|claude-sub\|codex\|qwen\|agy, model, attempt, parent (node or COO that dispatched), status: ok\|fail\|timeout\|skipped, error_type, tokens_in, tokens_out, tokens_cache_read (null if unknown), duration_ms, artifacts_in[], artifacts_out[], check: {name, pass}, brief_variant, engine_session_id}. - **Fit.** Strongest fit. It is driven by state files and results as files, and a script makes every number (methods:F14). The COO reads one digest, and no daemon runs, so nothing polls. It extends the existing 'journal of every decision' idea of ancient_games/journal.py (local:RP3) instead of adding a second culture. n=0 until the first trial.

- **Captures.** C's OTLP stream (or B's events converted to OTLP) is sent to a local platform with a UI, trace search and evaluations. Phoenix: one container, SQLite by default, OTLP HTTP on 6006 and gRPC on 4317, can run air-gapped, ELv2 licence, with evals/datasets/experiments and an MCP server/CLI so Claude or Codex can query traces (tools:F9). Langfuse: traces only, HTTP only, needs web+worker+Postgres+ClickHouse+Redis+S3, MIT core, and has ready-made Claude Code (Stop hook reading the transcript) and Codex (plugin hooks) integrations (tools:F8, F16).
- **Engine blind spots.** agy is not covered by either platform (tools:F5, F8). qwen/Gemini CLI are not in Langfuse's list (tools:F8). Phoenix has no documented native Claude Code/Codex ingest; it would rely on generic OTLP with unclear attribute mapping (tools:F9). Workflow node, attempt, verdict and hand-off structure would still have to come from B's events. Langfuse's hook integration reads transcripts, so it sees the COO and possibly subagents but not our run_id unless we add it.
- **Answers.** Mostly the same questions as B+C, but interactively: browse a trace, compare runs, tag failures by hand. Its real addition is a place for error analysis and eval datasets (methods:F6, F7): annotating traces, building an eval set from failed runs, and running LLM-as-judge experiments. That is the step after measurement, worth it once there are tens of runs.
- **Cost.** Phoenix: one Docker container (Docker Desktop on Windows via WSL), modest. Langfuse: five services, heavy for one person. Both are long-running services that need upgrades, and both put a UI between the COO and the data, against 'COO reads digests only'. Whether either self-hosted build sends usage telemetry home, and how to switch it off, was not checked (tools gaps).
- **Privacy.** Local if self-hosted and air-gapped (Phoenix documents this). Their integrations often send message content by default (Langfuse's hook reads full transcripts), so prompts would sit in a database, though on this machine. SaaS variants (LangSmith, Weave, Logfire; tools:F11, F12, F15) would send prompts and user.email off the machine and are not recommended.
- **Smallest trial.** Only after B has produced events for at least one run: start Phoenix in Docker with SQLite and convert one run's events.jsonl into OTLP spans (invoke_workflow > invoke_agent > execute_tool per methods:F12). Pass if the run's tree, tokens and durations show correctly in the UI and the Phoenix CLI/MCP returns the slowest node with the same answer as B's digest. Check outbound network (no traffic to arize.com) during the trial.
- **Schema.** OTel spans with gen_ai.* / OpenInference attributes (tools:F1, F9; methods:F12).
- **Fit.** Weak for now. It adds a service, a UI and a second store, and the n=0 ledger has nothing to browse yet. It becomes reasonable later as the eval and annotation layer, fed from B's file, which stays the source of truth.
- **Finding ids.** tools:F8, F9, F10, F11, F12, F13, F15, F16, F17; methods:F6, F7, F12

### E. Analysis layer on top of the event log: AAR triggers, failure coding, then process mining and prompt optimization
- **Captures.** Nothing new; it consumes B's events.jsonl (or A's feedback.jsonl). It is listed as an option because it is a separate decision from collection, and each piece has its own data threshold. (1) After-action review triggered by script rules (any failed node, attempt>N, wall time over the projection, EJ intervened): a 4-question review per triggered run, with the design-vs-actual diff filled in automatically (methods:F10). (2) Failure coding on failed or retried traces with MAST's 14 modes as the starting codebook, counted to rank fixes (methods:F6, F11). (3) Process mining with PM4Py: performance DFG for bottlenecks, rework per activity for retry loops, variants, and conformance of actual runs against workflow-design.md (methods:F3, F4, F5). Not installed; pandas 3.0.2 is. (4) Prompt optimization for one node with DSPy/GEPA, using validate_result.py as the metric (methods:F8, F9).
- **Engine blind spots.** Inherits the blind spots of whatever feeds it: agy tokens, and COO per-node cost if fed by A only. LLM attribution of which step caused a failure is unreliable: the decisive step was found only 14.2% of the time (methods:F11). So causes must come from logged step fields, not from a model reading the trace.
- **Answers.** Which fix to make first, ranked by failure count. Which steps can become scripts (TraceCompiler-style; methods:F5). Whether real runs follow the designed graph. Whether a new instruction for one node scores better on its check. Each of these is a decision, not just a measurement.
- **Cost.** AAR triggers: a few lines plus one short written review per triggered run. Failure coding: human reading time, at least 30 traces and about 100 for the full loop (methods:F6). PM4Py: free CPU, but AGPL-3.0 and it needs tens of runs before variants mean anything (methods:F3). DSPy: about $2 and 10 minutes per simple optimization, up to tens of dollars, and the node must be rewritten as a DSPy module (methods:F8).
- **Privacy.** Local scripts. Failure coding reads transcripts on the machine. DSPy/GEPA sends traces to whichever model runs the optimizer.
- **Smallest trial.** Only the AAR trigger now: after B's first trial run, run the trigger script against its events.jsonl. Pass if it fires exactly on the conditions that held (sabotage: inject a fake attempt=3 event and confirm it fires) and writes a review stub with projected vs actual cost filled from the ledger row. Leave PM4Py until the ledger has about 20-30 runs, and DSPy until one node has a scripted metric and at least 10 examples.
- **Schema.** Reads the methods:F13 / Option B line format. PM4Py maps run_id to case, node_id to activity and ts to timestamp via format_dataframe; OCEL 2.0 uses artifacts_in/out as objects (methods:F3, F4).
- **Fit.** Good, if added in order and only when the data threshold is met. It matches 'scripts make the numbers, models read the digest' (methods:F14) and the house rule against rule changes on n=1.
- **Finding ids.** methods:F3, F4, F5, F6, F8, F9, F10, F11, F14

### Recommendation (as the options step wrote it)
Choose Option B, the run-written event log, and build it in two steps. First, write A's harvester and test it on the existing run wf_fc2ffa51-890. That costs nothing, changes no config, and proves the parsers against data we already have. Second, add the runlog wrapper around codex/qwen/agy calls and one verdict line per node check in the workflow scripts. Then run the B trial on the next real multi-engine run. Add E's AAR trigger on top straight away. Leave C (OTel collector) and D (Phoenix) as later steps, to take only if a measured gap calls for them. Reasons: (1) The engines already record most of the numbers. The Workflow run JSON alone has status, per-agent tokens, duration, attempt and model (local:CC5, which I checked on a live file: tokens=53515, durationMs=86857, attempt=1). codex, qwen and Claude transcripts carry token usage and errors (local:CC2, CX2, QW2, QW3). So C would mostly duplicate data already on disk, at the price of a daemon and three live-config edits that need EJ's approval (Rule 6). (2) The questions EJ cares most about cannot be answered from any engine's telemetry, in any option. Those are retries per node, first-try validity with and without the example/template, hand-off cost, and design vs actual. They need events that only the workflow knows: node id, attempt, check pass/fail, brief variant and the artifacts consumed and produced (methods:F1, F13; tools:F17). B is the only option that records them. (3) B fits the stance: state-file driven, script-made numbers, a digest for the COO, no polling, no service. It also stays exportable, because field names follow OTel gen_ai.* (tools:F1; methods:F12). Two cautions. The repo is public and runs/ is tracked (453 files in git, checked), so only ids, numbers, paths and status go into runs/<id>/, and never prompt or response text or previews. Codex/qwen/agy session ids in the stream output and the hook payload fields are unverified, because no model call was made. The first B trial has to settle both.

The critic's narrowing of this recommendation (next section) changes the trial run, the retry signal and the scope of the first version.

### What it will not tell
B (with A and E) will not tell us: (1) Whether a node's output was actually correct beyond what its scripted check tests. A pass on validate_result.py is not proof of quality, so error analysis on real traces is still needed (methods:F6). (2) Why a node failed. The log shows where and how often; cause needs a human review, and LLM attribution of the decisive step is right only about 14% of the time (methods:F11; reported, abstract only). (3) Counterfactuals: whether another engine, model or brief would have done better. That needs a deliberate A/B trial with a control, not observation. (4) agy token use, which stays unknown until its protobuf metadata is decoded (local:AG2). Also the exact share of COO main-session tokens per node, which is only approximate. (5) Real money cost for codex/qwen/agy under subscription or credit billing; it gives token counts, not dollars, except for Claude's cost-state (local:CC3). (6) Anything statistically solid for a long time. With the ledger at 0 rows, every result is n=1 per run, process-mining variants mean little before tens of runs (methods:F3), and no rule should change on one run (house rules). (7) What happens inside a codex/qwen/agy call (its own tool steps and sub-agents) in our schema; that detail stays in each engine's native files unless C is added. (8) Calls made outside the wrapper. Coverage depends on discipline, which is why the completeness check, and its sabotage test, are part of the trial.

## Critic

### Weak findings
- local:CC5 is partly contradicted by the data. I checked all 6 Workflow run JSONs that exist. In every one, the sum of per-agent tokens equals totalTokens exactly, and attempt is never above 1. The workflow script retries by spawning a new agent with a new label (plan#1, plan#2, plan#3), not by raising attempt. So the claim that 'this file alone covers ... retry counts' is wrong. Option A's 'every node with attempt>1' will always come back empty, and retries have to be read from the '#n' label suffix or from logs[]. (Spot check 1, /home/smoke01/.claude/projects/-home-smoke01-dev-ancient-games/*/workflows/*.json)
- local:CC5 again, for the proposed trial run. In wf_fc2ffa51-890, 4 of 6 agents (plan#1/#2 and plan-critic#1/#2) are cached:true with tokens=null and durationMs=null. totalTokens=186230 covers only round 3. Option A's pass check (a), 'per-agent tokens sum to totalTokens', is true by construction on all 6 files, so it tests nothing. It also hides the fact that two thirds of that run's cost is missing. That makes it a poor trial run. (Spot check 1)
- local:CC5 / methods:F1: this session has 4 Workflow journal dirs but only 3 run JSONs (wf_526758fa-2c8 has a journal and no JSON). That run is probably still in progress, possibly this one, but the label is unknown. If the run JSON is only written on completion, then killed or crashed runs, the ones feedback most needs, have no record. Option A relies on that file. (Spot check 2)
- Option B's 'engine session id from the stream' is unverified. The codex binary contains the string 'thread.started' 8 times, and the rollout session_meta has id == session_id. That suggests codex exec --json announces a thread id the wrapper could capture. This is reported (from binary strings), not verified, because no model call was made. qwen and agy session ids in their streams are fully unknown. (Spot check 3)
- tools:F2 (Claude Code OTel event and span names, TRACEPARENT propagation) and tools:F3 (the codex [otel] table, trace_exporter/metrics_exporter) come from summarizing fetches and one secondary blog. CC7/CX4 binary strings back up the names only, not the config syntax or the export behaviour. They are reported, single source, and Option C rests on them.
- methods:F11 (14.2% decisive-step attribution) and methods:F5 (TraceCompiler 34->11 calls, arXiv 2608.02680) are abstract-only, single-source and single-domain. The recommendation's 'will_not_tell' and Option E use the 14.2% figure as a load-bearing argument. It should carry the 'reported, abstract only' label wherever it is cited.

### Overbuilt
Yes, for a ledger that has zero rows. (1) Option B's schema has about 19 fields: handoff events, artifacts_in/out, brief_variant, engine_session_id, parent, and a check object. Most of these answer questions nobody has asked yet with n=0. A first version needs run_id, node, round (from the '#n' label), engine, status, check pass/fail, tokens and duration_ms. Add hand-off and artifact links only when a run raises a hand-off question. (2) The wrapper covers codex, qwen and agy all at once, but the model-role memory says most work runs on Codex. qwen and agy wrappers should wait until a real run uses them. (3) Option A parses 5 engines' internal formats. Workflow run JSON plus codex rollouts covers almost all current spend, and every extra parser adds upgrade-breakage upkeep. (4) Option E's PM4Py (AGPL), MAST coding, DSPy and GEPA belong after about 30 runs. The proposal already defers them, but the 'AAR trigger straight away' piece is also early: with zero runs, the trigger has nothing to fire on except the sabotage test. (5) C (collector daemon plus 3 live-config edits) and D (Phoenix or Langfuse) are clearly overbuilt now, as the report itself says. (6) The completeness check that matches every Bash engine call in the COO transcript against runlog events is a second parser of Claude transcripts. A simpler first check is enough: every result file has an end event.

### Blind spots
Claude Workflow: cached or resumed agents report null tokens and duration, so a resumed run under-reports its true cost. In wf_fc2ffa51-890, rounds 1-2 are missing, and recovering them means finding the earlier session's agent transcripts. Retries are new labels, not attempt>1, so any option keyed on attempt misses every retry. Runs that crash or are killed may have no run JSON. The COO main-session tokens are not in the run JSON at all. Claude cost-state USD is a list-price estimate, not what the subscription actually bills. Codex: the options get tokens but no money, and they cannot tie a call to a run without the wrapper. Under Option A alone, overlapping calls make the match ambiguous. qwen: covered locally, but telemetry.logPrompts must be set to false explicitly under C. agy: there are no readable tokens in any option (protobuf), and no telemetry. Gemini CLI (0.61.0 is installed per tools:F4) is in no option, yet memory says Gemini 3.1 Pro is assigned to classification. If that runs through gemini rather than agy, every option misses it. Copilot (30,000-credit budget, Kubernetes work) is in no option, so its credit spend is invisible. Data that does not exist: a per-node split of COO tokens, a verifier verdict per node (no engine emits one, so it must be written by the workflow), brief variant, and EJ interventions. Option C also needs codex and qwen to honour TRACEPARENT, which is unchecked.

I would keep the direction (A then B, with C and D deferred) and narrow it. (1) Start the harvester on Workflow run JSON plus codex rollouts only. Derive rounds from the '#n' label suffix and logs[], not from attempt. Mark cached agents as 'cost unknown' rather than counting them as zero. (2) Do not use wf_fc2ffa51-890 as the trial run. Use wf_0349f318-dcc or wf_c59cf053-175 (no cached agents). Replace check (a), which is true by construction, with a check against the agent-<id>.jsonl message.usage sums. (3) In B, write only one verdict line per node (run, node, round, check, pass) and pass run_id into codex calls. Add the qwen/agy/Gemini wrappers and the hand-off and artifact fields once a run actually uses them. (4) The first consumer should be the existing ledger's 'Actual cost' column, not a new digest. (5) Before trusting run JSON for failed runs, check whether a killed or failed Workflow run writes one at all. (6) Add runs/*/raw/ to .gitignore. It does not exist yet: today's .gitignore covers only *.db, *.sqlite and .qwen/, and 453 files under runs/ are tracked in a public repo. That .gitignore edit should be shown to EJ before it is made.

### First measurement
For one real run with no cached agents, a cost and outcome table per node: tokens and wall time summed across all rounds, plus first-try check pass/fail. Its totals must match the engines' own records within a tolerance stated before the run (agent-<id>.jsonl usage sums and codex token_usage_record). It must be entered as the first TASK_TYPES_LEDGER row, Actual cost next to a Projected cost written down before the run. Without the pre-registered projection and the independent match, the trial only shows that a parser runs. It does not show that the feedback loop can test a design claim.

### Risks
Privacy: the repo is public and runs/ is tracked (git ls-files runs = 453, checked). Run JSON promptPreview/resultPreview, Claude and qwen transcripts, codex stdout/stderr in exec_command_end, and Claude OTel user.email attributes must never reach runs/<id>/. There is no gitignored raw/ path yet, so one accidental write could be pushed.
