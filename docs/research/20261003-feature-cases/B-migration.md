# Findings — case B: clear requirements, migrating from an old system
Produced 2026-10-03 by a research agent. Question asked: how should a single developer (EJ) who directs AI coding agents best build a feature by migrating it from an old system to a new one, when the old system's behaviour is the spec — what makes this case different, what goes wrong in practice, and which practices handle it well (established practice and what is known in 2025–2026 about AI-assisted legacy migration)?

Labels: **verified** = I read the primary source myself (full text, README or arXiv abstract page fetched raw and searched); **reported** = a secondary source or a summarizing fetch; **unknown** = not settled. For arXiv papers marked verified from the abstract only, the finding uses only what the abstract says. Local sources are the files named.

| B1 | A characterization test (also called golden master testing; term coined by Michael Feathers) describes the *actual* behaviour of existing software. It recommends tests to prove parity and asking users which features are low value or unused. | verified | https://martinfowler.com/articles/patterns-legacy-displacement/feature-parity.html |

It names Feature Parity as a factor in several failed programs. | verified | https://martinfowler.com/articles/patterns-legacy-displacement/ |
| B6 | Diffy sends each request to three instances: candidate (new code), primary (known-good code) and secondary (the *same* known-good code). Nested or complex columns are not supported for column or row checks. | verified | https://github.com/GoogleCloudPlatform/professional-services-data-validator (README) |
| B10 | "Lost in Translation" (ICSE 2024) ran 43,379 translations of 1,700 samples between C, C++, Go, Java and Python with 7 LLMs (2023 models). On the two real-world projects (Commons CLI, Click), GPT-4 reached 8.1% and every other model 0%. | verified | https://arxiv.org/abs/2308.03109 (HTML full text) |

## What makes this case different

- **The oracle already exists and can be run.** In case A the truth lives in EJ's head, in C it is a new criterion plus a baseline, and in D there is no baseline at all. In B the old system answers "what should happen for this input?" mechanically, which makes it a historical oracle (B1). That makes B the only case where the tester's oracle can be fully automatic (B6, B7, B22, B24). It also means a *description* of the old system is never the oracle. At best it is an intermediate document for the dev (B25, B21).
- **The spec is everything observable, not just what was intended.** Users and downstream code depend on accidental behaviour (B2): bugs, workarounds (B3), data-type and precision quirks (B11), and interval boundaries (B16). So "requirements are clear" is true only in the sense that they are *checkable*. They are not *known* until extracted and tested.
- **Full parity is itself a scope decision.** Porting everything carries the parity trap's cost: unused features, bug workarounds and off-system processes (B3, B4). Case B therefore needs a deliberate "do not migrate" list, which the other cases do not.
- **There are usually two deliverables: code and data.** Data checks (counts, aggregates, row hashes, read comparison before switching reads) are their own work (B8, B9).
- **Cutover is gradual.** Parallel run, dark launch, transitional pieces and diverting the flow apply here (B5, B6, B8); cases A, C and D have nothing to run in parallel against.

## What goes wrong

1. **Plausible but wrong extraction.** A fluent summary misses details that only execution exposes (B25). LLMs judging equivalence barely beat chance on hard pairs and go by surface similarity (B21). An LLM reviewer is therefore not a parity check.
2. **Implicit behaviour lost in translation.** The commonest classes are data types and precision, input parsing, output formatting, mutability, API substitutes that behave differently, and half-open intervals (B11, B16). Encodings, time zones and rounding were not measured separately in any source I read. My inference is that they fall in the same classes (data types, parsing, formatting).
3. **"Tests pass" is weaker than parity.** Industrial pipelines validate mainly with build plus the *existing* unit tests (B15, B16). Weak suites let wrong translations through (B12). Bugs can pass unit and fuzz testing yet fail symbolic differential testing (B23). Even with validation, humans had to revert incorrect or unneeded changes in most cases at Google (B16).
4. **Agents change the yardstick.** Tests get renamed, disabled or removed during migration, so the benchmark must guard against it explicitly (B19). Pre-existing failures poison the signal (B15).
5. **Logic added or dropped, and noise edits.** Translations remove source logic, add logic that was not there (B11), or make edits that only reformat or add comments (B15).
6. **Scale collapses accuracy.** Measured success falls from snippet to repository level: B10 (GPT-4 benchmarks 47.3% versus real projects 8.1%), B13 (32.8% repo level), B14 (96.40% syntactically correct versus 25.14% functionally validated). Direction matters: dynamic→static is under 10% (B13).
7. **False mismatches.** Without measuring old-vs-old noise, diffs flood with timestamps and randomness. People then start ignoring diffs wholesale (B6, B7).
8. **Porting what nobody needs.** Effort goes to dead features and bug workarounds, while vital features get cut late (B3, B4).
9. **Overstated success numbers.** Headline numbers are developer estimates or unpublished methods (B15's 50%, B17, B18's 9-file basis, B20). They show the method works at some companies. They do not measure correctness.

## Recommended handling for EJ's method (each point citing finding ids; mark anything that is your inference)

Concrete changes to the case-B lead-in (TASK_TYPES "Lead-in by case") and the tester's parity oracle:

1. **Lead-in step 0, scope cut before extraction (change to lead-in).** List the old behaviours (entry points, outputs, side effects, known bugs and workarounds). EJ marks each one *port*, *drop* or *change deliberately*. Dropped and changed items become explicit rows, not silent omissions. (B3, B4; one EJ approval, matching the case-A style, is my inference.)
2. **The oracle is the old system's recorded output, never the extracted description (change to oracle).** Golden input/output pairs are produced by *running* the old system. When the old code can be called, the tester differential-tests old against new directly, as Scientist or Hypothesis would (B7, B22, B24). The extraction is still checked against the old code with `verify-extraction` (B25), but only because it feeds the dev. The tester never uses it as an oracle.
3. **Noise baseline before any diff (change to oracle).** Record each golden twice (old against old) and list the fields that differ. The comparator gets an explicit ignore or normalise list, each entry with a reason, and the join report prints the list. (B6, B7)
4. **Golden-input selection targets the measured bug classes (change to oracle).** Mix sampled real inputs with generated edge inputs aimed at data types and precision, parsing and formatting, empty or null, boundaries and intervals, error paths and immutability (B11, B16). Errors are compared as values too (B7's `compare_errors`; the verify-extraction note that exceptions are a second axis). Encoding, time-zone and rounding cases are my inference from the same classes, not measured.
5. **Tamper guard in the join check (change to join check).** Golden files and the tester's cases are read-only to the dev. The join fails if any golden case name disappears or the count drops. (B19, B15)
6. **Known-difference ledger.** Every intentional divergence (an old bug fixed rather than ported) is a ledger row with the golden updated, the reason and EJ's approval. Nothing goes into the comparator's ignore list without one. (B3, B7; the ledger form is my inference.)
7. **Data-migration checks as three named levels (change to oracle "plus data-migration checks").** (a) Schema. (b) Counts and per-column aggregates, grouped by a business key. (c) Row-level hash joined on primary key. (d) If data stays live, a read comparison of old and new paths before reads switch. Counts alone are not accepted. (B8, B9; "counts alone not accepted" is my inference from B9 offering finer levels.)
8. **Translate small, in dependency order, cheapest checks first.** Each piece passes build, unit tests and then its goldens before the next piece builds on it. Failures go to the COO or EJ rather than being retried without end. (B14, B15, B17) Inference: for *mechanical* per-file translation, a separate bounded retry budget with error feedback is supported (B12: +5.5% average; B17: 10 iterations covered 75%). Keep the method's 2-round cap for design-level fixes.
9. **No LLM-only parity verdicts.** The COO review checklist stays a checklist. "Matches the old system" is answered only by execution (B21, B25, B23).
10. **Readiness rule extended (change to readiness).** Today a case-B run with no access to the old system is not ready. Extend that to: not ready without a way to *record* old outputs on representative inputs. If the old system can only be observed and not called, use approval testing on recorded I/O (B1; `verify-extraction` step 2, third bullet).
11. **Cutover only for live systems.** If the old system serves real traffic, run the new one in shadow or dark-launch mode before switching (B5, B6, B8). Inference: for EJ's typical single-developer case, offline replay of recorded inputs is the proportionate form.

## Gaps

- No source measures AI-assisted migration by a single developer directing agents. All industrial reports are large teams with in-house tooling (B15–B20).
- Most measured translation rates use 2023–2024 models (GPT-4, Claude-2, Claude 2.1). MigrationBench (B19) is the only one with a 2025 model, and it covers a version upgrade, not translation to another language. How current models (Codex GPT-6-sol and others) do on parity is **unknown**.
- Airbnb's primary post could not be fetched (403), so B17 stays reported. Amazon's figures (B20) have no published method.
- No source quantified failures specific to encoding, time zones or rounding. Recommendation 4 extends the measured classes by inference.
- How many golden pairs are enough, and how to sample them, is **unknown**. No source gave a sizing rule. Hypothesis' 5,000-case budget in B25 is n=1.
- Feathers' and Bache's primary texts on characterization and approval testing were not read; B1 is secondary.
- Data-migration practice here comes from tool documentation and one company's blog (B8, B9), not from comparative studies.
- EquiBench (B21) measures equivalence judgment on synthetic pairs, not review of real migrations. Applying it to reviewers is an inference.
