# Findings — case C: clear requirements, new feature in an existing system
Produced 2026-10-03 by a research agent. Question asked: how best to handle adding a new feature to an existing system when the requirements are clear — which first needs scanning and understanding the existing system — for one developer (EJ) directing AI coding agents (a main Claude session as leader; Codex, agy and qwen as tool agents): what makes this case different, what goes wrong in practice, and which practices handle it well (established practice, and what is known in 2025–2026 about agents in existing codebases).

Labels. *verified* = the primary text was read raw (arXiv HTML or the page itself fetched with curl and searched for the quoted sentence or number). *reported* = a search-engine summary or a summarizing fetch, not the primary text. *unknown* = not settled by the sources. Benchmark numbers give benchmark, date and conditions. Note: in two papers the summarizing fetch got numbers wrong (SWE-Bench Pro failure shares; the AGENTS.md study's +4%). The raw text was used instead, which is why the raw read was needed.

## What makes this case different

- **The truth has two sources, and the oracle has two halves.** The new requirement says what must be added. The existing code says what must stay. Case A has no settled requirement. Case B uses the old system as the spec (parity). Case D has no baseline. In case C the tester's oracle is "the new criteria pass" and "everything that passed before still passes", and on today's agents the second half is the one that fails (C8, C9, C10).
- **Comprehension is the main cost, not a preamble** (C1). The relevant code is spread across files: about half of real feature tasks need more than one file changed (C10), and harder benchmarks average about 4 files (C11).
- **The main risk is a connection nobody knew about.** Reading only the code near the change misses interactions (C2). Scope-creep edits by the agent create new unknown connections (C9).
- **Conventions are implicit.** The code expects certain patterns, layering and ORM use that no requirement states. Agents get much worse as these accumulate, and also when they must infer them from an existing codebase (C17).

## What goes wrong

1. **Regressions while adding the feature.** This is the top failure on feature benchmarks: 73.6% of analysed FeatBench failures (C9). Regression pass rates on FeatBench are 25–50% (C8), and 62–77% of Doc2Feat patches pass all regression tests (C10).
2. **Scope creep.** The agent refactors or extends beyond the request, which breaks existing behaviour (C9). Larger, many-file agent PRs are the ones not merged (C23).
3. **Incomplete context (low recall).** Agents find the right files but not enough of the right lines. Missing context is the dominant failure, with a threshold effect (C18). Not understanding existing modules is a named cause in Doc2Feat (C10).
4. **Too much reading.** Context overflow and endless file reading are measured failure modes (C12). Failed runs are longer (C19).
5. **A baseline that is too narrow.** Checking only nearby tests lets breaks elsewhere through (C13).
6. **Conventions in prose get ignored or cost a lot.** Instruction files are followed only partly (C16). LLM-written overviews add cost and no benefit (C14). Non-functional rules are rarely written down at all (C15).
7. **Overconfidence in the speed-up.** Developers misjudged AI's effect on familiar repos, and the current size of the effect is unknown (C24).

## Recommended handling for EJ's method (each point citing finding ids; mark anything that is your inference)

Concrete changes to the case-C lead-in (TASK_TYPES "Lead-in by case", row C):

1. **The scan must produce a fixed-shape impact map, not a free-form summary** (lead-in change). It has seven sections, and every entry carries a `file:line` reference:
   - (a) **focus points**: where the requirement's behaviour enters the code (C3, stage 1);
   - (b) **extension points**: the seams where new code plugs in without editing callers (C6);
   - (c) **one-hop impact**: direct callers and callees of every symbol that will change, from a plain call graph or grep (C5: the basic call graph has the best precision/recall trade-off);
   - (d) **shared state**: tables, config keys, files and globals the feature reads or writes, and who else touches them. *Inference*: interactions run through data as well as calls (C2);
   - (e) **conventions**: 3–5 nearby examples of how the code already does the same kind of thing (C17);
   - (f) **tests covering each entry, and the gaps**: entries with no test;
   - (g) **"must not change"**: the list the dev's contract and the COO checklist will use.

   Because a second LLM read is not a check, the map's claims about behaviour go through `verify-extraction` (TASK_TYPES #1) before any build node uses them.
2. **Depth: systematic inside the affected area, not across the whole repo** (lead-in change). Trace data and control flow fully through the focus points plus one hop and the shared state (C2, C3). Do not write a repo-wide overview: overviews do not help agents locate code (C14), and over-reading is a failure mode (C12). Stop when sections (a)–(g) are filled with evidence. Give the node a tool-call or token budget and treat hitting it as a failed attempt (C12, C19). When unsure, prefer recall: missing context hurts more than extra context (C18). *Inference*: "one hop" is a starting rule at n=0. Raise it to two hops when (c) lists a symbol with many callers.
3. **The baseline must be the full suite, recorded per test** (lead-in change; method 3.6 part 2). Before any build node starts, run the product's whole test command, not only nearby tests (C13). Write the result as a list of test ids with pass/fail into the state file; that list is the pass-to-pass set the join check compares against (C8, C10). *Inference*: run the suite twice and mark tests that disagree as flaky, so they do not count as regressions later.
4. **Fill the coverage gaps with characterization tests before the change** (lead-in change). For each entry in (f) with no test, a node writes characterization tests at the seam: tests that pin what the code does now (C7). They join the baseline and get the method's sabotage check (they must fail on a deliberately altered build). *Inference*: if most of the affected area has no tests, the run is closer to case B, and EJ should be told before building.
5. **Make scope creep a checked failure.** The dev's contract forbids changes outside the impact map's files unless a reason is listed. The COO's one-round checklist gains one line: "every file in the diff is in the map or has a listed reason" (C9, C23). Behaviour changes outside the criteria go to `backlog.md`, as method 3.6 already says.
6. **Turn conventions into checks where possible, and keep context files minimal.** Each convention in (e) that can be expressed as a grep, lint rule or small script becomes part of the join check (C16: 88.3% versus 67.0% for prose-only). CLAUDE.md/AGENTS.md hold only tooling and non-standard rules; do not ask an agent to generate an overview file (C14, C22).
7. **Exploration engine: agentic search first, a repo map only for large repos.** The scan node uses grep/read exploration, which beats one-shot embedding or BM25 retrieval (C18). *Inference*: for a repo too large to grep comfortably, add an Aider-style ranked map (C21) or a code graph (C20) as the starting point. Both are measured on bug fixes, not features, so treat this as unproven for case C.
8. **Tester in case C** (*inference*). The tester stays blind to the dev's code, but gets the impact map's (c), (d) and (g), so some of its cases target the boundaries where the feature meets existing code. That is where the measured failures are (C9, C10).

## Gaps

- No source measures whether an impact-map-first step improves agent success on feature tasks. Recommendations 1–2 and 8 rest on human studies (C2, C3) and on bug-fix agent studies (C18, C20). n=0 for the method.
- Feature benchmarks (C8, C10, C11) are mostly Python and open source. The commercial-set drop (C11) suggests private code is harder, but nothing measures EJ's own repos or the Codex/agy/qwen mix.
- Littman (C2) and Sillito (C3) are small, old human studies read only through secondary summaries (reported). Koenemann and Robertson (1991) found experts read code *as needed*, which may counter C2; it was not read (the PDF is a scan).
- The one-hop rule and the scan budget are guesses; no source gives a depth number.
- The size of AI speed-up or slow-down on familiar mature repos is unknown (C24).
- Characterization tests for non-deterministic or external-service code were not researched.
