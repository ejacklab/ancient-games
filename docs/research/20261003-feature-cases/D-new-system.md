# Findings — case D: feature for a new system
Produced 2026-10-03 by a research agent. Question asked: how should EJ's method handle building a feature for a brand-new (greenfield) system, where a main Claude session leads and Codex/agy/qwen are tool agents — what makes this case different, what goes wrong in practice, and which practices handle it well (established practice, and what is known in 2025–2026 about AI agents building new systems from scratch)?

## What makes this case different

- **There is nothing to copy and nothing to protect.** In case C the existing code is both the agents' pattern library and the regression baseline. In case D there is neither: no conventions an agent can imitate, and no baseline for the tester (TASK_TYPES already says "there is no baseline yet").
- **The first code becomes the architecture.** People and agents both copy what is already there (D3; the Claude Code guide's advice to "reference existing patterns", D16). So the first slice sets the style, the layering and the security defaults for everything after it, and decisions the blueprint leaves open get made by the first agent to write code. Left alone, agents tend to make monolithic, single-file code (D6).
- **Decisions are cheapest to change now, but also least informed.** This is the tension between deciding at the last responsible moment and the most responsible moment (D2, D3). A few decisions are expensive to reverse once code exists (stack, the main architectural parts, the data store, the auth and security model). Most others are not.
- **Agents are weakest at exactly this task.** Building whole systems from scratch is where measured agent success is lowest (D6: best model passes 95% of tests on 3% of tasks; D7: 30–55%). Patch-level benchmarks do not carry over.
- **The case happens once.** After the first slice ships, the next feature has an existing codebase, so it is case C. The method's rule "an existing codebase is never case D" already implies this; the lead-in should say so out loud.

Contrast: A's risk is the wrong target (fixed by asking EJ), B's is a plausible but wrong reading of the old system (fixed by a differential test), and C's is an unseen coupling (fixed by a baseline). D's risk is that structure is either fixed too early on paper or, more often in practice, fixed by accident in the first generated code.

## What goes wrong

1. **No design (vibe coding).** Generated systems arrive inconsistent, duplicated and insecure: about 1.7× more issues per PR, more naming and readability problems (D21), more duplication and less refactoring (D22, correlational), security flaws in 45% of tests regardless of model size (D19), and missing authorization at the data layer in real deployed apps (D23).
2. **Fix loops quietly make security worse.** Iterating "improvements" with an LLM raised critical vulnerabilities by 37.6% after five rounds (D20). An unbounded or unchecked repair loop is a security risk as well as a cost.
3. **Too much design (spec waterfall).** Full spec pipelines produce more markdown than a person can review (D12: 2,067 lines for one plan step; D11, D13). Agents still ignore parts of the spec or over-apply single rules (D11), and the result can still be about 10× slower than iterating with review (D12; n=1, existing app). The spec feels like control without giving it ("false sense of control", D11).
4. **Architecture fixed too vaguely.** Prose choices that nothing checks drift: Nygard's "afraid to change anything" (D4) and the agent copying whatever the first slice did (D3).
5. **Conventions written as long prose.** Long or agent-generated context files cost more than 20% extra and do not raise success; repository overviews do not help (D15). Bloated files get ignored (D16).
6. **No runnable check from day one.** Without tests, CI and lint, the agent's own "looks done" is the only stop signal (D16, D18), and from-scratch builds stall below full correctness (D7).
7. **Stack chosen for novelty.** Agents are measurably weaker in less-represented languages and libraries (D24), and an unrecorded stack choice gets re-argued or worked around later (D4, D14).

## Recommended handling for EJ's method (each point citing finding ids; mark anything that is your inference)

**R1 — Replace "all eight blueprint sections settled first" with a two-tier rule (change to the case-D lead-in).** *Inference, built on D2, D3, D8, D11–D13, D17, D25.* "All eight settled first" is too heavy, and it is also aimed at the wrong thing. The method's own reason for the blueprint is a fixed target for stop conditions (method §3.1). That needs the criteria in scope and the hard-to-reverse decisions, not a finished domain, data and UI design for the whole product. Proposed rule: all eight sections **exist** (none missing, so the blueprint check still passes for "new product"), but only these must be **settled** before scaffolding:
- 1 vision;
- 2 requirements, i.e. the R-blocks of the first slice with checkable acceptance criteria;
- 5 architecture, i.e. only the hard-to-reverse choices (stack, main parts, data store, auth model), each as a short ADR in `decisions.md` (D4);
- 8 non-functional, with security as N-criteria that a test can check (D19, D23).

Sections 3, 4, 6 and 7 are settled **for the slice being built** and stay draft beyond it. Unknowns are marked as questions, not guessed (D9). This matches Spec Kit's own split, where the constitution is project-wide and specs are per feature (D8). EJ decides whether to amend the method §3.1 "New product → all eight" row the same way or to keep it as is. Confidence is low: there is no controlled evidence either way (D25).

**R2 — Add a walking-skeleton node between the blueprint and the build-a-feature steps 3–5 (change to the lead-in).** *Built on D1, D3, D6, D16, D18; the node shape is inference.* After the blueprint, one node scaffolds the repository with a minimal end-to-end path through every main architectural part, plus lint/format, type check, test runner, CI, and a preview or run command. Check: CI green, and one end-to-end test passes through all layers. Sabotage: break one layer, and the end-to-end test must fail. The COO or EJ reviews this node line by line, because every later agent copies it (D3). Only then do dev ∥ tester start on the first slice.

**R3 — Give case D a structural baseline in place of the missing behavioural one (change to the "Tester's oracle" cell).** *Built on D5, D6, D20–D23; inference that these stand in for a baseline.* Oracle = the criteria **plus** the skeleton's end-to-end test **plus** fitness functions written at scaffold time:
- dependency/layer rules that block a single-file monolith (D6);
- a duplication threshold (D22);
- a SAST/secret scan;
- an authorization test per data entry point (D23).

These join the three-part join check. A security rescan runs after every fix round, because fix loops can degrade security (D20). The existing 2-round cap stays.

**R4 — Write the conventions file first, short and by hand, and enforce it with tooling (change to the lead-in).** *Built on D14–D16.* At scaffold time, write AGENTS.md/CLAUDE.md with only what an agent cannot infer: commands, non-standard conventions, pointers to the ADRs. Follow Kiro's split of product / tech / structure (D14). Do not have an agent write a repository overview (D15). Anything that must always hold becomes a lint rule, hook or fitness function rather than prose (D16). This also covers the Codex/agy/qwen nodes, which read AGENTS.md but never run Claude hooks (inference).

**R5 — Choose a mainstream stack and record why (change to the lead-in).** *Built on D24, D4, D14.* Readiness asks whether the stack is well represented in model training (a popular language and libraries). The choice and the rejected alternatives go into `decisions.md` before scaffolding.

**R6 — Name the hand-off to case C (change to the TASK_TYPES case rules).** *Inference.* Case D covers only the run that creates the skeleton and first slice. Its last step records the regression baseline (tests plus fitness functions), so the next feature enters as case C.

**R7 — Keep the agent's spec output small enough to review.** *Built on D11–D13, D17.* The COO's design node writes per-slice specs that name files and interfaces, state what is out of scope and end with an end-to-end check (D17). No generated user-story sets. The tester's blind cases stay the check on whether the spec was followed (D11: agents do not reliably follow specs).

## Gaps

- No controlled study compares full up-front specs with skeleton-first slicing for agent-built greenfield systems (D25). The SDD evidence is n=1 practitioner reports (D11, D12), and D12 was on an existing app.
- ProgramBench and RepoZero (D6, D7) are reproduction tasks with a reference program or API spec. Open-ended greenfield with a human blueprint is untested, so success rates may differ in either direction.
- The AGENTS.md study (D15) used existing repositories. In a new repository with no README or code to read, a short conventions file may matter more. Unknown.
- Only abstracts were read for the arXiv papers. Veracode's details and the GitClear, Lovable and Poppendieck sources were not read at the primary source (D2, D19 details, D22, D23 reported). Cockburn's original walking-skeleton page returned 404.
- How much the fitness functions in R3 cost to write and keep up for a single developer: no source found. It needs a ledger entry after the first real case-D run.
- R1–R7 are n=0 in EJ's method. Per house rules, none should become a rule before two real runs.
