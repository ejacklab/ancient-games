## For the builder

**Build:**
- `tools/memory_index.py`: Python 3, standard library only. Next to `tools/export_skills.py`; the repo has no
  `scripts/`.
- `tests/test_memory_index.py`: run with `env -u NO_COLOR python3 -m pytest -q`.
- `.githooks/pre-commit` and `.githooks/pre-merge-commit`. The second is one line that runs the first.

**Do not, without EJ's go:**
- edit `docs/memory-system/SOURCE_OF_TRUTH.md`, `CLAUDE.md` or `AGENTS.md`;
- run `git config core.hooksPath .githooks`;
- create `project-memory/` in this repo.

**When something here is unclear or looks wrong,** stop and record it. The requirements are still under review in
another session; do not settle a requirement by building it.

## The algorithm

**Build the index** (shared by both modes):

1. **List entry files** (B1). Take files directly in `project-memory/entries/` whose name matches `^[DFLOH]-[^/]+\.md$`.
   - **Write mode:** list them with `git ls-files -z --cached --others --exclude-standard -- project-memory/entries/`.
     Any file that is in `--others` (untracked) is an error naming it: "git add it first".
   - **Check mode:** list them with `git ls-files -s -z` (the staging area) or `git ls-tree -r -z <rev>`, then read
     every blob in one `git cat-file --batch` call. On this machine, one call per file was about 20 times slower.
2. **Sort** the file names with Python's default `str` order (code points). Never use locale collation or directory
   order (B3.1).
3. **Decode** each file as UTF-8, and turn CRLF into LF. A decode error becomes `<file>: not valid UTF-8` (B2.6).
4. **Parse** (B2.1, B2.2).
   - **Header:** line 1 must be `---`; it ends at the next line that is exactly `---`. Read top-level `id:`, `kind:`
     and `status:` as `key: value`, stripping whitespace and one pair of surrounding quotes.
   - **Claim:** the text after the header, up to the first line that starts with `**Why:**`. Drop blank lines,
     collapse whitespace runs to one space, and strip the ends. *Known limit:* this also collapses spaces inside an
     inline code span (r codex 8). It is accepted, since claims are plain sentences.
5. **Validate** (B2.3–B2.5). Collect every problem and report them all.
   - **Errors, for every entry:** no header; empty `id`; `status` not one of active, superseded or retired; a
     duplicate `id`; an `id` not in W1.1's form; a line starting `<<<<<<<` or `>>>>>>>`; a known credential (B2.8),
     reported with its kind and line number, never its text.
   - **Errors, for active entries:** `kind` not one of the five; file prefix not matching `kind`
     (D decision, F fact, L lesson, O observation, H hypothesis); no `**Why:**` line; empty claim.
   - **Warnings:** anything else wrong in an inactive entry.

   Any error: print `<file>: <problem>` lines, write nothing, exit 1.
6. **Render** (B3). The bytes are exactly:
   ```
   # Project memory index

   <!-- Generated by tools/memory_index.py from project-memory/entries/. Do not edit by hand. Rebuild: python3 tools/memory_index.py -->

   - [<id>](entries/<urllib.parse.quote(file name)>) <kind>: <claim>
   ```
   - One line per active entry, in step-2 order. With none, the line `(no active entries)`.
   - UTF-8, LF, one final newline. No date, count or host.
7. **Measure** (B4). Read the limits (B4.1, B4.5): `project-memory/start-limits.json` from the same tree as the
   entries — the working tree in write mode, the snapshot in check mode. A bad file is an error (step 5's rule:
   print, write nothing, exit 1). With no file, use `MAX_LINES` and `MAX_BYTES`, two constants at the top of the
   script, whose comment cites Rd3.1 and says the values are the design's example. For each unit the smallest row
   applies; a unit with no row keeps the example. Count lines, UTF-8 bytes and, when a `characters` limit applies,
   code points. Print `INDEX.md: <lines>/<l> lines, <bytes>/<b> bytes` (plus `, <characters>/<c> characters`) and
   then `limits: project-memory/start-limits.json` or `limits: the design's example (no
   project-memory/start-limits.json)`, on every run.

**Write mode:** `python3 tools/memory_index.py`

8. Run steps 1–7 on the working tree.
   - If the result equals the current `INDEX.md` byte for byte, leave it alone.
   - Otherwise write a temporary file in the same folder and rename it over `INDEX.md`. A missing `INDEX.md` is simply
     written.
   - Over the size limit: still write the whole file, print a warning, and exit 0 (B4.3).
   - It writes nothing but `project-memory/INDEX.md`.

**Check mode:** `python3 tools/memory_index.py --check [<rev>]`

9. Run steps 1–7 on the snapshot and compare with the snapshot's `INDEX.md` (C1).
   - Exit 0 only if the entries are valid, the bytes are equal and the size is within the limits.
   - Otherwise exit 1 with the reason. If the bytes differ, also print a `difflib` unified diff and the fix: stage the
     entries, run `python3 tools/memory_index.py`, then `git add project-memory/INDEX.md`.
   - No `project-memory/` in the snapshot, or an unborn `HEAD`: exit 0, "nothing to check".

**The hook** (G2)

10. `.githooks/pre-commit`:
    - If `git diff --cached --name-only -- project-memory/ tools/memory_index.py` is empty, exit 0.
    - Otherwise run `python3 tools/memory_index.py --check` and return its exit code.

    `.githooks/pre-merge-commit` is `exec "$(dirname "$0")/pre-commit"`. git runs `pre-merge-commit` on a clean merge,
    and `pre-commit` on the commit that ends a conflicted merge (`githooks(5)`, git 2.43, verified).
11. The tests (C2) run `--check HEAD` on the repo, which covers what the hook misses: rebase, cherry-pick,
    fast-forward and `--no-verify`.

**Merging** (G3)

12. `INDEX.md` merges as plain text. When it conflicts, resolve the entries first, then run write mode, stage
    `INDEX.md` and commit. The pre-commit check confirms the result.

## Why this shape (from the run)

1. **One file per entry with a generated combined file** is what ended shared-file conflicts elsewhere (C31). Committing
   it is what Rd1.2 needs. Sorting by file name puts parallel additions on different lines. That merges are therefore
   mostly clean is *not measured*.
2. **Same entries, same bytes,** so "regenerate and compare" is an exact check (Kubernetes and Cog work this way: C54,
   C55, X31). Qwen Code switched to code-point order after locale order made collaborators rewrite the file back and
   forth (C2).
3. **Nothing is cut.** Every overflow scheme found either drops active entries or changes what sessions load (C45,
   C46, C52). The mechanism is chosen when it is needed.

## Must not

1. Edit or hand-merge `INDEX.md`, or give it `merge=union`. `union` silently re-adds a superseded entry's line (C36).
2. Let the output depend on the machine: locale, directory order or a timestamp (C2, C14, C15).
3. Truncate, drop, rank or dedupe lines to fit (C45, C46).
4. Skip an invalid active entry, or write a line with a hole in it (X4, X33).
5. Rely on the hook alone. Hooks are not cloned, and rebase and `--no-verify` skip them (G2.3).
6. Stage, commit or push anything, or change an entry. The script writes `INDEX.md` only.
