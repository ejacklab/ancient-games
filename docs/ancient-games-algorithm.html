The method

Turns a task into a designed workflow — its sections, 3.0–3.8.

  1. 3.0 Understand — objective, scope, six whys, category.
  2. 3.1 Readiness — prove the tools work; check the blueprint.
  3. 3.2 Write the algorithm — each step names its check; label the pieces.
  4. 3.3 List every unclear spot — before resolving any.
  5. 3.4 Size — a prompt file, or a full workflow; default-first.
  6. 3.5 Loops — clear pieces run with a check, a limit, feedback, an exit.
  7. 3.6 Graph — the rest wires up; a run ends at the criteria, the baseline, and "must not change".
  8. 3.7 Sequential first — parallel is the last decision.
  9. 3.8 Run a node — executors are tools; two timers; a pass-back; no polling.

The referee

Clears the plan before the work runs — 5 stages, fixed rules.

The code makes no LLM calls; some steps are LLM judgments passed in as inputs.

  1. Gate — how many agents (resolved if a cheap probe already answers; split when more than 3).
  2. Guard — which actions need approval.
  3. Corroborate — how many independent sources a claim needs, scaled to the stakes.
  4. Filter — which candidates survive.
  5. Prove — is the plan cleared (pass, or back to the planner with findings).

Words used above

blueprint — the product's fixed spec (vision, requirements, architecture…). six whys — six questions that each feed one design field. unclear spot — a missing fact or an unmade decision. default-first — start from the type's default pattern; challenge it only with a reason. baseline — the tests and their output, recorded before any build. "must not change" — what a piece is forbidden to touch.

The method designs; the referee clears; the workflow runs. Feeding the findings back into the method is the goal, and is not wired yet — drawn as a dashed arrow until it is.
