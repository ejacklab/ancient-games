The workflow-design method

The method half of the Ancient Games: it turns an incoming challenge into a prompt file (small task) or a workflow design (bigger task). It designs; it does not run anything.

Is it tiny? (method §2) — after 3.0, if the restated problem, the fix and the check are one sentence each, and being wrong would show itself at once: write the prompt file by hand, or just do the task. Running the method on such a task costs more than the task.

3.0 Understand the challenge — before anything

EssenceFrom the challenge text alone — no tools, no agents, no repository browsing — state the objective (what is true when the task is done), what is in scope and what is out of scope; then answer the six whys; end with a provisional category, a guess that 3.2 relabels.

WhyThe restatement goes at the top of the output, so EJ sees and can correct what the run understood before tokens are spent. A part that cannot be written, or a challenge with two readings, is the first unclear spot.

The six whys — stop early once an answer no longer changes the design
  1. Why does EJ want this — what problem is behind the ask? → the objective
  2. Why now — what triggered it? → priority; whether a cheaper fix exists
  3. Why this shape of solution? → the provisional category and its default pattern
  4. Why would it fail? → the risk tier, so review depth and independent checks
  5. Why does it stop where it stops? → in scope / out of scope
  6. Why would we believe it is done? → the stop condition and check kind (script, checklist, EJ)

Cost: one paragraph and six short answers in the same session — never an agent, never a tool call. · Skill: “First: understand the challenge”.

3.1 Readiness — always first

EssenceList the tools, each with the command that proved it works — run it, do not assume; the skills that already cover part of the work; and the information: is it there, what structure it is in, and which agents and tools can use it. For a product change, add the blueprint check.

WhyAnything missing becomes a preparation piece at the front. A stop condition means something only against a fixed target: a piece that builds does not start until every blueprint section it depends on is settled, and blueprint questions are not answered by silence.

Git is not required; the baseline is the product's test command and its output. · Skill: step 1.

3.2 Write the algorithm

EssenceTry to write the steps that would solve the task. A step is one action with a result that can be checked. Then group the steps into pieces — consecutive steps that end in one deliverable — and give each a category from TASK_TYPES.md.

CheckA step that cannot be written clearly, or that has no check you can name, is an unclear spot, however tidy it looks. A label is not a node: pieces that share an engine and have no independent check between them merge into one node run by the main agent.

A piece that changes product code, schema, UI or configuration is never labelled read-only; a contradicting label is a stop and replan. · Skill: step 2.

3.3 List all the unclear spots before resolving any

EssenceFor each spot record its kind — missing information → a research piece · a decision → ask EJ · unknown → a bounded explore loop — which steps it blocks, and which other spot it depends on.

WhyAnother spot's answer might remove or change this one. Questions for EJ go out as one batch, each with a provisional assumption so it can be answered in a few words. A contradiction between answers is a stop: pick one and say why, never average.

Skill: step 3.

3.4 Size

EssenceUp to 3 steps, and nothing unclear except decisions that have a provisional assumption → one piece → a prompt file. Otherwise a workflow design, which starts default-first from each piece's category row in TASK_TYPES.md.

CheckSplit only if each part keeps its own check and splitting changes how the work is done. Work that is hours long is not a piece: split it into six or more logical pieces, never one huge prompt. Risk is judged separately from size — tiny but risky gets one independent check.

A spot of kind information or unknown always means a workflow design. · Skill: step 4.

3.5 Clear pieces run as loops

EssenceWhile the unclear spots are being resolved, the pieces that are already clear and not blocked run as loops: the agent attempts, the check runs, pass → close the loop, fail → the feedback goes back to the agent.

CheckA loop only closes when its check is objective. A piece is loop-ready only if it has all five:

  1. a check — best a script; next a fixed checklist judged by a separate agent; last EJ's judgment;
  2. a limit on the number of attempts — a count, not a time limit;
  3. specific feedback — the script's real output, not just “failed”;
  4. an exit for when the limit is hit — a fresh node on a stronger tier if there is one; when that fails too, back to the unclear list or to EJ;
  5. a check the worker cannot edit, and that is known to be able to fail.

Attempts start on the cheapest tier that could plausibly do the piece; escalation is a fresh node, never a tier switch inside the running session. · Skill: step 5.

3.6 The rest is a graph

EssenceNodes are right-sized pieces; edges are “this piece needs that piece's result”; gates verify a result before anything that depends on it starts; a joining node is where branches meet. The design's edges decide who works next — not the role agents.

CheckA node that builds stops on three objective parts: (1) the acceptance criteria it covers pass; (2) what passed before still passes — the baseline; (3) its “must not change” holds. Anything else found goes to docs/blueprint/backlog.md, not into this run — “this is what lets a run end.”

The design and the runnable plan (plan.json) are compared: the plan may add and may not lose. · Skill: steps 6 and 8.

3.7 Sequential first; parallel is the last decision

EssenceDesign the whole flow as sequential, state-based steps: read the state file → do one step → write the state back. Only when the design is complete, look for tasks that are really independent.

CheckAll five must hold: neither needs the other's result; no shared files or resources; doing one would not change how the other is done; each has its own check; the time saved is worth the extra joining step. Parallel buys only clock time, and it costs predictability, debuggability and extra joins.

Never write “running in parallel” without saying which unit you mean — resident sessions, engine processes alive, or candidate approaches. · Skill: step 7.

3.8 Running a node: executors are tools, timers, pass-back, no polling

EssenceThe COO leads and holds the thinking; Codex, agy, qwen and role subagents are tools it calls — one small task per call, two timers per call, no polling, and one result file per call that a script validates.

WhyAgents are not yet stable — a call may stop half-way, return nothing, or return something malformed — and every exchange costs the COO a turn that re-reads its whole context. An unstable return is a failure of the executor, not of the work: the node is blocked and goes to EJ; there is no fallback.

The rules, in the method's order
  • Before any of it: know which binary will make the call, and what version it is.
  1. One small task per call.
  2. Two timers per call, both named in the node — and no single call runs past the ceiling of 8 hours.
  3. No polling.
  4. Pass-back contract.
  5. An unstable return is a failure of the executor, not of the work.
  6. A half-finished node must not leave a mess.
  7. Keep the COO's reading small.
  8. The stronger model gives the worker a template, an example and a standard.
  9. Research is written to files.
  10. Exploring existing code is its own role.
  11. Every run leaves a feedback record.
  12. Design decisions cite their evidence.

Skill: step 7, “When running, executors are tools”.

Every node carries five things

So that it can be run, checked and resumed without asking anyone (method 3.6).

Tools

What the agent uses, each proved working.

Context

Exactly what the agent is given, and what is withheld.

Contract

The intent, the stop condition, what comes back and in what shape, what may and must not change.

Evidence

The proof that comes back with the result, and the file it is saved in. A verifier reads the evidence, never the reasoning.

State

What the node reads from the state file, and what it writes back.

An edge is then more than “needs”: the earlier node's returns and evidence become the later node's context.

Three qualities every design must show

Predictability

The design's edges schedule; fixed bounds on attempts, pieces and concurrency; structured outputs; stop conditions and success criteria written before the run; a cost estimate before the run.

Debuggability

Every agent labelled; each step's input and output saved to a file; pieces small enough to rerun alone; resume from the failed point; feedback kept per attempt; state in one place.

Quality control

A check per piece; a verifier that does not see the worker's reasoning; proof the check can fail; a contradiction check at joins; a final “what is missing” pass; skipped or unrun checks reported.

State and memory

The state lives in a file. Each agent reads it, does one step, and writes the new state back; the next agent continues from there, and a broken run resumes from the last written state. One writer at a time.

The state file holds progress and results, never a worker's reasoning — that goes in the worker's own output file, so a verifier can be kept blind to it.

Files in the repo are the one memory every tool and every agent can read: use them for anything that must last. A subagent's final report is all that comes back; the rest is lost unless written to a file.

Words used above

prompt file — one written prompt for a small task; a workflow is prompts plus the wiring between them. six whys — six questions about the challenge, each feeding one design field; six is a ceiling, never a target. blueprint — what the product is for and what it must do, written down and accepted by EJ (eight sections, in docs/blueprint/). piece — consecutive steps that end in one deliverable. unclear spot — a step that cannot be written clearly, or whose check cannot be named: missing information, a decision, or an unknown. default-first — start from the category's default pattern; a bespoke design replaces it only on a written claim of ≥20% lower cost at equal coverage. tier — how strong (and how costly) a model is; start cheap, escalate in a fresh node. builds — changes the product's code, schema, UI or configuration. baseline — the product's test command and its output, written to the state file before the first node that builds starts. COO — the main Claude session: it leads, follows the graph, and calls the executors. pass-back — the one result file each call writes, with a fixed header that a script checks.
