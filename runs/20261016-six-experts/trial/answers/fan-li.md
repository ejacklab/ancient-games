# 范蠡 (Fan Li) — Pre-flight verification of question files and worker briefs

## Answer
A pre-flight script should verify only five deterministic structural conditions before handing a file to an AI engine: prerequisite path existence, engine capability compatibility, mandatory section and template placeholder completeness, explicit resource limits, and an executable verification standard; it must deliberately not verify semantic quality, task difficulty, or expected output correctness. If latency constraints require sub-50 ms execution, path verification must remain shallow rather than recursive.

## How I decided
1. **Prerequisite path existence (Order 1, highest value):** As in my #18 (`quoted`: 「審備則可以戰乎？」 — "If the preparations are examined, can we then fight?") and my #3 (`quoted`: 「時不至，不可彊生；事不究，不可彊成。」 — "When the time has not come, growth cannot be forced; when the matter has not run its course, completion cannot be forced."), launching an engine without ensuring its ground preparations are intact invites certain failure. The script looks for every file path cited in the Context and Task sections (or linked via Markdown) and checks `os.path.exists()` and read permissions, and checks that the designated output directory exists and is writable. This prevents launching an engine that immediately crashes or hallucinates because input files do not exist, saving both token budget and wall-clock time.
2. **Engine capability match (Order 2):** As in my #14 (`quoted`: 「四封之內，百姓之事，蠡不如種也。四封之外，敵國之制，立斷之事，種亦不如蠡也。」 — "Inside the four borders, the people's affairs: I am not as good as 種. Outside the four borders, dealing with enemy states, matters decided on the spot: 種 is not as good as I."), each executor must be matched strictly to what it can perform. The script inspects the brief for required actions against the engine matrix in `docs/EXECUTOR_KINDS.md`: if the brief requires shell commands or web fetches, it fails if the assigned engine is headless `agy` (which cannot run shell or fetch tools); if the brief demands workspace edits, it fails if the engine runs in a read-only sandbox. This prevents silent tool denial failures where engines exit cleanly without performing the required work.
3. **Template integrity and unexpanded placeholders (Order 3):** As in my #5 (`quoted`: 「夫謀之廊廟，失之中原，其可乎？」 — "To plan it in the temple hall and lose it on the central plain — can that be right?" and 「唯謀不遷。」 — "only the plan does not move."), a plan settled in council must not be corrupted before it reaches the field. The script verifies that mandatory template headings from `docs/workflow-templates/node-brief.md` (`## Task`, `## Context`, `## Template`, `## Standard`, `## Limits`, `## Write the result to`) or question headings are present, and scans for unexpanded placeholder patterns such as `<path>`, `<node id>`, or `{question}`. This prevents workers from guessing missing specifications or executing incomplete prompt skeletons.
4. **Bounded limits and stop counters (Order 4):** As in my #10 (`quoted`: 「無過天極，究數而止。」 — "they did not pass Heaven's limit, and stopped when the count was exhausted."), operations must have bounded ceilings before they begin. The script inspects the brief or CLI invocation to ensure an explicit outer timeout (in seconds), max turns/tool calls, and attempt numbers are specified. This prevents runaway processes from hanging indefinitely or exhausting hourly rate-limit windows.
5. **Objective machine-checkable standard (Order 5):** As in my #1 (`quoted`: 「夫人事必將與天地相參，然後乃可以成功。」 — "Human affairs must be joined with Heaven and Earth as a three; only then can success be achieved.") and my reading, execution succeeds only when the standard of completion is aligned beforehand. The script verifies that the `## Standard` section contains a non-empty, executable check command, script path, or deterministic regex rather than vague aspirational prose. This prevents unresolvable disputes between worker and verifier during evaluation loops.
6. **Deliberately exclude semantic judgment and early planning:** As in my #7 (`quoted`: 「彊索者不祥。」 — "one who seeks by force is unlucky." and 「王無蚤圖。」 — "Do not plan early.") and my #13 (`quoted`: 「兵者，凶器也；爭者，事之末也。」 — "weapons are ill-omened instruments; contention is the last of affairs."), the pre-flight check must deliberately NOT verify whether the instructions are wise, creative, or logically sufficient, nor attempt to predict output validity. Evaluating semantic quality without an LLM call is brittle, and adding an LLM judge introduces contention, latency, and false rejections before the worker even begins.
7. *Proposed change to the pattern:* The existing pattern records timestamped progress lines for small pieces during execution. The pattern should be improved to require the pre-flight check itself to append a timestamped verification line (`- <ISO time> · <node id> · preflight · <pass|fail> · <note>`) to the progress file prior to engine launch (my reading, improving upon my #18). If pre-flight fails, execution stops before spawning the engine, recording the exact structural defect in the visible audit trail without expending an engine attempt.

## What I need to know
- What is the maximum acceptable latency overhead per pre-flight check (e.g., <20 ms vs <500 ms)? If under 20 ms, path existence checks must check only top-level declared paths without opening files; if up to 500 ms is permitted, full regex scans for placeholders and schema validations across all referenced files are viable.
- Will pre-flight checks execute concurrently during multi-agent fan-out or sequentially? If concurrently, progress reporting must avoid locking shared log files; if sequentially, pre-flight can safely write inline status entries.

## Costs and risks
- False rejections on intentionally novel or freeform briefs (my #18, my #7): Rigid regex requirements for standard headers will fail informal or experimental prompts unless an explicit bypass flag is supported.
- Accumulation of dispatch latency in rapid iteration loops (my #4: 「得時無怠，時不再來，天予不取，反為之災。」 — "Having got the time, do not slacken; the time does not come again; what Heaven gives and you do not take turns into disaster."): Checking multiple disk paths and parsing Markdown before every call slows down rapid multi-step sequences where dispatch speed is critical.
- Maintenance burden of capability matrices (my #14): Hardcoding engine limits into pre-flight rules creates risk of rejecting valid briefs whenever an underlying engine or harness plugin is upgraded with new tools.

## How we would know I was right
Run the pre-flight script across all historical briefs in `runs/` and prompt fixtures in `tests/fixtures/operator_prompts_r1–r3.jsonl`. We would know the check succeeded if:
1. It catches 100% of sabotaged test briefs containing missing file paths, headless capability mismatches, or unexpanded `<...>` placeholders with zero false negatives.
2. It yields zero false rejections on historically successful production runs.
3. In live harness runs, engine startup failures caused by missing input files or tool refusal exits drop to zero, while pre-flight check execution adds less than 50 ms per engine call.
