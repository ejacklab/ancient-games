# Spec questions and evaluator scope

Author: P2 Codex. These are implementation readings, not changes to the requirements or spec.

| Question | Narrow reading used |
|---|---|
| What makes a relative case-file path relative? | External case `root` and `project` paths are relative to the evaluator's working directory, following the example's `root: "."`. The bundled fixture case file uses package-relative paths so the two invocation forms in the brief both work. `--cases` itself is relative to the working directory. |
| How does `equals` work with `[]` or recursive `children`? | A simple path compares its single selected value. A path using `[]` or `children` compares the complete selected list, in traversal order. An absent simple path is missing, not JSON `null`; an empty wildcard selection is `[]`. `children` visits descendants in source/depth-first order, never the current step. |
| What happens for `tests --file` without `--per-function`? | The tool may give an empty JSON answer with an explanatory limit; it must not return a per-function report. The fixture does not prescribe the explanation's wording. The spec defines no positive per-function JSON shape, so the evaluator does not invent one. |
| What are evaluator exit codes? | 0 means a report completed without NOT MET cases; NOT CHECKED is allowed. 1 means NOT MET cases. 2 means invalid evaluator input or an evaluator/environment failure. |
| Where is the R1 marker path for external cases? | The case format has no marker field. Runtime marker checks use only the known bundled `marker/EXECUTED.marker`, after every invocation (including all eight command-table forms). An external R1 case alone is NOT CHECKED for the runtime part. The evaluator removes only its own marker. |
| Does `unshare -rn` detect connection attempts? | It isolates network access; it does not trace syscalls. Filesystem changes fail the snapshot check; a nonzero tool exit is an R1 observation, not evidence of an R3 violation. A connection failure caught inside a successful tool cannot be detected from stdout. Such attempts and the broader privacy/training promise remain explicitly NOT CHECKED in `uncheckedParts`. No syscall tracer dependency is introduced. |
| Does isolation establish all of R3? | No. R3's MET line describes the spec-assigned isolation and before/after filesystem observation only. Snapshots hash regular files and retain mode, timestamps and symlink targets under `--root` and cwd; links are not followed. Files outside those trees, transient changes restored between snapshots, and transmissions by other processes are not observed. A missing/denied `unshare` makes R3 NOT CHECKED, even if snapshots are unchanged. |
| How are combined tool/agent Fails-if lines reported? | Line statuses describe the evaluator's tool checks. The JSON `displayStatus` and Markdown verdict show `MET (tool part)` with the unchecked part beside them; `uncheckedParts` also records A2 candidate choice/naming, A3 asking the user, and A5 whether the user asked. These belong to P6; a MET tool line does not assert that the agent part passed. |
| What is `Link.from` for a top-level call? | No module-node spelling is prescribed. The marker map's canned answer uses a Node with `kind: "other"` at the top-level statement, and marks runtime callees unresolved/outside-repo. Cases do not require that node's name or forbid alternative valid enclosing-node representations. |
| Can a fixture check A6 or L2? | No. No A6 claim is made without external cases for the three real opencode modules. L2 is P5's independent comparison. Both remain NOT CHECKED in the bundled suite. |
| How does an external case certify A6? | The spec supplies no module-certification field or A1 linkage field. An A6 case is therefore NOT CHECKED unless the three module-map commands and A1 case checks on those same commands are present; module location is identified by the three specified path suffixes. |

| Does the repair check default text output and no `--tests` without changing the spec format? | Fixture cases add optional `format`, per-case `tests`, and `expect.textIncludes` fields. Existing case files still default to JSON and suite-level test patterns. The text fixture checks evidence substrings, without prescribing a rendering format. |
| How are R1/R3 faults kept separate from other requirements? | R1 uses marker absence and exit 0 only, regardless of stdout. R3 uses isolation and observed writes only. Other cases use answer expectations and source/contract checks. Raw changes are retained in `observedChanges`; the deliberate R1 marker and its parent's directory timestamp change are excluded from R3's `changedFiles`, so that one known R1 observation does not create an R3 verdict. Other writes still fail R3. |
| How should a real tool identify a held-out test when its declared ambient `test` identifier is renamed? | The repair brief asks for every fixture-defined identifier to be renamed, including ambient declarations; the spec defines tests using `test(...)` and `it(...)`. The generator follows the brief and renames the ambient declaration and its uses. The evaluator can validate the supplied test title, callback body and evidence call in that body, but recognition of renamed test APIs by the builder is not specified. This remains open for the spec owner; no exception to renaming or new builder rule is silently imposed. |

Requirements check: **who decides**, **one thing**, **unit**, **can it fail**, **weak words**, **level**, **basis**, and **links** pass for the concrete evaluator contract when read as the author's accepted spec and fixture checks. The unresolved interface details above affect **who decides** or **can it fail**; the brief explicitly assigns their recording and the narrowest reading to this evaluator. No numeric threshold, acceptance criterion, or new dependency is added.
