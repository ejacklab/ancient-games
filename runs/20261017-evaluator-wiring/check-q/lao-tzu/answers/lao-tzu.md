# 老子 (Laozi) — is the requirements evaluator ready to be the judge of every build?

## Answer

Not as *every* build — and the two things stopping it are small and named: it reads only VISION and REQUIREMENTS, never a use case, while the rule EJ wrote today names use cases (`docs/HARNESS_REQUIREMENTS.md:45-46`), and its parser reads one product's spec grammar, which none of this repo's current requirement files uses (my reading, below). Inside those two borders the instrument holds its own shape well: a FAIL needs a confirmed faithful probe, and a crash, a timeout, an error or a bad restore can only land on UNKNOWN.

## How I decided

1. **My #1 — "Take away, and take away again."** The words give a repeated step and an end point, 損之又損，以至於無為。無為而無不為。 I start by subtracting, so: does the evaluator need a third reader to serve R12.2, or does it need to say out loud what it did not judge? **My reading: subtract the third reader.** EV-R1.1 and EV-R1.2 read `<spec>/REQUIREMENTS.md` and `<spec>/VISION.md` and nothing else (`snapshot/docs/evaluator/REQUIREMENTS.md:29-34`); the workflow passes exactly those two files and always passes a `--vision`, so a product with no VISION.md blocks at `e1-spec` (`snapshot/.claude/workflows/evaluate-requirements.js:97`, `snapshot/tools/evaluator/spec_parse.py:231-236,264`). A use case therefore cannot become a failure today. Adding a `USE_CASES.md` reader is 為者敗之 (my #4): a new grammar, a new parser rule, a new brief, on a spec EJ has already accepted. Instead the verdict's coverage manifest should carry one row per accepted use case, reading **"no case serves U3"** — and that row is the owner's to judge, not the tool's. 損之又損, 以至於無為: with the gap named, nothing is left undone; with a third reader added, the accepted EV-R1 is undone.

2. **My #8 — "Know that you do not know."** 知不知上，不知知病。夫唯病病，是以不病。 I asked the question the brief names — can a crash or a timeout read as anything but UNKNOWN — and read the code rather than trusting the claim. **It cannot, and this is the strongest part of the instrument** (my reading, with lines):
   - a non-zero exit, a null result or `done: false` stops the run and writes no verdict at all (`snapshot/docs/evaluator/DATA.md:230-238`; `snapshot/.claude/workflows/evaluate-requirements.js:48-70`); a model step that had work and wrote no file exits 1 (`DATA.md:255-258`);
   - a pytest timeout marks the run `timeout` and a missing report marks it `no-report`, and verdict.py refuses to call such a run healthy (`snapshot/tools/evaluator/probe_matrix.py:124-125,139`; `verdict.py:134-140`);
   - a probe that ended in a JUnit error is listed in `errors` and cannot be proof (`verdict.py:138-139`; `probe_matrix.py:146-149`);
   - a copy not restored, or changed by the product run, forces UNKNOWN on every executable case (`verdict.py:147-149`, R1-F4);
   - MEETS needs at least one in-scope id and every one PASS; an empty manifest is refused at the door, not judged (`verdict.py:229,233-237`; `spec_parse.py:266-268`; `DATA.md:277-280`).
   - Evidence that the FAIL side holds: K1d's two FAILs both reproduce and both are real, and K1e turned one of them into a PASS once the product was fixed (`snapshot/runs/20261013-calibration/report.md:79-85`). That is a judge that found a defect and then verified the fix — the whole point of the instrument.
   - **The one crack, my reading, not run:** `probe_matrix.py:153` returns `Run(results or {key: "fail" for key in plan}, OK, errors)` — a JUnit file that parses but holds **no testcase** (everything deselected, a filter that matches nothing) becomes *every probe red, status `ok`, no errors*. `runs` is written only when some run was unhealthy (`probe_matrix.py:256-259`), so for a single-probe case that red is indistinguishable from a healthy kill and reads as proof (`verdict.py:134-142`). The backlog already names this hole for F5(c) (`snapshot/docs/evaluator/BACKLOG.md:21-22`); this is the code path that keeps it open. `知不知上`: the tool is right to name what it does not know; here it does not know, and says so in the backlog, but one path still lets it say yes.

3. **My #1 again — the PASS side is where the subtraction has not been done.** EV-P1.1 gives PASS when every case has a probe green on the product and red on that case's mutant (`REQUIREMENTS.md:111-115`). That is the vision's own definition of proof (`VISION.md:31-33`), and the evaluator satisfies it in form. In substance the pair is unchecked: the probe is written by one model from the requirement's sentence, the mutant by another model that never sees the probe, and **only a probe that is red on the product is checked for faithfulness** — EV-C4.1's confirm step exists on the FAIL path alone (`REQUIREMENTS.md:84-88`; `verdict.py:112-122`; `DATA.md:244-245`). Nothing checks that a green probe and a red mutant between them say what the requirement sentence says. The measurement is already on record: on six seeded faults the evaluator caught five, and the sixth was **masked by an over-specified probe** — the probe over-asserted, so the fault never turned it red (`snapshot/runs/20261013-calibration/report.md:28`; `snapshot/state.md:73`). The mutants brief warns the model not to break "everything" (`snapshot/docs/evaluator/briefs/mutants.md:28`), and Dave's F5(c) guards only the global case (`DATA.md:286-291`); nothing guards the ordinary one. **A wrong PASS is the dangerous direction here**: R12.2 makes the evaluator's word the only failure a person must act on, so a PASS it should not have given accepts a broken build with nobody reading. My #16 — 知人者智，自知者明。勝人者有力，自勝者強 — puts it plainly: the tool is currently strongest on the half it admits is hard (proving a FAIL) and unchecked on the half it calls proof.

4. **My #2 — "Know what is enough; know to stop."** 知足不辱，知止不殆，可以長久。禍莫大於不知足。 The cost is measured and it is per build: K1b 24 min and 774k subagent tokens, K1d 18 min blocked plus a resumed leg to ~1.24M over 36 agents (`snapshot/state.md:69,71,83`). The tool does not record its own tokens — `cost.json` writes `"tokens": "not reported", "models": "requested, not verified"` (`snapshot/tools/evaluator/model_io.py:400-405`; `BACKLOG.md:27-28`) — so **no cost limit can be enforced, only a wall clock observed** (EV-P3's open item 4 says measure first, `REQUIREMENTS.md:130-135`). 知足不辱: with the cost unreadable, "every build" is a decision made without knowing what it spends. This run has one hour and three rounds (`runs/20261017-evaluator-wiring/state.md:3-4`); one evaluation is a fifth of it. So: run it on the build the owner names, once, not on every build. That is not a compromise on the instrument, it is my #18 — 且君子得其時則駕，不得其時則蓬累而行。 (`attributed`): ride out when the time comes.

5. **My #19 — take the rear.** 人皆取先，己獨取後 (`attributed`); 以深爲根，以約爲紀 (`attributed`). The evaluator reports; the owner and the guard decide. The hand-off has four exact requirements, all checkable:
   - **A blocked run is a failure, not silence.** R12.1: an evaluator reports fail — never pass — when the evaluator itself errors or times out, and "Exit 0 is not success" (`docs/HARNESS_REQUIREMENTS.md:42-43`). The workflow returns `{status: "blocked"}` and writes no `verdict.json` (`DATA.md:230-238`), so the wiring must log it with `--found-by evaluator`. Otherwise a Codex usage limit or a refused path costs nothing and shows nothing — the same shape as K1d blocking silently for18 minutes (`state.md:82`).
   - **`--found-by` must be passed every time.** `recordFailureFromArgs` defaults `found_by` to `"cli"` (`guard/src/journal.ts:222`), and `JUDGES` is exactly `new Set(["evaluator", "owner"])` (`guard/src/insight.ts:361-367`). A record without the flag is evidence and never opens an insight.
   - **One record per FAIL case, not per report.** The guard requires `check`, `input`, `expected`, `actual`, `reason`, `evidence`, and the evidence path must exist (`guard/src/journal.ts:117-130`); `verdict.json` supplies the reason and the repro (`verdict.py:104,121-122`), and the requirement sentence comes from `requirements.json`. Each record then costs six whys (R12.3, `docs/HARNESS_REQUIREMENTS.md:53-63`) — which is why item 3 above matters: on the K1 run, 28 FAILs of which 0 reproduced (`report.md:26`) would have been 28 insights.
   - **The engine field cannot be filled truthfully** (`BACKLOG.md:27-28`), and UNKNOWN is one state where the harness needs five: memory-check needed pass, fail, needs a reviewer, not applicable, could not run, and its smoke run was 0 fail / 3 pass / 3 needs a reviewer / 72 not applicable (`runs/20261017-memory-check/report.md:23`). The evaluator's UNKNOWN carries at least four owner-facing reasons — "needs EJ", "no probe" / "no mutant" / "unproven…", "judging void: plant missed", and `out_of_scope` for ids the spec marks open (`verdict.py:92,111,126,140,144,146,213-214`). Collapse them and72 "not applicable" reads as one undifferentiated blob. *Proposed change to the pattern:* a judge reports the coverage it did **not** judge beside the verdict it did — the manifest (`verdict.py:231`) is already that half, and it is the half the guard's insight never sees.

6. **My #6 — act before the disorder, and treat it as difficult.** 為之於未有，治之於未亂。是以聖人猶難之，故終無難矣。 R12.1 already asks for a cheap check before the full check (`docs/HARNESS_REQUIREMENTS.md:36-38`). For this evaluator the cheap check is three lines of script: does the spec parse to a non-empty manifest, do the probes collect, does the product archive exist at the named commit. Each of those fails in under a second; each of them, missed, costs the 20 minutes before it is discovered.

7. **My #2 for the blocker for "every build" — my reading, not run.** `spec_parse.py:26-28` reads a group heading `**G1 — title**`, an id bullet `- **G1.1**`, and a `**Fails if**` bullet. `docs/index-md/REQUIREMENTS.md:21,28` has all three. `docs/HARNESS_REQUIREMENTS.md:42` (`**R12.2 Failure log (MUST).**`), `.claude/skills/requirement-check/references/use-cases-and-requirements.md:25` (`**R13.5 Who writes a requirement.**` with a `Fails if:` paragraph at :38) and `memory_check/REQUIREMENTS.md:9-21` (`**F1 (MUST) The locations.**`, `Fails if:` inline) have none of the three, so their manifest is empty and `e1-spec` exits 2 — a loud block, which is the right direction, but it means **no build in this repo can be judged today** until one grammar is chosen. One of the two must move: the parser widens (a change to EV-R1.1 and DATA rules 1–3, so EJ says yes) or the specs are written in the evaluator's grammar. A wrong known answer in this parser has already cost twice (`snapshot/state.md:56,59`).

## Costs and risks

- **Five items, most important first.** (1) Name the use cases the evaluator does not read — one coverage row per accepted use case, judged by the owner. *Serves R12.2; touches EV-R1.1.* (2) One grammar for spec files. *Serves EV-R1.1 and EV-R1.3 — without it every build here blocks at step 1.* (3) Extend faithfulness from the FAIL path to the PASS path: have the confirm step check the green probes of PASS cases, so a probe or mutant that does not match the requirement's sentence gives UNKNOWN, not PASS. *Serves EV-P1.1 and the vision's "never PASS without proof"; costs a second confirm wave, roughly the K1c/K2 confirm share of 385k tokens.* (4) The hand-off: blocked run = failure, `--found-by evaluator` on every record, one record per FAIL case, and the five owner-facing states split out of UNKNOWN. *Serves R12.1, R12.2 and this run's C2; costs a small adapter and a decision on the blocked case.* (5) Do not run it on every build until the cost is recorded. *Serves EV-P3.1 and open item 4.*
- **My #1's price, said plainly:** every item above takes something away — a third reader not added, a per-build sweep not started — and what is taken away is coverage the owner no longer gets. That is the trade and the owner should see it as one.
- **Item 3's risk:** a faithfulness check on the PASS path will turn some of today's PASSes into UNKNOWNs, which reach the owner as notes instead of as nothing. K1c's 24 PASS would likely shrink; that is a true number becoming a smaller one.
- **Item 4's risk:** the engine field of every record will read "requested, not verified" (`BACKLOG.md:27-28`). A guard field that cannot be filled truthfully is better empty and named than filled with a guess.
- **My #2's price:** "know when to stop" is the item that costs the most, because it decides how often the instrument is used, and every use is20 minutes and up to 1.2M tokens.
