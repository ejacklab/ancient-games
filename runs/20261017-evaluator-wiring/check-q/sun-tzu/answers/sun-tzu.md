# 孫子 (Sun Tzu) — Is the evaluator ready to judge every build?

## Answer

**No, not as the sole judge of every build; yes, as one independent check, after five changes.** It largely does what its own vision says — 17 of its 26 requirements are met, its 177 tests pass, and in the one real use it found two real defects and verified one fix. But two MUSTs are not met as written: `EV-C3.2` says every probe must fail on its mutant, while the code passes on one; `EV-R3.2` says it writes only inside `runs/<runId>/`, while the judge copy is written to `/tmp`. Its input also has no use cases, which `R12.2` names, and a run-level crash or timeout ends as `blocked`, not as a per-requirement UNKNOWN. **If "every build" means a sole gate on MEETS, not ready. If it means one evidence source whose FAILs feed the guard and whose UNKNOWNs go to EJ, ready after the five changes below.**

   **Direct answer — can it PASS without proof?** On the recorded-evidence path, no. A case with no evidence is UNKNOWN, never PASS (`verdict.py:83-146`; `test_evaluator_verdict.py:124`); an executable or static PASS needs a green product run, an applied mutant and a red probe on it (`verdict.py:123-144`); a judged PASS needs a found plant and quoted evidence (`verdict.py:93-104`); missing files become empty and cannot make a PASS (`verdict.py:23-36`). **But two "yeses" remain:** the proof can be *partial* by `EV-C3.2`'s own words — one red probe carries a case while another probe stays green on the mutant (`verdict.py:139-144`); and the proof can be a *shared misreading* — `E8` confirms only red probes, never a green probe's fidelity to the sentence (`model_io.py:141-178`; `briefs/confirm.md:5-7`), so a probe and its mutant can encode the same wrong reading and still PASS. The mechanical "green on product + red on a mutant" is enforced; "faithful to the sentence" is enforced only for FAILs.

   **Direct answer — can a crash or timeout read as anything but UNKNOWN?** A *probe* timeout reads as UNKNOWN, not PASS: `probe_matrix.py:124-125, 134-139` marks every probe red and records `timeout`/`no-report`, and `verdict.py:129-144` refuses the mutant as unhealthy; the tests cover both product and mutant timeouts (`tests/test_evaluator_r1_matrix_spec.py:242-280`). A *model or runner* crash or timeout is different: the workflow throws `blocked` and returns `{status: "blocked", step, reason}` with no verdict at all (`evaluate-requirements.js:50-70, 139-141`), and `verdict.py`'s input errors exit 2 (`verdict.py:280-290`). That is safe — it is not a PASS — but it is not one of the three result states; the wiring must map it explicitly.

2. **My #2 — make yourself unbeatable first; win, then seek battle.** *quoted*: 「昔之善戰者，先為不可勝，以待敵之可勝。」 and 「勝兵先勝而後求戰，敗兵先戰而後求勝。」 The evaluator's safety core is genuinely built: the empty-evidence test, the no-mutant test, the unproven test, the unconfirmed-red test and the restored-copy test all hold (`test_evaluator_verdict.py:124-205, 298`; `test_evaluator_probe_matrix.py:199-256`). But a judge is not unbeatable while its own accepted requirement and its data contract say opposite things about what a PASS proves. That is the first thing to settle, before any wiring.

3. **My #4 — know yourself and the other.** *quoted*: 「知彼知己，百戰不殆；不知彼而知己，一勝一負；不知彼不知己，每戰必殆。」 The evaluator knows REQUIREMENTS and VISION (`spec_parse.py:28-38, 167-196`), not use cases, not the owner's corrections, not the builder. `R12.2` defines a failure against "the product's vision, use cases and requirements" (`docs/HARNESS_REQUIREMENTS.md:45-48`). Its own vision is narrower — "does it meet all of its requirements?" for products whose requirements carry ids and **Fails if** lines (`VISION.md:12-20`). So the gap is a **scope mismatch, not a parser bug**: a build that breaks a use case but meets every requirement can still come back MEETS. The owner must widen the evaluator's contract or accept that use-case failures are logged by EJ, not by the evaluator.

4. **My #17 — probe it and read the signs.** *quoted*: 「故策之而知得失之計，作之而知動靜之理，形之而知死地之地，角之而知有餘不足之處。」 The signs from the one real use are mixed but readable: K1 produced 0 of 28 reproducible FAILs (`state.md:69`); K1b produced a false FAIL on C2-F2 because the probe needed the product's tests the blind workspace removes (`state.md:71`); K2 caught 5 of 6 seeded faults while the product's own tests caught 6 of 6 (`state.md:73`); K1d ran 24 PASS / 2 FAIL / 5 UNKNOWN and both FAILs reproduce (`state.md:83`); K1e turned B1-F2 from FAIL to PASS when the defect was fixed (`state.md:85`). The safety direction is right; the evidence base is thin: one product, no product with 2+ judged cases (`BACKLOG.md:40-42`), and the post-repair judge path has not run live. **What blocks the wiring, specifically:**
   - **Inputs:** no USE_CASES, no owner correction, no builder (`evaluate-requirements.js:13-18`); `R12.2` names all three.
   - **Cost:** about 0.8–1.2M subagent tokens, 18–24 minutes and 14–36 agent calls per evaluation (`state.md:69, 71, 83`; `workflow-design.md:208-211`); that is roughly the cost of the build itself, and Codex is a single point with no fallback (`EV-C6.2`; Codex limits hit twice, `state.md:50, 79`).
   - **Result states:** only PASS, FAIL, UNKNOWN, plus out-of-scope; a `human` case is always UNKNOWN "needs EJ" (`verdict.py:91-92`), so a spec with a human-only case can never MEET (`verdict.py:229`). There is no machine state for *needs a reviewer*, *not applicable*, or *could not run* — the five states the memory-check build needed (`runs/20261017-memory-check/report.md:23`).
   - **Output format:** `verdict.json` has `meets`, counts, cases, requirements, out-of-scope, manifest (`DATA.md:178-194`), but no product path, commit, builder, per-step engine/harness, run status or per-call cost. The run is not self-describing.
   - **FAIL → guard failure:** `guard fail` needs `--check --input --expected --actual --reason --evidence --found-by` (`guard/src/cli.ts:37`; `guard/src/journal.ts:200-232`), and every field must be non-empty (`journal.ts:113-133`). `verdict.json` gives the check id, reason and repro/quote, but not the input commit, expected sentence, actual probe output, engine or harness; an adapter must join `requirements.json`, `matrix.json` and `cost.json`, and the commit is missing. A false FAIL becomes a durable guard failure and forces an `R12.3` insight; K1b's C2-F2 is the precedent. UNKNOWN has no guard note record; a blocked run has no verdict to adapt. `JUDGES` will count only `found_by: evaluator` (`guard/src/insight.ts:361-368`), so the adapter must be explicit.

5. **My #12 — change the conditions, not the people.** *quoted*: 「故善戰者，求之於勢，不責於人，故能擇人而任勢。」 The five changes, most important first. Each names the requirement it serves and its price.
   1. **Settle the PASS proof rule.** Choose the literal `EV-C3.2` (every probe red on its mutant) or `DATA.md:164` (one red enough), and close the F5(c) single-probe hole (`BACKLOG.md:8-11, 21-22`). Serves `EV-C3.2`, `EV-P1.1` and the vision's "never PASS without proof" (`VISION.md:31-33`). **Price:** the literal rule loses 51 of 72 PASSes for 0 extra faults caught (`state.md:87`); the guarded rule keeps them but leaves the accepted requirement unmet. Either way the calibration must be rerun, and the meaning of PASS changes.
   2. **Make the run self-describing.** Record product path and commit (or the workspace manifest hash when the product is not a git repo), spec path, builder engine, per-step engine/model/effort, start/end, agents, tokens or "not reported", and a run status (`done`/`blocked`). Serves `EV-R3.1`, `EV-C5.1`, `EV-C6.1`, `EV-P3.1` and `R12.2`'s record. **Price:** touches `verdict.py`, the workflow, `DATA.md` and the 177 tests; a required commit argument can block non-git products, so use the manifest hash as the fallback.
   3. **Split the result states and map them to the guard.** PASS, FAIL, *needs a reviewer*, *not applicable*, *could not run*; a run-level `blocked`. Map FAIL → one guard failure per case with `--found-by evaluator`; needs-a-reviewer / not-applicable → an owner note (the `verdict.md` path); could-not-run / blocked → an `R12.1` failure or an owner note, never a pass. Serves `EV-P1.1/P1.2`, `EV-C6.2`, `R12.1` and `R12.2`. **Price:** a schema and adapter change; "not applicable" can become a loophole for a real failure, and the guard has no note record today.
   4. **Resolve the write boundary.** `EV-R3.2` and `VISION.md:40` say writes only inside `runs/<runId>/`; `model_io.py:240-247, 290-306` writes the judge copy to `/tmp/evaluator-judge-<runId>/`, and `probe_matrix.py:109-117` puts HOME/TMPDIR in a scratch temp folder. Amend the requirement/vision to allow a named, cleaned scratch area and record it, or move the judge copy inside and accept the F2 plant leak. Serves `EV-R3.2`, `EV-R2.1` and the evidence path of `R12.2`. **Price:** amending a MUST weakens the safety bound; moving inside reopens the plant leak; the current `/tmp` folder persists after the run.
   5. **Add use cases, or a trace, to the input.** Either read `USE_CASES.md` and give each use case its own cases and verdicts, or require every use case to trace to requirement ids and check the trace. The owner's corrections must land in the spec or a recorded note. Serves `R12.2` and `EV-R1`. **Price:** direct use-case verdicts add cases, probes, mutants and confirm calls and can double the 0.8–1.2M tokens; a trace is cheaper but weaker.

   **What can wait:** merging `build/evaluator` and building the guard adapter until changes 1–4 are settled; cost *optimization* (caching probes and mutants, cheaper tiers) until the budget is set; requirements that need the product's tests or `.git` will remain UNKNOWN and are a spec-narrowing decision (`BACKLOG.md:23-24`). **What cannot wait:** a per-run token and wall-time budget before "every build", and a second-product calibration with 2+ judged cases before any judged PASS is trusted.

6. **My #16 — orders clear first, then enforced.** *quoted*: 「約束不明，申令不熟，將之罪也；既已明而不如法者，吏士之罪也。」 The wiring needs one clear order: **FAIL** becomes a guard failure with a rerunnable repro; **UNKNOWN** becomes an owner note and never a failure; **blocked/could not run** becomes a distinct `R12.1` record or note; **not applicable** is a note, never a PASS. Without that map, the guard either receives nothing or receives a false failure. **Price:** every false FAIL becomes a durable guard failure and an insight; one record per case multiplies records, one per requirement loses case evidence; reruns will duplicate failures unless the adapter carries a runId + requirement/case key.

   **Proposed change to the pattern:** before five experts are asked "is X ready", the main agent should publish a one-page **judge contract + status table** — inputs, result states, evidence fields, cost, guard mapping, and one row per requirement with met/partial/not met and `file:line`. The experts then challenge a checkable claim instead of each re-deriving the same facts. It changes the "research and data" step from per-expert recall to one shared evidence table; it would have surfaced `EV-R3.2` and `EV-C3.2` before the experts started. Cost: about 20 minutes of the main agent's time, saved five times over.

7. **My #5 and my #6 — move only on advantage; mix harm into benefit.** *quoted*: 「合於利而動，不合於利而止。」 and 「是故智者之慮，必雜於利害」. The advantage is real: it found a spec drift the product's own tests passed (B1-F2), verified the fix (K1e), and catches 5 of 6 seeded faults. The harm is also real: a false PASS in a gate is the expensive failure; a false FAIL is now a durable guard record; the judged path is uncalibrated live; and one run costs as much as the build. So the recommendation is not "do not use it" and not "wire it everywhere": use it as **one independent check on acceptance builds**, with the five changes, and let the guard take only its confirmed FAILs.

8. **My #14 — choose the action by the ratio of forces.** *quoted*: 「故用兵之法，十則圍之，五則攻之，倍則分之，敵則能戰之，少則能守之，不若則能避之。」 At 0.8–1.2M tokens, 18–24 minutes and 14–36 agents per evaluation, "every build" is a ten-to-one siege of the build pipeline. Do not besiege every build. Run the full evaluator where the risk justifies it — acceptance and release builds, products with judged cases, products with recent spec drift — and use a cheaper check elsewhere until the cost falls. *quoted*: 「故兵貴勝，不貴久。」

## What I need to know

- **The proof rule:** literal `EV-C3.2` (every probe red on its mutant) or `DATA.md:164` (one red enough)? The answer changes the meaning of PASS and the cost of every run.
- **Use cases:** must the evaluator give a verdict per use case, or is a requirement-to-use-case trace enough? This changes the input contract and the number of probes.
- **The scope of "every build":** every acceptance/release build in this repo, or every agent build? What wall-time and token budget per build? This changes whether tiering is acceptable.
- **Blocked and UNKNOWN:** should a crash/timeout be a guard failure under `R12.1`, or an owner note? Should any UNKNOWN ever be a failure? This changes the adapter.
- **The write boundary:** may the judge copy live in a named, cleaned temp folder outside `runs/<runId>/`, or must `EV-R3.2` and `VISION.md:40` be read literally? This changes where the judge works and whether F2's blindness fix survives.
- **Commit identity:** if a product is not a git repository, is the workspace manifest hash an acceptable "named commit"? My default: yes, record the hash; ask only if that does not satisfy `R12.2`'s input.

## Costs and risks

- **The proof rule — my #2.** The literal rule loses 51 of 72 PASSes for 0 extra faults (`state.md:87`); the guarded rule keeps them but leaves `EV-C3.2` unmet. Either choice changes the calibration and may over- or under-block builds.
- **The self-describing record — my #12.** A schema and argument change touches `verdict.py`, the workflow, `DATA.md` and the 177 tests; a required commit can block non-git products. Without it, every guard record's `input`, `engine` and `harness` are `none` or reconstructed, which is not the record `R12.2` asks for.
- **The result states — my #16.** "Not applicable" can become a way to avoid a verdict; a wrong N/A is a false pass. The guard has no note record today, so the owner-note half of `C2` needs a design. A blocked run must not be silent.
- **The write boundary — my #2 and my #4.** Amending `EV-R3.2` weakens a MUST; moving the judge copy inside `runs/<runId>/` reopens the plant leak F2; a named temp area still writes outside the run folder and must be cleaned and recorded. The current `/tmp` folder persists.
- **Use cases and cost — my #4 and my #14.** More cases mean more probes, mutants and confirm calls on top of 0.8–1.2M tokens and 20+ minutes; Codex is a single point with no fallback (`EV-C6.2`), so a usage limit blocks the gate. Tiering saves cost but risks missing a fault in a low-risk build.
- **Wiring FAIL to guard — my #5 and my #16.** A false FAIL becomes a durable guard failure and forces an `R12.3` insight; K1b's C2-F2 is the precedent. One record per case multiplies records; one per requirement loses case evidence; reruns duplicate unless keyed.
- **The judged path — my #17.** One product, no product with 2+ judged cases, and no live post-repair judge run (`BACKLOG.md:40-42`; `state.md:83`). The plant-retry unit tests are not a live proof; a false PASS on a prose requirement is the expensive failure.

## How we would know I was right

- **The seeded-fault pilot.** On a second product with one seeded fault per requirement group and at least two judged cases: every seeded fault becomes a guard failure `found_by: evaluator` with a repro that reruns red; no seeded fault is PASS; the judged plant is found; the named requirement is right (K2 was 5/6 — the bar is 6/6, or a miss that lands on UNKNOWN, never PASS).
- **The forced-failure test.** Set a one-second matrix timeout and kill a runner mid-step: the affected cases are UNKNOWN/could-not-run; the workflow returns blocked; the adapter logs no product failure and no pass; the owner note names the step; a rerun creates no duplicate guard failure.
- **The state test.** A spec with a human-only case and an open requirement: both appear as owner notes, not failures; `meets` is false; no guard failure. If EJ wants N/A to be pass-like, that policy shows up here and can be decided.
- **The hard test — a matched misreading.** Give the evaluator a case whose probe and mutant both encode a wrong reading of the requirement sentence. The current design PASSes it. If EJ wants that caught, the design needs a green-probe confirmation or an independently written mutant; if not, this is the accepted limit of "proof". This is the test that tells whether "never PASS without proof" is true in `R12.2`'s sense or only in the vision's mechanical sense.
- **The cost measure.** Median and worst-case tokens and wall time per run against the budget, and the catch rate next to the product's own tests (K2: 5/6 vs 6/6). The sign I was right: at least one independent spec drift the tests miss (B1-F2) is caught, at a cost EJ accepts.

**not ready because** the evaluator's own contract is split on what a PASS proves — `EV-C3.2` says every probe must fail on its mutant, `verdict.py` passes on one — and on where it may write — `EV-R3.2` and `VISION.md:40` say only inside `runs/<runId>/`, while the judge copy goes to `/tmp` — and its input has no use cases, which `R12.2` names.
**It is close on mechanics: 17 of 26 EV ids met, 177 tests pass, two real defects found and one fix verified, so this is a contract-and-evidence problem, not a rewrite.**
**Ready after the five changes above, a per-run token and time budget, and a second-product calibration with 2+ judged cases; until then, one independent check on acceptance builds — not the sole judge of every build.**
