# 范蠡 (Fan Li) — readiness of the requirements evaluator as judge

## Answer
The requirements evaluator is not ready to be the judge of every build today: while its core safety invariants hold (it does not report PASS without proof, never reports FAIL without a repro, and crashes or timeouts never read as PASS), it does not yet read use cases as required by R12.2, costs 0.8–1.2M tokens and 20+ minutes per evaluation, lacks a bridge to `guard fail`, and lumps distinct operational states into UNKNOWN. It becomes ready after adding `USE_CASES.md` parsing, bridging `verdict.json` to the guard CLI, separating operational states, and scoping runs to milestone gates rather than every small build.

## How I decided

1. **Examine the preparations of the evaluator (my #18).**
   I ask whether the preparations have been examined before committing to battle: `「審備則可以戰乎？」王曰：「巧。」` (國語·吳語, `quoted`).
   The preparations on branch `build/evaluator` show that the core mechanism works (*ran*, 177 tests pass at `runs/20261017-evaluator-wiring/nodes/evaluator-tests.txt:1-2`):
   - **Spec parsing (`EV-R1.1`, `EV-R1.2`, `EV-R1.3`):** It extracts requirement IDs and failure cases from `REQUIREMENTS.md` and vision lines from `VISION.md` (`snapshot/tools/evaluator/spec_parse.py:1-200`). Untestable requirements without a **Fails if** line become UNKNOWN (`untestable: no Fails if`), never PASS (`snapshot/runs/20261013-calibration/report.md:29`, test K3). Requirements marked open become `out_of_scope` and receive no verdict (`snapshot/tools/evaluator/verdict.py:213-214`).
   - **Blind workspace (`EV-R2.1`, `EV-R2.2`):** Excludes product tests, run folders, and git history (`snapshot/tools/evaluator/workspace.py:1-120`). In calibration test K4, 70 test paths were excluded and a planted marker was never read (`snapshot/runs/20261013-calibration/report.md:30`).
   - **Probes, mutants, and independent proof (`EV-C2`, `EV-C3`):** Probes are written by Claude and mutants by Codex (`snapshot/docs/evaluator/REQUIREMENTS.md:97-107`). Probes must fail on their mutant to be proven (`snapshot/tools/evaluator/verdict.py:124-144`). In live calibration run K1e, fixing the real defect turned case B1-F2 from FAIL to PASS (`snapshot/runs/20261013-calibration/report.md:84-86`).
   - **Failure confirmation (`EV-C4.1`, `EV-C4.2`):** A probe that fails on the real product must be confirmed faithful to the spec sentence by a fresh model, or it becomes UNKNOWN (`snapshot/tools/evaluator/verdict.py:118-122`).
   - **Judged cases with plant checking (`EV-C5.1`, `EV-C5.2`):** If the judge misses the planted defect, the judging is voided and all judged cases become UNKNOWN (`snapshot/tools/evaluator/verdict.py:95-96`).
   - **Automated verdict computation (`EV-P1.1`, `EV-P1.2`, `EV-P1.3`):** Verdicts are computed by script from table-driven rules, never by a model (`snapshot/tools/evaluator/verdict.py:229-238`).
   - **Reports (`EV-P2.1`, `EV-P2.2`):** Produces machine-readable `verdict.json` and formatted `verdict.md` (`snapshot/tools/evaluator/verdict.py:281-284`).

2. **Can it ever report PASS without proof, or read a crash or timeout as anything but UNKNOWN? (my #18, my reading).**
   - **PASS without proof:** In code, `_decide_case` enforces that an executable or static case receives PASS only when all probes pass on the product copy, the mutant is applied, the mutant run is healthy, at least one probe fails on that mutant, and the product copy hash is restored and unchanged (`snapshot/tools/evaluator/verdict.py:123-150`). If proof is missing, it returns UNKNOWN. Two narrow caveats remain on the backlog: Backlog O8 (`snapshot/docs/evaluator/BACKLOG.md:8-11`), where `verdict.py:141-142` awards PASS if *at least one* probe fails on the mutant whereas `EV-C3.2` literally says a probe staying green is unproven; and Backlog F5(c) (`snapshot/docs/evaluator/BACKLOG.md:21-22`, `snapshot/tools/evaluator/verdict.py:134`), where Dave's guarded rule does not evaluate a single-probe mutant run with no `runs` status key.
   - **Crashes and timeouts:** A timeout or failure during any workflow step immediately blocks execution (`snapshot/docs/evaluator/DATA.md:230-234`, `snapshot/.claude/workflows/evaluate-requirements.js`). If a mutant run times out or errors, `mutant_run.get("status")` is not `"ok"`, forcing `row["reason"] = "unproven: the mutant run was not healthy"` and leaving the case UNKNOWN (`snapshot/tools/evaluator/verdict.py:137-140`). Missing or malformed input JSON files count as empty, leaving cases as UNKNOWN (`snapshot/tools/evaluator/verdict.py:27-35, 184-185`). Furthermore, a probe crashing on the product cannot create a false FAIL because `confirm-check` voids any probe lacking recorded failure output (`snapshot/docs/evaluator/DATA.md:253-254`). Thus, a crash or timeout cannot read as PASS or FAIL; it reads only as UNKNOWN or BLOCKED.

3. **What blocks using it as the judge of every build? (my #1, my #3).**
   Heaven's time and human affairs must both arrive: `「夫聖人隨時以行，是謂守時。天時不作，弗為人客；人事不起，弗為之始。」` / `「人事至矣，天應未也，王姑待之。」` (國語·越語下, `quoted`). When the time has not come, growth cannot be forced: `「時不至，不可彊生；事不究，不可彊成。自若以處，以度天下，待其來者而正之，因時之所宜而定之。同男女之功，除民之害，以避天殃。田野開闢，府倉實，民眾殷。無曠其眾，以為亂梯。時將有反，事將有閒，必有以知天地之恆制，乃可以有天下之成利。事無閒，時無反，則撫民保教以須之。」` (國語·越語下, `quoted`).
   Four obstacles block immediate adoption as the universal judge:
   - **Inputs:** R12.2 states that a failure is what the evaluator judges wrong against the product's vision, use cases, and requirements (`runs/20261017-evaluator-wiring/check-q/fan-li/briefs/fan-li.md:16-17`). The evaluator currently parses only `REQUIREMENTS.md` and `VISION.md` (`snapshot/docs/evaluator/REQUIREMENTS.md:28-39`, `snapshot/tools/evaluator/spec_parse.py:1-200`). It has no mechanism to read `USE_CASES.md`.
   - **Cost and runtime:** In live calibration runs K1, K1b, and K1d, each evaluation required 20–24 minutes of wall time and consumed 0.8M–1.24M subagent tokens across 14–36 agent calls (`snapshot/state.md:69, 71, 83`; `snapshot/runs/20261013-calibration/report.md:76-83`). Running this on every build would exhaust token quotas, trigger engine rate limits (which halted Codex twice during calibration, `snapshot/state.md:50, 79`), and destroy the rapid cadence of small, timestamped steps.
   - **Result states:** The evaluator returns only three states: PASS, FAIL, UNKNOWN (`snapshot/docs/evaluator/VISION.md:13-14`, `snapshot/tools/evaluator/verdict.py:218-220`). Building `memory-check` demonstrated that five operational states are necessary: `pass`, `fail`, `needs a reviewer`, `not applicable`, `could not run` (`runs/20261017-memory-check/report.md:23-24`). Currently, human-judged cases, excluded product test/git checks (such as C2 and V6), setup timeouts, and unproven probes are all collapsed into UNKNOWN, leaving automated build harnesses unable to distinguish between untestable environments and missing proofs.
   - **Output format and guard integration:** The evaluator outputs `verdict.json` (`snapshot/tools/evaluator/verdict.py:178-185`). Nothing currently pipes confirmed FAIL rows into `guard fail --found-by evaluator` (`.claude/skills/workflow-design/guard/src/cli.ts:37, 190-194`). Because `evaluator` is an active entry in `JUDGES` (`.claude/skills/workflow-design/guard/src/insight.ts:364`), any recorded failure becomes an open failure (`insight.ts:370-373`) that blocks the harness until an insight file is written. Without verified repro commands and robust false-positive elimination, an automatic hook would trigger constant pipeline blocks.

4. **What must change first, and what can wait? (my #7, my #10).**
   Do not force what is incomplete: `「未可也。蠡聞之，上帝不考，時反是守，彊索者不祥。得時不成，反受其殃。失德滅名，流走死亡。有奪，有予，有不予，王無蚤圖。夫吳，君王之吳也，王若蚤圖之，其事又將未可知也。」` (國語·越語下, `quoted`). Stop when the measure is reached: `「臣聞古之善用兵者，贏縮以為常，四時以為紀，無過天極，究數而止。天道皇皇，日月以為常，明者以為法，微者則是行。陽至而陰，陰至而陽；日困而還，月盈而匡。古之善用兵者，因天地之常，與之俱行。」` (國語·越語下, `quoted`).
   Five prioritized items:
   1. **Parse `USE_CASES.md` (Must change first):** Extend `spec_parse.py` to extract use case flows into verifiable cases, satisfying R12.2 and `EV-R1`.
   2. **Bridge `verdict.json` to `guard fail` (Must change second):** Write a bridge script that reads `verdict.json`, extracts confirmed FAIL rows with their repro commands, and executes `guard fail --found-by evaluator --check <id> --reason <reason> --evidence <verdict.json>`.
   3. **Expand result states from 3 to 5 (Must change third):** Update `verdict.py` and schema to split UNKNOWN into `needs a reviewer` (for human/ambiguous classifications), `not applicable` / `could not run` (for excluded tests/git checks), and `unproven` (probes failing mutant checks).
   4. **Scope evaluation runs to milestone gates or changed requirement deltas (Must change fourth):** Change the wiring so the full 30-step evaluator runs at acceptance gates, releases, or against modified requirement groups, rather than running a 1.2M-token matrix on every build commit.
   5. **OS-level sandbox isolation and literal O8 probe coverage (Can wait):** Strict container isolation for blindness (`snapshot/docs/evaluator/BACKLOG.md:15-20`, F2/F9) and reconciling literal all-probe mutant coverage (O8, `snapshot/docs/evaluator/BACKLOG.md:8-11`) can wait; calibration proved the current in-tree boundaries and Dave's guarded rules function safely in practice.

5. **Proposed change to the pattern: Divide internal build checks from independent evaluation (my #14).**
   *Proposed change to the pattern:* Acknowledge who is better at what: `「四封之內，百姓之事，蠡不如種也。四封之外，敵國之制，立斷之事，種亦不如蠡也。」` (國語·越語下, `quoted`). Do not burden routine, internal development loops with the full weight of the independent evaluator. Let the builder's fast unit and acceptance tests govern ordinary builds inside the workspace (where speed and fast feedback rule), and reserve the evaluator as the independent external judge triggered at designated milestone reviews, release readiness checks, or when the owner requests evaluation.

## Costs and risks
- **Cost of premature wiring (my #7):** Forcing a 20-minute, 1.2M-token evaluator run on every single build commit will exhaust token quotas and stall iterative work (`彊索者不祥... 反受其殃`).
- **Risk of pipeline paralysis from unrefined FAILs (my #18):** Because `evaluator` is an active judge in `guard`, any FAIL immediately creates an open failure requiring an insight file (`.claude/skills/workflow-design/guard/src/insight.ts:364-373`). Wiring it before repro generation and failure confirmation are fully hardened risks blocking development on false alarms.
- **Risk of misinterpreting operational limits (my #3):** Without the 5 result states, legitimate builds that touch areas outside the blind workspace (like `.git` or product tests) will be blocked under the ambiguous label of UNKNOWN (`事不究，不可彊成`).

## How we would know I was right

- A prototype bridge that parses `USE_CASES.md`, emits the 5 distinct result states, and triggers `guard fail` only on confirmed milestone FAILs will successfully gate a release without impeding local development loops.
