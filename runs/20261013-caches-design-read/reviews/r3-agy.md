### Still disputed

1. **Discovery versus exhaustive routes in the Part 1 "none" rows (`CACHES.md:81–98`)**
   - **Positions**: Codex maintains this is *still open*, arguing that lines 94–95 assign "none" to structured headers and "why" questions without distinguishing initial discovery of an entry from authoritative reading or exhaustive verification. Claude, opencode, and agy hold this is *settled*, pointing out that lines 81–85 route free-text and semantic discovery to FTS5 and vector once their triggers fire, while explicitly reserving exact matches, completeness, absence, and metadata lookups to files ("Everything else is the files").
   - **Better supported**: The **settled** position (claude, agy, opencode). The routing rule at lines 81–85 clearly delegates candidate discovery to the caches once triggered. Line 95 begins from an already-identified entry ("the entry's **Why:**"), and line 94 is a schema search across frontmatter links. Codex's distinction between candidate discovery and reading is an unadopted design refinement rather than an unsettled conflict in the text.

2. **K3.2 rerun triggers for the full-text cache (`CACHES.md:413–414`)**
   - **Positions**: Claude, opencode, and agy hold that K3.2 erroneously assigns vector miss events to full-text, leaving full-text without an agent-side rerun trigger in a full-text-only installation; it must provide distinct rerun events for B1.1 (reading many hits) and B1.2 (misses). Codex rejects the finding, arguing that K3.1 specifies running the comparison on a built cache, so full-text exists and can record misses, and K3.2 does not have to duplicate B1.1's initial scheduling condition.
   - **Better supported**: The **position of claude, opencode, and agy**. In B1.2 (`:333–335`), a "miss" is defined as a question where `INDEX.md`, grep, and full-text all failed. In a project with only full-text built, an agent cannot experience a B1.2 vector miss. Full-text's value proposition is reading less than grep; when entries grow, it loses value if grep catches up or full-text yields too many hits. Re-evaluating full-text requires B1.1's reading-friction trigger.

3. **`INDEX.md` as the cache membership reference in "Rules for every cache" (`CACHES.md:152`)**
   - **Positions**: Claude, opencode, and agy hold that `:152` (*"the same set as `INDEX.md`"*) contradicts Core Requirement B4.1 (`:373–375`), which was amended to make entry headers the reference because `INDEX.md` is a generated derivative. Codex rejects the defect, arguing that specifying equality with a correctly generated index is compatible with B4.1 and does not instruct the builder to parse `INDEX.md`.
   - **Better supported**: The **position of claude, opencode, and agy**. B4.1 was explicitly modified to prevent a stale or corrupt `INDEX.md` from dictating cache contents. Having an implementation summary rule designate `INDEX.md` as the membership set invites implementers to parse `INDEX.md`, defeating B4.1's explicit safeguard.

4. **Treatment of historical journal misses against an active-only index in K3.1 / B1.2 (`CACHES.md:330, 411`)**
   - **Positions**: Codex and opencode hold that the relationship between historical journal notes and the active-only index is an *unresolved gap*: notes accumulate over time, but entries may become superseded or retired, leaving it unspecified whether misses targeting retired entries are filtered out or counted as search failures. Claude holds it is a narrow, easily closed gap (judge miss against target's active successor). Agy holds it is *already covered by existing rules*: Rd4.2 builds question sets fresh from currently existing entries when the comparison runs, and B1.2 defines misses over active entries, excluding retired targets.
   - **Better supported**: **Agy's and Claude's reading**. Rd4.2 explicitly mandates that question sets are constructed fresh from current entries at comparison time (`:456–457`). Stale historical targets do not exist in the active set and cannot form part of a valid evaluation set under B4.1.

5. **Vector 5W1H How row citation of Model2Vec Option A (`CACHES.md:227`)**
   - **Positions**: Claude, opencode, and agy hold that citing Option A without qualification is misleading because Option A in `vector.claude.md:292–293` specifies incremental rebuilds by re-embedding changed files, violating B3.1's full-rebuild requirement. Codex rejects the finding, arguing that Option A is cited strictly for the static model/runtime choice, and B3.1's explicit prohibition on incremental updates prevents any misinterpretation.
   - **Better supported**: The **position of claude, opencode, and agy**. While B3.1 governs, citing an option whose source definition specifies an incremental update procedure creates unnecessary friction for implementers. A brief parenthetical clarifying that rebuilds are full closes any ambiguity.

6. **Disclosing CONTESTED status of M17 and M6 (`CACHES.md:97, 438`)**
   - **Positions**: Opencode, claude, and agy hold that M17 at line 97 should disclose its CONTESTED status, as B2 already does for M6 at line 352–353. Codex rejects the finding, arguing that citations in an owner-accepted design do not require repeating source recommendation vote tallies at every mention.
   - **Better supported**: The **position of codex on principle, but opencode/claude/agy for consistency**. While citations do not need full committee minutes, M17 represents an unresolved disagreement about session-start files; noting it briefly aligns line 97 with line 352.
