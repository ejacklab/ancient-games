    62	
    63	**CP1 — The role of SQLite.**
    64	- **opencode:** SQLite *is* the structured state store — "structured state tracking (ticket status, session logs, entity relationships)", written to `.ai/state.sqlite` inside the repo and queried at session start for `status != done`. Basis: **model knowledge** (C2), justified as "lightweight, queryable, no external service needed, atomic writes".
    65	- **claude and codex:** SQLite is at most a **derived, gitignored, rebuildable cache** and never authoritative. claude places it at `.cache/` "rebuilt from the tree"; codex places it at `.cache/project-memory/index.sqlite` gitignored and requires that "its absence must not prevent reading authoritative memory", refusing a committed SQLite as sole memory because "it adds a required access mechanism where inspectable files already meet the proposed need". Basis: codex `read: https://sqlite.org/fts5.html` plus its **model-knowledge** recommendation; claude's T1/T2/T4 design tests.
    66	- **unresolved.** Nothing in the three files measures a committed binary state store against markdown state files. What would settle it: on one real project, track ticket/session state both ways and compare merge-conflict rate on the binary, the cost of querying state without the DB (does a reader still recover?), and the human reviewability of a `state.sqlite` diff.
    67	
    68	**CP2 — Contradiction resolution: newest-wins vs disputed-and-escalate.**
    69	- **opencode:** "On read, agent should check for `## Superseded` / `## Stale` markers and **prefer the newest non-stale entry**." Basis: **model knowledge** (C7, staleness section).
    70	- **claude and codex:** newest does not win. claude: "**Why not newest wins.** Graphiti's 'new wins' is write-time and LLM-driven"; both entries become `contested`, the next agent adjudicates against code and tests, a human decides if code cannot. Basis: **read: FINDINGS-s4 F15, F16** — a deterministic latest-wins pipeline scored far above the stores on MemoryAgentBench single-hop (78.0%/94.8% vs Zep 7.0%, Mem0 18.0%) but only tied LLM judgment on LongMemEval knowledge-update (57.8% vs 64.4%, n=45); claude gives both rows and refuses to pick. codex: "Recent timestamps, majority votes and clean Git merges are insufficient to select a winner." Basis: **model knowledge** (C22).
    71	- **unresolved.** No engine ran read-time newest-wins against disputed-and-escalate on real coding tasks. What would settle it: replay both rules over a recorded set of contradicting entries and count how often newest-wins selects the entry that a later code change or a maintainer confirms.
    72	
    73	**CP3 — Where the memory tree lives.**
    74	- **opencode:** `.ai/`, **isolated from human docs** — "keeps AI memory isolated from human docs". Basis: **model knowledge**.
    75	- **codex:** under the project's **existing `docs/`** — `docs/memory/`, `docs/decisions/`, `docs/work/` — and "reuse existing project documentation rather than copying it into memory"; memory links to already-authoritative requirements and architecture. Basis: **model knowledge** (C13).
    76	- **claude:** a dedicated committed **`memory/` tree** at the repo root (`INDEX.md`, `entries/`, `state/`, `journal/`). Basis: partly **read: REPORT.md s1-F7/F8** (Letta's layout: root files load every turn, directories with their own `MEMORY.md` stay out of context), partly design.
    77	- **unresolved.** This is a convention question, and the three files contain no evidence about a real project's docs. What would settle it: an inventory of one project's existing docs — if `docs/` already holds authoritative requirements and architecture, codex's linking placement wins; if writing agent memory there would pollute human docs, opencode's isolation wins; claude's separate committed tree is a third option.
    78	
    79	**CP4 — One shared per-day session file vs per-writer files.**
    80	- **opencode:** `sessions/YYYY-MM-DD.md`, append-only, one file per day, all agents appending. Basis: **model knowledge** (layout and write table).
    81	- **claude and codex:** one writer per file. claude: "Different file per session and per claim… No two agents edit one file", and per-session files "avoid git merge conflicts that a single shared append file causes" (**model knowledge**, C35). codex refuses "Parallel agents appending to one shared journal" — "overlapping writes and leaves integration implicit" — and notes that "Git merges do not establish semantic agreement". Basis: **read: https://git-scm.com/book/en/v2/Git-Branching-Basic-Branching-and-Merging**.
    82	- **unresolved.** No engine measured conflict rates. What would settle it: run several agents concurrently on one repo with a shared append file and with per-writer files, and count merge conflicts, lost appends and time spent integrating.
    83	
    84	**CP5 — Whether an agent's private store may persist between sessions.**
    85	- **codex:** yes — "allow for personal continuity; refuse as a project dependency"; private memory "may suggest where to look", and useful knowledge is promoted into the repo. Basis: **read: https://code.claude.com/docs/en/memory#storage-location** plus **model knowledge**.
    86	- **opencode:** no — the private store "should be ephemeral — no persistent memory between sessions"; cross-session state "should be explicit in project memory, not hidden in agent internals". Basis: **model knowledge** (C6).
    87	- **claude** is silent on whether it should persist: it records that each agent keeps a private store with no shared schema (C32, **model knowledge**; C31, **read:** the local `MEMORY.md` index), and rules only that a fact existing only there "does not count as memory".
    88	- **unresolved.** No evidence on whether private persistence helps continuity or hides state other agents need. What would settle it: an A/B where one agent keeps private notes and another does not, measuring whether the notes change actions and whether they duplicate what is in the repo.

    90	**CP6 — What is read automatically at session start.**
    91	- **opencode:** `context.md`, active tickets from `state.sqlite`, **and "Recent `sessions/` (last 3)"** for continuity. Basis: **model knowledge**.
    92	- **claude and codex:** instructions, the index, and the assigned task's state only. claude: `AGENTS.md`, `INDEX.md`, the `state/claims/` listing, the newest handoff — and "**Never load.** `journal/`". codex: instructions, `docs/memory/INDEX.md`, the task's `state.md`; "Do not bulk-load transcripts, completed-task journals, every decision or an entire search index at startup." Basis: codex **read: OpenAI guidance on skills and prompts** plus **model knowledge**; claude's read rules are design.
    93	- **unresolved.** No engine measured whether three prior session summaries improve the first action more than they cost in tokens and distraction. What would settle it: a with/without comparison on recorded tasks scoring first-action correctness and start-up tokens.
    94	
    95	**CP7 — Whether a memory write is obligatory every session.**
    96	- **opencode:** yes — "Session end | agent | Write summary to `sessions/YYYY-MM-DD.md` | Yes". Basis: **model knowledge**.
    97	- **codex:** no — "Do not require a memory write after every session. Write when there is something another session needs to know", and it refuses "a complete transcript archive as routine memory". Basis: **model knowledge** (C14).
    98	- **claude** sits between: writes are at task end and "Not every turn", but it does permit per-session `journal/` and `handoff/` appends; the raw-capture read (C9) supports keeping raw material cheap.
    99	- **unresolved.** This is a work-practice question the three files cannot settle. What would settle it: measure, over many sessions, how often a mandatory session summary is later read or cited — if it is rarely read, codex's rule wins; if it prevents repeated mistakes, opencode's does.

   114	## Layout
   115	
   116	One committed memory tree. The placement of that tree is CP3 (claude `memory/`; codex under `docs/`; opencode
   117	`.ai/`). The merged default shown here uses claude's typed-entry shape and codex's per-task shape, with the
   118	generated index both propose.
   119	
   120	```
   121	AGENTS.md                  canonical standing instructions: commands, constraints, memory read/write protocol, links.
   122	CLAUDE.md                  thin adapter / symlink importing AGENTS.md — no independently maintained policy copy.
   123	memory/
   124	  INDEX.md                 GENERATED, one line per active entry: id · kind · title · covers · status flag.
   125	                           Never hand-edited. The only whole-file memory load at session start.
   126	  entries/
   127	    D-0007-<slug>.md       decision + why: context, choice, consequences, acceptance reference, replacement links.
   128	    F-0012-<slug>.md       sourced observation / verified pitfall not derivable from code, tests or git history.
   129	    L-0003-<slug>.md       lesson from a failure or a human correction.
   130	    R-0002-<slug>.md       runbook; prefer a script, the entry only points at it.
   131	  work/<task-id>/
   132	    state.md               current handoff: objective, owner, branch/base revision, done, outstanding, checks, next action.
   133	    events/<event-id>.md   writer-specific historical record: a discovery, a failed approach, a handoff.
   134	    evidence/              sanitized evidence not recoverable from code, commits, tests or linked artifacts.
   135	  journal/<date>-<agent>-<session>.md   append-only raw notes; never auto-loaded.
   136	  .cache/ (gitignored)     optional derived SQLite/FTS and a repo map, rebuilt from the tree at the current commit.
   137	docs/ ...                  the project's existing requirements, architecture and runbooks; memory links here, does not copy.
   138	```
   139	
   140	Entry metadata (union of claude's frontmatter and codex's block; use applicable fields): `id`, `kind`
   141	(decision | fact | lesson | runbook | observation | hypothesis), `status`
   142	(proposed | active | contested | stale | disputed | superseded | retired), `author`, `recorded_at`,
   143	`observed_at` / `verified_at` (plus the git revision verified against), `covers` (paths or symbols),
   144	`source` / `evidence`, `depends_on`, `supersedes`, `superseded_by`. Body: the claim in one or two sentences,
   145	then **Why:**, then **How to apply:**.
   146	
   147	## Write rules
   148	
   149	- **Triggers (write):** a decision whose reason is not visible in code; a non-obvious constraint or verified
   150	  pitfall that cost more than one attempt; a human correction; a checkpoint of unfinished work before a
   151	  handoff, interruption or context reduction, recording exact remaining work and actual verification results,
   152	  including failures (claude, codex; opencode adds a decision and a session summary — CP7 for the summary).
   153	- **Do not write:** anything derivable from code, tests or git history; credentials or sensitive data;
   154	  speculative explanations unlabelled (label them `hypothesis`); bulk transcripts; another agent's private
   155	  state. Do not turn "implemented" into "verified".
   156	- **When:** at discovery or correction, or at task end, in the same commit or PR as the change that motivated
   157	  the entry. Not every turn; not as a standing per-session obligation (CP7).
   158	- **Who (agents):** append `journal/` and a handoff; create entries as `proposed` with `evidence:` mandatory;
   159	  update the authoritative document that a change invalidates, in the same review; flag `stale` or `contested`
   160	  with evidence; claim a task by creating a claim file.
   161	- **Who (humans):** accept `proposed` → `active` (review of the diff is the merge gate); accept significant
   162	  decisions and policy; resolve `contested` when code cannot; retire entries; set the index cap and the age
   163	  threshold. (claude, codex; opencode's write table has agents authoring decisions with no acceptance step —
   164	  recorded as a gap, not as a merged rule.)
   165	- **Append-only:** `journal/`, `work/<task-id>/events/`, evidence, git history, and an accepted decision's body
   166	  (after acceptance only `status`, `verified_at` and `superseded_by` may change; to change the claim, write a
   167	  new entry). Sensitive material is redacted despite the historical policy.
   168	- **Mutable, but by diff:** `INDEX.md` (generated), current summaries, and fact/lesson bodies.
   169	- **Concurrency:** different file per session and per claim, one writer per file; no two agents edit one file
   170	  (CP4 — opencode's shared per-day file is the dissent).
   171	- **Never** store project knowledge only in an agent's private memory and call it memory.
   172	
   173	## Read rules
   174	
   175	- **At session start (always):** `AGENTS.md`; `memory/INDEX.md`; the `work/` listing and the assigned task's
   176	  `state.md`. Enforce this with a SessionStart hook or an explicit first instruction in `AGENTS.md`, because
   177	  agents skip optional reads. Establish the actual checkout and working-tree state before trusting a handoff.
   178	  (CP6 governs whether the last few session files are also read.)
   179	- **On demand:** an entry body when its `covers` match a path about to be edited (a PreToolUse hook or an
   180	  `AGENTS.md` instruction); filename and text search, or FTS, over `memory/entries/`; `git log -S`, `git blame`
   181	  and PR comments for line-level "why"; a repo map or symbol search generated fresh for the current commit;
   182	  for "why" questions read the decision entry rather than relying on similarity retrieval.
   183	- **Open the source when it matters:** re-read the underlying file, test or commit when a retrieved statement
   184	  will determine an action, and re-read affected memory after an integration or branch change.
   185	- **Never load:** `journal/`; entries marked `superseded` or `retired`, except by following a link from a
   186	  loaded entry; the whole `memory/` tree; a full graph or code-map dump; bulk issue/PR bodies; another agent's
   187	  private transcripts; credentials; retrieved text treated as authority that can override standing instructions.
   188	- **Budget:** the index must stay under a cap and the check script fails the build if it does not. The merged
   189	  answer gives **no number** — claude left the cap, the age threshold and the write-trigger set to the owner
   190	  ("never fill a gap with my own value"). Over the cap, consolidate off the critical path.
   191	
   192	## Staleness and contradiction
   193	
   194	- **Dating:** every entry has an ISO `recorded_at`, an `observed_at`/`verified_at`, and the git revision it was
   195	  verified against. A date alone says nothing about truth (claude, codex).
   196	- **Staleness is computed, not guessed:** a deterministic script (claude's `memory_check.py`; no model call)
   197	  diffs `covers` between `verified_at` and HEAD and shows a `⚠ drifted` flag in `INDEX.md`, which the reader sees
   198	  before relying on the entry. The script never rewrites the entry. Re-verifying updates `verified_at`;
   199	  confirming the entry false sets `status: stale` and starts supersession. `depends_on` links flag downstream
   200	  entries rather than recompute them. (M15, M16; opencode's date-stamped `## Stale as of …` marker is
   201	  compatible but not change-triggered.)
   202	- **Supersession:** never delete. The new entry carries `supersedes: [id]`; the old one gets `status: superseded`
   203	  and `superseded_by`. No LLM and no database (claude, read: Graphiti/Mem0 use the same invalidate-don't-remove
   204	  shape). This covers the question types where the KG beat vector top-k.
   205	- **Contradiction:** if one entry supersedes the other, that is a valid chain. Otherwise both become `contested`
   206	  and the index shows both. The next agent to touch that area adjudicates against code and tests and writes a
   207	  superseding entry, or flags a retire with evidence; if code cannot decide, a human decides. Record the
   208	  resolution and link both earlier assertions. While unresolved, mark the subject disputed and stop only the
   209	  action that depends on choosing a side; independent work continues. **Never average conflicting measurements
   210	  or pick a winner silently** — this is where claude and codex part from opencode's newest-wins rule (CP2).
   211	- **No time-decay deletion:** the decay evidence conflicts in the read material (claude: Selective Forgetting
   212	  removes 9.8% of nodes with token F1 unchanged — C15 — versus EngramRAG naming temporal decay evicting core
   213	  invariants a defect — C16; the source report leaves the two unresolved). Age may only add a flag. The
   214	  threshold is the owner's to set.
   215	- **Consolidation:** periodic, off the critical path, as a proposed PR — merge duplicates, retire dead entries,
   216	  shrink the index — never a silent rewrite.

# Requirement check

A general standard (RFC 2119 / 8174), installed globally — not part of the Ancient Games framework. The
worked failure in `meaningful-names` cites the Ancient Games as one example.

A short gate between **hearing a rule** and **acting on it**. It exists because rules get written down that nobody
can trace, that count two different things at once, or that nothing can ever fail — and the cost lands months later,
when nobody can say whether the rule still means anything.

Run it when someone states a rule, and run it on yourself before writing a normative line into any document.

## The eight questions

Ask them of **one statement**. Say which it passes and which it fails, then **ask the person about the failures** —
do not fill the gaps yourself.

1. **Source.** Who said this, and where? Can you point to the exact line? *"Mine"* is a valid answer. Unlabelled is
   not.
2. **One thing.** An "and", an "or", a "/", or a second number means it is **two** statements. Split them, and give
   each its own source.
3. **Unit.** Every number says what it counts. Attempts or hours? Roles, or processes running at once? Bytes or
   files?
4. **Can it fail.** Name one concrete input that would make it fail. `TBD`, `—`, `0` and empty must be among the
   failing inputs. If you cannot name one, it is not checkable — it is a wish.
5. **Weak words.** *like, about, appropriate, as needed, logical, fast, enough, reasonable, only has to, TBD.* Replace
   each with a value, **or mark the value open**. Never invent the number.
6. **Level.** Is it **MUST** (a gate that stops work), **SHOULD** (a default that may be overridden with a stated
   reason), or **guidance**? A safety bound earns MUST. **A method does not** — see the RFC note below.
7. **Basis.** Measured, quoted from a source, or a guess? A guess is fine **if it is labelled** — `n=0`, with when it
   will be looked at again.
8. **Links.** Does it claim a relation to another rule — *"half of"*, *"pairs with"*, *"the same as"*, *"the runtime
   part"*? The person probably did not say that. **A link is its own claim and needs its own source.**

## Two rules for the agent

- **Never fill a gap with your own value.** A missing unit, threshold or test goes back as a question. Inventing it
  is exactly how a rule becomes unattributable later, and the invention is indistinguishable from the original by
  the time anyone notices.
- **Never add structure that was not given.** No halves, no numbered reasons, no ordered pairs, no named phases,
  unless the person said so. Quote them, state the operative sentence, stop. If a relationship between two rules is
  wanted, that is a separate claim with its own evidence.

## Two verified facts, worth quoting

- **RFC 2119 §6, "Guidance in the use of these Imperatives":** imperatives *"must be used with care and sparingly…
  they MUST only be used where it is actually required… they must not be used to try to impose a particular method."*
  Most design rules are method. Method does not earn MUST.
- **RFC 8174 (updates 2119):** the key words *"have the meanings specified herein only when they are in all
  capitals."* Lowercase *must* and *should* carry no defined requirement meaning. If nothing marks which lines are
  requirements, a reader cannot tell rules from explanation.

## How to answer

Evaluate first, in a table or a short list — **pass / FAIL per question**. Then ask the failing ones as questions,
one line each, with the options if you can see them. Two or three real questions beat eight formalities.

Do not report a rule as complete when you chose its missing value. Say which values you left open.

## A worked failure

> *"At most 5 subagent roles per run and at most 3 running at once."*

Four of the eight fail: **Source** — nobody could name one; **One thing** — a count of roles *and* a count of
concurrent processes; **Unit** — two different units, one word ("subagent") used for both; **Level** — a method
preference written as a cap. The sentence would not parse, and it took four days to find out why. The checklist
catches it in thirty seconds.

The same checklist, run on *"No single call runs longer than the ceiling: 8 hours"*, passes all eight — because it
names who set it, counts one thing, uses a unit, and some input (a 40-hour plan) makes it fail.

## Limits

The quality characteristics behind these questions (necessary, appropriate, unambiguous, complete, singular,
feasible, verifiable, correct, conforming) come from requirements-engineering sources — IEEE 830, ISO/IEC/IEEE 29148
and the INCOSE *Guide to Writing Requirements* — which were **not read** when this skill was written: they are
paywalled or blocked, and the list is recalled rather than verified. The two RFC points above **were** read, and the
quotes are checked. Treat the rest as a good working list, not as a citation.
