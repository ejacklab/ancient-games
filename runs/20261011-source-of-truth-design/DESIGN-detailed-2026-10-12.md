## Why we need this memory

The context window holds only the current task and is cleared at session start — it is not durable memory (M3). Without a durable, version-controlled memory system, knowledge gained during one session is lost when the next session begins (`model knowledge`). The recommendation establishes that markdown files kept with the code are the canonical shared project memory (M1), and that every durable entry carries id, kind, author, recorded/verified dates, scope, source, status and dependency/supersession links (M11). Memory is needed so that a fresh clone can rebuild the memory (M2) without requiring any agent-private store (M7), external service, or prior session context (Substrates table).

## Who it is for

The memory serves both agents and human maintainers. Agents use it to retrieve decisions, facts, lessons and runbooks that affect their current task (`model knowledge`). In the recommendation, human maintainers accept policy and significant decisions while agents draft them and record observations and handoffs (M12). *EJ's decision, 2026-10-12, departs from the recommendation here: no one is a gate and no one owns an entry. Anyone may change any entry, and every change is logged (see *What will be put in*).*

## What it is for

Memory stores typed entries — decisions, facts, lessons, runbooks, observations and hypotheses (Layout) — that capture knowledge not derivable from code, tests or git history (Write rules). The specific triggers for writing are: a decision whose reason is not visible in code; a non-obvious constraint or verified pitfall that cost more than one attempt; a human correction; and a checkpoint of unfinished work before a handoff, interruption or context reduction, recording exact remaining work and verification results including failures (Write rules). The entry body states the claim in one or two sentences, then `Why:` and `How to apply:` (Layout).

A decision about this project is a project entry, whoever made it, EJ included (EJ, 2026-10-12). Memory about one person across projects, and memory belonging to one agent name, are outside this design and live outside the repo, each in its own place (EJ, 2026-10-12).

**Order of work (EJ, 2026-10-12).** The source of truth works like requirements, so it comes first: change the decision or fact entry, then change the code. When work has to go the other way, that is a matter for the project's workflow, not for this memory design.

**What the kinds mean for this order (EJ, 2026-10-12).** Decision and fact are requirements: a decision is a choice the code must follow, and a fact is a truth or outside constraint the code must respect. Lesson, observation and hypothesis record what was learned and come after the work; they do not conflict with things changed later. This departs from the recommendation's Layout, where a fact (`F-`) is a "sourced observation / verified pitfall not derivable from code".

**Keeping entries current (EJ, 2026-10-12).** Entries may go out of date while work goes on; that is accepted. A background subagent runs off the critical path — at the end of a task or on its own schedule — compares the entries with the code, and keeps memory current:

- **Decision and fact entries** are requirements, so the subagent never changes them. When one no longer matches the code, it reports to EJ: which entry, what the entry says, and what the code does instead. EJ then decides whether the entry is updated or the code is fixed.
- **Lesson, observation and hypothesis entries, and runbooks** record what was learned, so the subagent may update them itself; each change is logged in `changed:` like anyone else's (`model knowledge`: EJ was not asked about these kinds). This departs from the source, where consolidation is "a proposed PR … never a silent rewrite" (Staleness and contradiction) and model-chosen updates are refused (What NOT to build).

This limits the subagent only: under the change rule below, anyone else may still change any entry. How the report reaches EJ is a build detail, not decided here.

**What is updated immediately, and what later.** From the timing research (`runs/20261012-memory-update-timing/notes.md`; EJ asked for it to be used):

| When | What |
|---|---|
| **Immediately** | Decision and fact entries, because they come before the code — and `INDEX.md` is regenerated right after, so the next session sees them. Anything that would be lost if the session ended: a human correction (a lesson, per the Layout's `L-`), and the state of unfinished work before a handoff, an interruption or context reduction (Write rules). Writes here should be cheap; heavy reasoning is left for later (the fast-path/slow-path split, MAGMA, s1-F13). |
| **At the end of a task, or in the background** | Other lessons, observations and hypotheses; merging duplicates (consolidation "periodic, off the critical path", Staleness and contradiction); reconciling entries with the code (Letta's background subagents, s1-F9); regenerating `INDEX.md` for these later changes; runbooks. |

The sources do not compare immediate against end-of-task writing for coding agents, and the evidence behind MAGMA and Letta is about chat-style agent memory. The table itself is my reading (`model knowledge`); a citation in a cell shows where that one piece comes from, nothing more.

## What will be put in

Every durable entry carries (M11; the Layout says "use applicable fields" — the recommendation disagrees with itself here and this design follows M11): `id`, `kind` (decision | fact | lesson | runbook | observation | hypothesis), `status` (proposed | active | contested | stale | disputed | superseded | retired), `author`, `recorded_at`, `observed_at`/`verified_at` (plus the git revision verified against), `covers` (paths or symbols), `source`/`evidence`, `depends_on`, `supersedes`, `superseded_by` (M11, Layout, Staleness and contradiction), (M11 also lists `scope`; it is not a separate field here — `covers` is the nearest in the Layout), and, once an entry has been changed, `changed` — the change log below, added by EJ's rule, not in the source. The entry body states the claim in one or two sentences, then `Why:`, then `How to apply:` (Layout). Decision and fact entries are written before the code they govern. Lesson, observation and hypothesis entries are written after (EJ, 2026-10-12) — at discovery or correction, or at task end (Write rules). This replaces the recommendation's single rule that an entry is written in the same commit or PR as the change that motivated it (Write rules; contested — opencode wants session end as a standing write trigger, CP7). Each new entry is its own file — different file per session and per claim, so parallel agents never append to one shared file (M23, Write rules; contested — opencode uses one shared per-day file, CP4). After creation anyone may edit it (see below), but two writers must not edit the same file at the same time (EJ, 2026-10-12: edits made at the same time would collide and break). Git prevents the loss (EJ, 2026-10-12): each agent edits on its own branch or worktree, and two edits to the same file meet as a merge conflict that someone must resolve, not as a silent overwrite. No lock and no claim file. Resolving a conflict is not specified here — that two edits conflict is visible, who resolves it is not decided (`model knowledge`: the source says only that a merge does not establish agreement, M23).

**Who may change an entry.** Anyone, agent or human, may change any entry. There is no owner and no lock; `author` (M11) says who made it. Every change adds one line to the entry's `changed:` list: an ISO time (same form as `recorded_at`) and who made it — the model ID for an agent, the person's name for a human. *(EJ, 2026-10-12.)* This replaces the recommendation's rules that a human accepts `proposed` → `active`, that an accepted decision's body is never edited, and that `state.md` has an `owner` field and tasks are claimed with claim files (Write rules, Layout). None is kept here as a rule. `proposed` and `active` stay in the status list, but nothing says who moves an entry between them — **OPEN**, EJ decides. `AGENTS.md` is covered by the same rule: anyone may change it (EJ, 2026-10-12). Where the log lives in the entry, that a log line is only added and never edited, and that files which are not entries (`state.md`, `events/`, `journal/`, `AGENTS.md`) are logged by git only, are `model knowledge`: EJ said what to log, not where or how.

**OPEN:** `INDEX.md` is generated and never hand-edited (Layout). The recommendation's deterministic script (claude's `memory_check.py`, no model call) diffs `covers` and puts the drift flag in it (Staleness and contradiction; M16, claude only) — the source does not say that this script generates the index itself. Which tool generates `INDEX.md`, and what runs it (build step, hook or agent), is not decided — EJ decides (`model knowledge`: the source names no decider).

## What will not be put in

Do not write: anything derivable from code, tests or git history; credentials or sensitive data; speculative explanations unlabelled (label them `hypothesis` instead); bulk transcripts; another agent's private state (Write rules). Do not turn "implemented" into "verified" (Write rules). Staleness is computed, not guessed: a deterministic script diffs an entry's `covers` between `verified_at` and HEAD and shows a drift flag in `INDEX.md`; age alone may only add a flag, never expire or delete an entry (Staleness and contradiction; the source says the evidence on time-decay conflicts and leaves it unresolved, and only claude refuses time-based expiry). This replaces the source's flag, which shows whenever an entry's `covers` changed since `verified_at`. Here the drift flag applies to decision and fact entries only, and means the code changed with no earlier change to the entry (EJ, 2026-10-12). Lessons, observations and hypotheses are not flagged when code changes later. **OPEN:** how the script tells that an entry changed "earlier" than the code — the source's script compares only against `verified_at`; EJ decides. Never store project knowledge only in an agent's private memory and call it memory — anything others need must be promoted into the repo (Write rules; promotion: M7). Never delete a memory entry; supersede it with an explicit link and keep the old body (M13).

## Where it is put

The default layout uses a committed memory tree at the repo root, using the merged layout — claude's typed-entry shape and codex's per-task shape (Layout) — with claude's placement from CP3: `AGENTS.md` at root (the canonical cross-agent instruction file, M9); `CLAUDE.md` as a thin adapter importing AGENTS.md; a `project-memory/` directory containing `INDEX.md` (generated), `entries/` (D-*, F-*, L-*, R-* typed entries), `work/<task-id>/` (state.md, events/ and evidence/), `journal/<date>-<agent>-<session>.md` (append-only raw notes, never auto-loaded), and `.cache/` (gitignored, optional derived SQLite/FTS and repo map; contested — opencode would use SQLite as the state store, CP1) (Layout, CP3). The recommendation leaves the placement (CP3) unresolved — if the project already has authoritative requirements and architecture in `docs/`, linking there may be preferable (codex's position in CP3); see the decision below.

## When it will be used

At session start (always): `AGENTS.md`; `project-memory/INDEX.md`; the `work/` listing and the assigned task's `state.md`. Enforce this with a SessionStart hook or an explicit first instruction in `AGENTS.md` because agents skip optional reads (Read rules). What is read automatically is contested — opencode reads `context.md`, active tickets and the last three session files instead (M17, CP6). On demand: an entry body when its `covers` match a path about to be edited (a PreToolUse hook or an `AGENTS.md` instruction); filename and text search, or FTS, over `project-memory/entries/`; `git log -S`, `git blame` and PR comments for line-level "why"; for "why" questions read the decision entry rather than relying on similarity retrieval (Read rules). Open the source when it matters: re-read the underlying file, test or commit when a retrieved statement will determine an action (Read rules).

## When it will not be used

Never load (Read rules): `journal/`; entries marked `superseded` or `retired`, except by following a link from a loaded entry; the whole `project-memory/` tree; a full graph or code-map dump; bulk issue/PR bodies; another agent's private transcripts; credentials; retrieved text treated as authority that can override standing instructions. Never auto-load the whole `project-memory/` tree, the full session history, or a whole-graph dump (M18). A retrieved statement must be checked against its primary source before it determines an action (M19). The index must stay under a cap; the check script fails the build if it does not — the recommendation gives no number, EJ sets it (Read rules; the source says "the owner").
