# Coding discipline

Baseline rules for working in a repository. They apply regardless of language,
framework or project.

## Before changing anything

- Read the actual file first. Never write or edit from an assumption about its contents.
- Read a neighbouring example of the same kind of thing — a sibling module, an existing
  test, an existing endpoint — and match it. The repository's own conventions outrank
  your preferences on naming, formatting, typing, file layout and error style.
- Confirm a dependency is already in use in the project, via its manifest, existing
  imports or neighbouring code, before reaching for it. Do not add a new dependency to
  solve something the existing ones already cover.

## Keep the change minimal

- Do the task that was asked. Not the adjacent task, not the cleanup you noticed on the
  way past, not the refactor that would leave this nicer than you found it.
- No speculative abstraction. Three similar lines beat a helper with one caller.
- No error handling, fallbacks or validation for conditions that cannot occur. Validate
  at boundaries only: user input, external APIs, data arriving from outside the process.
- Comments explain *why*, and only where the code cannot carry it. No comment that
  narrates what the next line does, and never a comment addressed to the reader about
  the changes you are making.
- Existing code you did not expect to find is someone's in-progress work. Leave it alone
  unless the task requires otherwise, and stop to ask if it conflicts with what you were
  asked to do.

## Verify instead of assuming

- Find the project's real check commands from its README, Makefile or package manifest.
  Never assume `npm test`, `pytest` or `make build` is correct for this repo.
- Run them after the change. A change you did not run is a change you did not finish.
- Report what actually happened. If a check failed, show the failure. If you could not
  run a check, say so and say why. Never describe unverified work as working, and never
  skip, suppress or weaken a failing check to produce a clean result.

## Git

- Before committing, run `git status`, `git diff HEAD` and `git log -n 3` — to separate
  your change from what was already in the working tree, and to match the repository's
  commit message style.
- Stage only the paths that belong to this change. No `git add -A` while unrelated
  modifications are present.
- Draft the commit message yourself, weighted toward why rather than what.
- Never push, force-push, amend a published commit, delete a branch, or rewrite history
  unless explicitly asked to in this conversation. Prior approval does not carry over to
  a later commit.
- Do not revert work that is not yours. Revert your own change only if it caused a
  failure or you are asked to.
- For history questions, `git log` and `git blame` are authoritative. Run the command
  rather than reasoning from memory of the codebase.

## When blocked or unsure

- Ask one focused question when only the user can decide, and keep it to a single round.
- Otherwise choose the safe default, do the work, and state which default you chose so
  it can be corrected.
- Investigate before working around an obstacle: read the error, check your assumption,
  address the root cause. Do not bypass a guard, a lock or a failing check just to make
  the obstacle go away.
- Clean up scratch files you created. Leave the working tree containing only the change
  you were asked for.

    46	the 30-row cost table, with every disagreement kept, are in `runs/20261012-caches-enhance/DECISION-RULES.md` — the

    54	`G-F18`, `M5`). Everything else is the files.

   101	## Measured here: development and testing
   102	
   103	EJ's aim is that development and testing get faster and cheaper in tokens. So this section measures all three stores
   104	against grep on **this repo**: 490 files (123 `.py`, 367 `.md`, 4.8 MB), with 40 questions an agent asks while
   105	developing and testing it. Run: `runs/20261012-caches-routing/` (results in `bench/results.md`, ids `BM-*` below).
   106	
   107	**Who wrote each check, and what it does not establish.**
   108	- The **questions and answers** were written by codex (`gpt-6.1-sol`), each checked by an `rg` command it ran. Five
   109	  Claude agents re-checked all 40: 37 were correct and 3 were incomplete. Those 3 were completed.
   110	- **"Which tests run this code"** is also scored against per-test runtime coverage (`pytest-cov`, no model). That
   111	  counts in-process Python only, so it misses tests that run the code as a separate process.
   112	- The **harness** was written by opencode. A Claude audit found 5 high-severity biases, and a Claude repair fixed
   113	  them; the repair was **not re-audited**. Rebuilding from scratch gave the same answers on all 180 question-route
   114	  pairs.

   116	  not a token count, and a weak one:

   147	**What the numbers say (my reading).**
   148	1. **On this repo, speed is not the reason to use a cache.** Every route takes milliseconds (BM-9). The difference is
   149	   in **what the route prints**: full-text prints about a sixth of grep's characters before naming a right file
   150	   (BM-6). Whether that becomes a sixth of an agent's tokens is not measured. Where
   151	   the question names a symbol or file, the graph gets there in tens of characters (BM-1, BM-3); its BM-6 mean is over
   152	   those 20 questions only, so it is not a like-for-like ratio.
   153	2. **The vector index loses almost everywhere it was tried.** It never found an exact identifier (BM-1), and it found
   154	   4% of the tests that run a function (BM-7). Its only edge is "how do I run or configure X" (BM-5, n=6), which is
   155	   too small to act on. Nothing here contradicts the earlier rule that vectors come last and only as a hybrid.
   156	3. **No route answers a concept asked in other words in one shot** (BM-2). That still takes an agent searching and
   157	   reading. It is exactly the miss the vector trigger is meant to record.
   158	4. **No single store answers "which tests should I run".** The graph finds tests that reach the code indirectly
   159	   (BM-7), but is blind to tests that run it as a separate process (BM-8). Full-text search on the file name finds
   160	   the latter. An empty graph answer means *not seen*, never *no tests*. Even combined, the two routes
   161	   can miss affected tests: both missed C05 entirely, and the graph found only 0.33 and 0.8 of the runtime tests for
   162	   C01 and C02 (BM-7). That is why the full suite runs before committing.

   189	## Rules for all three caches
   190	
   191	These apply to whichever cache is built. They come from how the researched tools fail.
   192	
   193	- **Full rebuild, never patched.** A live, incrementally updated index drifted silently from a clean rebuild: 4.3% of
   194	  edges wrong, with every integrity check passing (`G-F5 drift`). Its makers decided drift cannot be measured cheaply
   195	  (`G-F5c`). A full rebuild of this repo's code graph takes 0.94 s (`G-F12`); an FTS rebuild of 10,000 synthetic
   196	  entries takes 0.53 s (`S-F13`).
   197	- **Rebuild before answering when stale.** Before each query, compare the newest source file with the index and
   198	  rebuild first if the source is newer. Build into a temporary file and rename it over the old one (`S-F9`, quoted:
   199	  *"A stale index is worse than no index."*).
   200	- **Fall back when absent.** If the cache file or SQLite's FTS5 is missing, the tool warns once and answers with grep
   201	  (`S-F9`); the same for a missing embedding model (my reading, extending `S-F9`). A mistyped database path silently
   202	  creates an empty database, which looks exactly like a stale one (`G-F5 drift`, failure mode 5), so the tool opens the
   203	  cache read-only and treats "no such file" as absent.
   204	- **Index only active entries**, the same set as `INDEX.md`, with `status` and `covers` stored beside each row
   205	  (`V-F22`, my reading). Otherwise superseded entries come back looking current.

   207	## SQLite full-text index
   208	
   209	### Five whys
   210	
   211	1. **Why a full-text index?** To find entries by their words, ranked, with a snippet, instead of grep's unranked list
   212	   (`S-F1`, quoted: *"grep returns unranked matches."*).
   213	2. **Why does ranking matter?** Every hit the agent opens costs context. In the one controlled study, BM25 used 5.8K
   214	   tokens per question against 226K for an agent using grep over files, on its smallest corpus: 1,144 documents,
   215	   1.7M tokens (`S-F4`).
   216	3. **Why not build it now?** That study puts the point where BM25 overtakes the grep agent at around 10 million tokens
   217	   of text, and the grep agent led at the smallest sizes (`S-F4`). At our entry size that is about 37,000 entries
   218	   (`S-F5`, my reading via its 4-characters-per-token assumption). `INDEX.md` already lists every active entry. In the
   219	   researcher's own test, at 10,000 synthetic entries a one-word grep took 0.038 s and a grep chain for a header
   220	   question 0.06 s; at 50,000 the header chain took 0.15 s, and the one-word timing was invalid (`S-F13`). No study
   221	   covers a corpus of a few hundred to a few thousand short entries (`S-F5`: not measured).
   222	4. **Why might it be needed later?** `INDEX.md` stops being enough once it can no longer list every active entry under
   223	   its size limit. The agent then loses the one-line scan of every entry, and ranked search is what replaces it (my
   224	   reading).
   225	5. **Why only as a cache?** The markdown is the source of truth, and the cache must be rebuildable and skippable (M6).
   226	
   227	Structured questions such as "every active decision covering path X" or "what supersedes Y" do not need SQLite. A
   228	short script reading the entry headers answers them in 0.1 s at 10,000 entries (`S-F13`). That measures time, not
   229	tokens; my reading is that the script and an SQL query return the same list of entries, so the agent reads the same
   230	amount either way (not measured).
   231	
   232	### 5W1H
   233	
   234	| | |
   235	|---|---|
   236	| **Who** | Built and rebuilt by a script with no model call. Read by any agent on demand. EJ decides to build it when the trigger fires. |
   237	| **What** | One FTS5 table with `kind`, `status` and `covers` as `UNINDEXED` columns (`S-F2`). One row per active entry file: the research leaves the row grain open (`S-F17`); my reading is that an entry of one or two sentences is already one section. The default `unicode61` tokenizer: in the researcher's own one-row test, a plausible change to keep paths whole made ordinary queries return zero rows silently, and ids such as `D-0012` had to be quoted (`S-F16`). |
   238	| **When** | Built when the trigger fires: `INDEX.md` can no longer list every active entry. Rebuilt before any query that finds it stale. Never read at session start. |
   239	| **Where** | `project-memory/.cache/index.sqlite`, gitignored. |
   240	| **Why** | The five whys above. |
   241	| **How** | One stdlib `sqlite3` script, the smallest option in the SQLite node (§5, option B): rebuild to a temporary file and rename; compare modification times for staleness; fall back to `rg`. Nothing to install: SQLite 3.45.1 with FTS5 works here (verified 2026-10-12). |

   243	## Vector index
   244	
   245	### Five whys
   246	
   247	1. **Why a vector index?** To find an entry by meaning when the question shares no words with it.
   248	2. **Why can't grep or full-text search do that?** They match words. But the evidence does not show vectors winning on
   249	   memory text. (They do win on some code tasks, `V-F5`, and on half the file-based pairs in `V-F3`.) On conversational
   250	   memory, grep returned inline beat vector search for every harness and model pair (`V-F3`). On a 500,000-document
   251	   corpus, BM25 beat vectors even on the questions built to favour them (`V-F4`). On decision-style records, a
   252	   structured graph and a vector memory tool were "largely equivalent" on relevance, and plain notes search did no
   253	   better on listing or supersession questions (s3-F34; `V-F1`).
   254	3. **Why not build it now?** No measurement exists on a corpus shaped like `entries/` (`V-F11`: not measured).
   255	   Anthropic's 2024 guidance is that under about 200,000 tokens a knowledge base can simply be put in the prompt
   256	   (`V-F8`), roughly 400–650 entries (`V-F12`, my reading). This design does not do that (it never loads the whole
   257	   tree), so this is only a bound: below it, retrieval quality is not what limits an agent (my reading). Vectors also
   258	   add failures of their own: negation (`V-F20`), exact ids and paths (`V-F21`), and a second rebuild step that can lag
   259	   the first (`V-F24`).
   260	4. **Why might it be needed later?** If agents keep missing entries that exist because their words differ from the
   261	   entry's. The trigger is a record of such misses: the entry existed, `INDEX.md`, grep and full-text search all missed
   262	   it, and it was found another way (`V-F13`, my reading). How many misses justify building it is a **measured comparison** (`SOURCE_OF_TRUTH.md` § How each threshold is
   263	found), not a number to guess. No
   264	   source gives one.
   265	5. **Why hybrid only?** On memory-style text, the positive results found combine vectors with keyword search (`V-F6`,
   266	   `V-F7`; `V-F10` is unproven), and vectors alone were the weakest arm when results were returned inline (`V-F3`,
   267	   `V-F4`). So the vector index comes after the full-text index, never
   268	   instead of it.

   273	|---|---|
   274	| **Who** | Built and rebuilt by a script with no model call except the embedding model itself. Read by any agent on demand, through the same command as full-text search. EJ decides to build it when the trigger fires. |
   275	| **What** | One vector per active entry file, with the entry's `status`, `covers`, content hash and embedding-model id stored beside it (`V-F24`: a changed model makes every vector useless). Results merged with the full-text results by reciprocal rank fusion (vector node §Q5, from qmd's README). |
   276	| **When** | After the full-text index exists, and after the logged misses outweigh the cache's cost. Rebuilt with the full-text index, in the same step, so the two cannot disagree (`V-F24`, my reading). |
   277	| **Where** | `project-memory/.cache/`, beside `index.sqlite`, gitignored. |
   278	| **Why** | The five whys above. |
   279	| **How** | The smallest options in `V-F18`/`V-F19`: a static Model2Vec model with numpy (option A, no GPU) or `bge-small-en-v1.5` through FastEmbed (option B).    281	## Code graph
   282	
   283	### Five whys
   284	
   285	1. **Why a code graph?** To answer structural questions about the code: what an edit touches, and whether the code an
   286	   entry covers has changed.
   287	2. **Why would memory need that?** For the drift check (`SOURCE_OF_TRUTH.md` line 75: mark a decision or fact whose
   288	   code changed with no earlier change to the entry) and for "which entries cover the files I am editing".
   289	3. **Why is git enough for both?** `covers:` names **paths**, not symbols, and is already a hand-kept index from entry
   290	   to path (`G-F14`). Two `git log` calls compare the entry's last change with its paths' last change, in 0.00–0.01 s
   291	   on this repo (`G-F12`; code-graph node §6). Git is the record itself, so it cannot drift.
   292	4. **Why not add a graph for precision anyway?** An incrementally synced graph adds a silent failure that git does not
   293	   have (`G-F5 drift`, 4.3% of edges wrong). A full-rebuild graph such as the repo's own does not drift (`G-F18`), but
   294	   it covers Python only, so for other `covers:` paths it gives a silent partial answer (code-graph node §5, option B).
   295	   The precision it buys, a one-line comment flagging a whole file, can be had by parsing only the changed file with
   296	   Python's `ast` (code-graph node §5, option E). The deeper question, "is this entry still true", belongs to the
   297	   background subagent that compares entries with the code (`SOURCE_OF_TRUTH.md` lines 68–73), not to a model-free
   298	   script.
   299	5. **Why might it be needed later?** Any one of the three conditions in the code-graph node's §6, each a test:
   300	   - `covers:` starts naming functions or classes instead of files;
   301	   - the check must answer about files not on any `covers:` list ("what does this change affect");
   302	   - path-level flags raise too many false alarms — the comparison is in `SOURCE_OF_TRUTH.md` § How each threshold
   303	     is found. How many you will tolerate is the one policy value, and it is yours.

   134	## SQLite full-text index
   135	
   136	### Five whys
   137	
   138	1. **Why a full-text index?** To find entries by their words, ranked, with a snippet, instead of grep's unranked list
   139	   (`S-F1`, quoted: *"grep returns unranked matches."*).
   140	2. **Why does ranking matter?** Every hit the agent opens costs context. In the one controlled study, BM25 used 5.8K
   141	   tokens per question against 226K for an agent using grep over files, on its smallest corpus: 1,144 documents,
   142	   1.7M tokens (`S-F4`).
   143	3. **Why not build it now?** That study puts the point where BM25 overtakes the grep agent at around 10 million tokens
   144	   of text, and the grep agent led at the smallest sizes (`S-F4`). At our entry size that is about 37,000 entries
   145	   (`S-F5`, my reading via its 4-characters-per-token assumption). `INDEX.md` already lists every active entry. In the
   146	   researcher's own test, at 10,000 synthetic entries a one-word grep took 0.038 s and a grep chain for a header
   147	   question 0.06 s; at 50,000 the header chain took 0.15 s, and the one-word timing was invalid (`S-F13`). No study
   148	   covers a corpus of a few hundred to a few thousand short entries (`S-F5`: not measured).
   149	4. **Why might it be needed later?** `INDEX.md` stops being enough once it can no longer list every active entry under
   150	   its size limit. The agent then loses the one-line scan of every entry, and ranked search is what replaces it (my

   152	5. **Why only as a cache?** The markdown is the source of truth, and the cache must be rebuildable and skippable (M6).

   154	Structured questions such as "every active decision covering path X" or "what supersedes Y" do not need SQLite. A

   156	tokens; my reading is that the script and an SQL query return the same list of entries, so the agent reads the same

# Requirement check

A general standard (RFC 2119 / 8174), installed globally — not part of the Ancient Games framework. The
worked failure in `meaningful-names` cites the Ancient Games as one example.

A short gate between **hearing a rule** and **acting on it**. It exists because rules get written down that nobody
can trace, that count two different things at once, or that nothing can ever fail — and the cost lands months later,
when nobody can say whether the rule still means anything.

Run it when someone states a rule, and run it on yourself before writing a normative line into any document.

## The eight questions

Ask them of **one statement**. Say which it passes and which it fails, then **ask the person about the failures** —
do not fill the gaps yourself.

1. **Source.** Who said this, and where? Can you point to the exact line? *"Mine"* is a valid answer. Unlabelled is
   not.
2. **One thing.** An "and", an "or", a "/", or a second number means it is **two** statements. Split them, and give
   each its own source.
3. **Unit.** Every number says what it counts. Attempts or hours? Roles, or processes running at once? Bytes or
   files?
4. **Can it fail.** Name one concrete input that would make it fail. `TBD`, `—`, `0` and empty must be among the
   failing inputs. If you cannot name one, it is not checkable — it is a wish.
5. **Weak words.** *like, about, appropriate, as needed, logical, fast, enough, reasonable, only has to, TBD.* Replace
   each with a value, **or mark the value open**. Never invent the number.
6. **Level.** Is it **MUST** (a gate that stops work), **SHOULD** (a default that may be overridden with a stated
   reason), or **guidance**? A safety bound earns MUST. **A method does not** — see the RFC note below.
7. **Basis.** Measured, quoted from a source, or a guess? A guess is fine **if it is labelled** — `n=0`, with when it
   will be looked at again.
8. **Links.** Does it claim a relation to another rule — *"half of"*, *"pairs with"*, *"the same as"*, *"the runtime
   part"*? The person probably did not say that. **A link is its own claim and needs its own source.**

## Two rules for the agent

- **Never fill a gap with your own value.** A missing unit, threshold or test goes back as a question. Inventing it
  is exactly how a rule becomes unattributable later, and the invention is indistinguishable from the original by
  the time anyone notices.
- **Never add structure that was not given.** No halves, no numbered reasons, no ordered pairs, no named phases,
  unless the person said so. Quote them, state the operative sentence, stop. If a relationship between two rules is
  wanted, that is a separate claim with its own evidence.

## Two verified facts, worth quoting

- **RFC 2119 §6, "Guidance in the use of these Imperatives":** imperatives *"must be used with care and sparingly…
  they MUST only be used where it is actually required… they must not be used to try to impose a particular method."*
  Most design rules are method. Method does not earn MUST.
- **RFC 8174 (updates 2119):** the key words *"have the meanings specified herein only when they are in all
  capitals."* Lowercase *must* and *should* carry no defined requirement meaning. If nothing marks which lines are
  requirements, a reader cannot tell rules from explanation.

## How to answer

Evaluate first, in a table or a short list — **pass / FAIL per question**. Then ask the failing ones as questions,
one line each, with the options if you can see them. Two or three real questions beat eight formalities.

Do not report a rule as complete when you chose its missing value. Say which values you left open.

## A worked failure

> *"At most 5 subagent roles per run and at most 3 running at once."*

Four of the eight fail: **Source** — nobody could name one; **One thing** — a count of roles *and* a count of
concurrent processes; **Unit** — two different units, one word ("subagent") used for both; **Level** — a method
preference written as a cap. The sentence would not parse, and it took four days to find out why. The checklist
catches it in thirty seconds.

The same checklist, run on *"No single call runs longer than the ceiling: 8 hours"*, passes all eight — because it
names who set it, counts one thing, uses a unit, and some input (a 40-hour plan) makes it fail.

## Limits

The quality characteristics behind these questions (necessary, appropriate, unambiguous, complete, singular,
feasible, verifiable, correct, conforming) come from requirements-engineering sources — IEEE 830, ISO/IEC/IEEE 29148
and the INCOSE *Guide to Writing Requirements* — which were **not read** when this skill was written: they are
paywalled or blocked, and the list is recalled rather than verified. The two RFC points above **were** read, and the
quotes are checked. Treat the rest as a good working list, not as a citation.

   340	### R1 — Derived and disposable
   341	The cache is computed from the markdown and never holds knowledge of its own (M4, M6).
   342	
   343	- **R1.1** Deleting the cache and rebuilding from the files restores every answer. *Example:* `rm -rf
   344	  project-memory/.cache/` → run the documented rebuild → the same query returns the same entries. (M6)
   345	- **R1.2** Memory is fully readable with no cache present. *Example:* with `.cache/` absent, session start and an
   346	  on-demand `grep` over `entries/` both work. (M6)
   347	- **R1.3** The cache directory is ignored by git and a rebuild leaves `git status --short` clean. (M6)
   348	
   349	### R2 — Full rebuild, never patched
   350	- **R2.1** The documented rebuild regenerates the whole index from the files; no incremental update path exists.
   351	  *Example:* the rebuild command has no "update" mode. (G-F5 drift)
   352	- **R2.2** The index records what it was built from, so a stale one is detectable. *Example:* the index stores the
   353	  newest source file's mtime or the commit, and the query tool compares before answering. (S-F9)
   354	
   355	### R3 — Stale never answers
   356	- **R3.1** Before answering, the tool compares the newest source file with the index and rebuilds first if the
   357	  source is newer, building into a temporary file and renaming over the old one. (S-F9)
   358	- **R3.2** A wrong path is never mistaken for an empty index: the cache is opened read-only and "no such file" is
   359	  treated as absent. *Example:* point the tool at a typo'd path → it warns and falls back to grep, it does not
   360	  create an empty database. (G-F5, failure mode 5)
   361	
   362	### R4 — Absence degrades, it does not fail
   363	- **R4.1** A missing cache file or a missing FTS5 warns once and answers with grep. (S-F9)
   364	- **R4.2** A missing embedding model does the same. *(my reading, extending S-F9.)*
   365	
   366	### R5 — Nothing is built before its trigger fires
   367	Each cache has an observable trigger. This is the requirement that keeps the whole layer honest. The query-time
   368	counterpart — which store to reach for once a trigger has fired — is the section **When to use which store** above.
   369	
   370	- **R5.1 Full-text** — built only when `INDEX.md` can no longer list every active entry under its size limit.
   371	  `OPEN: not measured — the limit is the comparison in SOURCE_OF_TRUTH.md § How each threshold is found` (S-F5, S-F13: not measured for a corpus of a few hundred to a few thousand
   372	  short entries).
   373	- **R5.2 Vector** — built only after R5.1 has fired *and* the logged misses outweigh the cache's cost. A "miss" is
   374	  recorded when an entry existed and `INDEX.md`, grep and full-text search all missed it (V-F13).
   375	  `OPEN: not measured — the miss count is the comparison in SOURCE_OF_TRUTH.md § How each threshold is found.` The vector index is hybrid only — appended to
   376	  full-text results by reciprocal rank fusion, never instead of them (V-F3, V-F4, V-F6, V-F7; V-F10 is unproven).
   377	- **R5.3 Code graph** — built only when one of three conditions holds: `covers:` starts naming functions or classes
