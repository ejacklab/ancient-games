**The problem it solves.** The memory is markdown in git, and today `INDEX.md` plus grep finds what an agent needs —
at 10,000 entries a grep takes 0.038–0.06 s (`S-F13`). It stops being enough as the memory grows, for two reasons:
`INDEX.md` can no longer list every active entry under its size limit, so the one-line scan of everything is gone;
and grep returns unranked matches, where every hit an agent opens costs context (`S-F1`). The caches exist to keep
finding the right entry cheap at that size — and not before.

**What it will never do.**
- It is never the source of truth. The markdown is, always, and a cache holds nothing the files do not (`M4`, `M6`).
- It is never patched incrementally. It is rebuilt whole or not at all — a live index drifted 4.3% of its edges from
  a clean rebuild with every integrity check passing (`G-F5`).
- It is never read at session start (`M18`).
- It is never built before its own trigger fires. Every trigger is observable, and all three numbers are EJ's.
- It never becomes a second thing to keep in sync: delete the folder and memory is unaffected.

**How we know it works.** Delete the cache, rebuild it from the files, and the same query returns the same entries,
with no model call. That is the whole test (`M6`; a 10,000-entry FTS rebuild takes 0.53 s, `S-F13`; this repo's code
graph rebuilds in 0.94 s, `G-F12`). One caveat travels with every number here: none of it has been measured on a
real `project-memory/` corpus, because that corpus does not exist yet (`S-F5`, `V-F11`).

## How each threshold is found

The design asks EJ to set numbers — the `INDEX.md` size limit, and three cache triggers in `CACHES.md`. **They do
not need to be guessed.** Each is a *comparison between two costs that can be measured on this project*, so the
design states the comparison and the measurement decides the value when the corpus exists:

| threshold | it is not a number, it is this comparison | measured with |
|---|---|---|
| `INDEX.md` size limit (R5.1) | the index stays while **scanning it costs less than the alternative** — grep plus reading the hits | start-up token count of `INDEX.md` vs the tokens spent finding the same entry by search |
| vector miss count (R5.2) | build it when the **logged misses cost more than the cache** does | the miss log — an entry existed and `INDEX.md`, grep and FTS all missed it — against the index's build and query cost |
| code-graph false-alarm rate (R5.3) | build it when **false flags outnumber true ones** for path-level drift | the drift check's own output over a period of real use |
| rebuild budget (R8.2) | the rebuild must be **cheaper than the query it serves**, since it runs before answering | the measured rebuild (0.94 s code graph, 0.53 s FTS at 10,000 entries) against the search it enables |
| grep-call threshold | the baseline has failed when **one question class repeatedly needs repeated multi-call searches** | `G-F7a` already shows the range — 7 calls against 28–43 |

What is genuinely policy, and stays yours: how many false alarms you will tolerate before the flag is retired, and
whether a drifted decision is edited in place or superseded (item 4 above). Everything else above is measurement.

Numbering follows the list above: item 2 — *how the script tells that the entry changed earlier than the code* — is
the `pm stale` row: two `git log` calls, one on the entry file and one on each `covers:` path (code-graph §6,
`G-F14`, `G-F12`). That is a design proposal, not a decision.

import ast, json, sys, collections, os
REPO = '/home/smoke01/dev/ancient-games'
d = json.load(open(sys.argv[1]))
file_tests = collections.defaultdict(set); func_tests = collections.defaultdict(set)
for path, v in d['files'].items():
    rel = os.path.relpath(os.path.join(REPO, path), REPO) if not path.startswith('/') else os.path.relpath(path, REPO)
    spans = []
    try:
        tree = ast.parse(open(os.path.join(REPO, rel)).read())
        for n in ast.walk(tree):
            if isinstance(n, (ast.FunctionDef, ast.AsyncFunctionDef)):
                spans.append((n.lineno, n.end_lineno, n.name))
            if isinstance(n, ast.ClassDef):

                    if isinstance(m, (ast.FunctionDef, ast.AsyncFunctionDef)):

    for ln, ctxs in v.get('contexts', {}).items():
        tests = {c.split('::')[0] for c in ctxs if '::' in c}
        if not tests: continue

        ln = int(ln)
        for a, b, name in spans:
            if a <= ln <= b:
                func_tests[f'{rel}::{name}'] |= tests
out = {'note': 'derived from pytest-cov --cov-context=test, 2026-10-12; in-process Python only',

## By category

`file hit@5` counts a gold `path::name` as hit when the route returns its file. `symbol hit@5` needs the symbol itself: an entry naming it, the top-level def/class holding it or a method of it, a module-code chunk for a module-level name, and for `rg` a printed match line inside the symbol's lines. A gold given as a plain file scores the same on both. **The best route is chosen on symbol hit@5.**

`chars` is the mean number of characters of output read up to and including the first line where the route names a gold file as its answer (`# <path> (`, or a line starting `<path>:`), over the answers that named one; `n` is how many did. A miss is left out, never scored 0. What each route prints differs -- rg: a `# path (N matching lines)` header per file plus at most 40 match lines of up to 300 characters; fts: one 24-token snippet per path; vec: the first 300 characters per path; hybrid: the vec or fts block per path; graph: one id per line -- so `chars` measures the print format as much as the store.
