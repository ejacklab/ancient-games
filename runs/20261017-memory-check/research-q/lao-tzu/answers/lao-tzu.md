# 老子 (Laozi) — how memory-check should work before any code is written

## Answer

Check the 9 `tool` records by calling `tools/memory_index.py` and check 5 more from git history per commit; report the other 6 `tool`/`git` records as **not checkable** and the 33 reviewer-only ones by id, and take nothing else. Four docs need one decision each before code: the conflict between C1 and U4, the "with no written reason" escape, the absent-memory exit code, and the hook that would break Rd1.1/Rd2.3b.

## How I decided

**Decision 1 — what is checkable, and how.** My count of the YAML (`SOURCE_OF_TRUTH_REQUIREMENTS.yaml`, 64 records; 9 `tool`, 13 `git`, 6 with both a reviewer and a tool/git check, 33 reviewer-only, 11 `none`) agrees with the brief's "about 20".

1. **All 9 `tool` records are already built. The tool adds no entry check at all.** W1.1a (prefix↔kind), W1.1b (id form, duplicate ids), W1.2a (header between two `---`), W1.3a (claim and `**Why:**`), W4.1b (`status` in active/superseded/retired), K6.1a, K6.2 (index bytes), K6.3a (conflict markers), Rd3.1a (200 lines / 24,000 bytes) — each has a function in `tools/memory_index.py` (`check_content`, `parse_header`, `read_claim`, `flag_duplicate_ids`, `flag_conflict_markers`, `check_index`, `over_limit`, lines 35–36, 104–203, 269–271, 481–508). **my #14** — 不自見故明，不自是故彰: the second, not-built, way to do it is what makes it unclear which is right.
2. **So C3 ("call it, do not rewrite it") means the report's 9 tool rows are one subprocess and a mapping, not 9 implementations.** My #1: 損之又損，以至於無為。無為而無不為 — take away the second implementation and the nine checks are still there.
3. **5 more are decidable from git history, one commit at a time:** W4.2 (each commit touching an entry adds a `changed:` line), K4.3 (claim/`source`/`depends_on` never change after the first commit), K4.1 (an entry file is never deleted; a `superseded` one carries `superseded_by`), K5.1 and W6.1b (a journal file is never edited after it is written), W6.3a and W6.2 (at a **merge** commit, the result must contain every `changed:` line, link and `covers` path either side added; an edit present in one parent, absent in the other and absent in the result is lost). My #6: 為之於未有，治之於未亂 — each is a check on a state that already exists, made before the tool is asked anything.
4. **6 of the 20 cannot be decided by any tool**, and must not be given a result: W2.1b, W5.1 and K1.1 all turn on "a commit changes code **under a new decision or fact**" — `covers` is a SHOULD field the reviewer checks (W1.2b) and is often empty, and "is this a new decision or fact" is a judgement; W6.2 on a **rebase** or force-push leaves no parent to compare; K5.1's "raw notes are kept elsewhere"; K4.1's "a reason in its `changed:` line". **my #8**: 知不知上，不知知病。夫唯病病，是以不病 — knowing what the tool cannot see is the result to give, and it must be a distinct word from "pass".
5. **5 more are mechanically decidable but the YAML gives them `reviewer`**, so building them would break C1/U4: W1.1c (file-name form), W1.2b (field keys present), K6.1b and K6.3b (hand-edited or hand-merged index — the same byte comparison as K6.2), Rd1.1 (layout). **my reading**: this is the guideline understating itself. AGENTS.md says a problem in the three guideline files "is reported, not fixed here" — so the tool's report should carry this as an observation for the owner, not a fix.
6. **One more thing the tool cannot do, which C3 does not mention:** `memory_index.py` takes no path. `repo_root()` is `git rev-parse --show-toplevel` of the **current directory** (`tools/memory_index.py:316-318`). On a fixture that is not a git repository it cannot run at all, and all 9 tool ids then have no result. Fixtures must be git repositories and the tool must spawn it with `cwd` set. Verified by reading the source; a fixture test is needed to see the error text.
7. **History scope and cost.** W4.2, K4.3, K5.1, W6.3a and W6.2 all want one pass over the history of `project-memory/`. This repo has no `project-memory/` (`ls project-memory` → No such file or directory), so there is **no measurement** of that pass — the same GAP `CACHES.md` records for its own triggers. **my #2**: 知足不辱，知止不殆，可以長久 — know where to stop; set the history scope as a parameter and measure it on a synthetic 1,000-commit fixture before fixing it.

**Decision 2 — what is missing or misleading in the four docs.**

8. **C1 and U4 contradict each other on six ids: W1.3a, W5.1, W6.1a, W6.3a, K1.1, K4.1.** C1 (MUST) says a record whose `check` is `tool` or `git` "is checked by the tool"; U4 (proposed) fails if a record whose `check` is `reviewer` "is reported as passing or failing by the tool". Those six carry both. AGENTS.md says a use case wins — so U4 wins and C1 is wrong as written for them. This must be settled in the docs, not by the agent. My #16: 知人者智，自知者明。勝人者有力，自勝者強 — read the six ids against the two rules yourself before writing a line.
9. **"With no written reason" defeats mechanical checking, and no doc says where a reason lives.** Every SHOULD's `fails_if` ends that way, and `levels` says a SHOULD "may be skipped with a reason written in the task's state.md". So a mechanically found break is *not* a failure if a reason exists — and the tool would have to read `state.md` files and commit messages and decide whether the reason belongs to this entry. That is the reviewer's judgement, which the YAML gives to `reviewer`. Without a rule for where a reason is written, the tool must invent one, and VISION.md forbids that ("The tool adds no rule of its own"). **This is the largest gap in the four docs.** My #19 (attributed): 以深爲根，以約爲紀 — the root and the rule; give the reason a place and a bound, or give up the check.
10. **R3 makes "no memory at all" a silent pass.** With no `project-memory/`, every MUST is "not applicable" under C4, no MUST fails, exit 0, and U3's warning is empty — so an agent at session start is told nothing, on a repo whose whole session-start memory is missing. C4 names only `AGENTS.md` as required-when-absent; `INDEX.md` and `entries/` are unlisted. **This repo would be exactly that case on day one.** My #17: 故有之以為利，無之以為用 — what is not there has its own use, but absence of the *whole* memory is not absence of an optional cache. The owner must name the required-when-absent list.
11. **R2's hook is the thing Rd1.1 and Rd2.3b forbid.** R2 makes the warning a session-start hook; Rd1.1 fails "if a start hook or instruction opens any file under `project-memory/.cache/`", and Rd2.3b never loads "the whole `project-memory/` tree at once". A warning built from every entry's header **and claim** is most of the memory's bytes at session start. R2 has no clause limiting what the hook reads. Decision needed: the hook runs locations + `memory_index.py --check` + index size only, and the body checks (W1.3a) belong to the command; or the warning can miss a W1.3a failure, and the report must say so. My #5: 我無為而民自化，我好靜而民自正，我無事而民自富，我無欲而民自樸 — the hook reads and warns; it does not act on memory.
12. **K6.1a and K6.2 have the same `fails_if`.** One command, two ids. U2's "exactly that requirement reported as failing" is ambiguous for a fixture that breaks both; the report must cite both ids on one result. My #8 again — say which ids, do not let one row imply one id.
13. **A tool-level error belongs to no id.** `memory_index.py` reports "not known to git, git add it first" (line 157) for an unstaged entry, and a rev that names no commit (line 527). These are real findings with no requirement id. R1 says one row per requirement; C2 says every result carries evidence. There is no place for a finding that is not a requirement. Small, but R1's format must have one, or the tool will drop or invent it.
14. **The exit code is a gate over the wrong thing if a check is unknown.** R3 exits 1 when a MUST fails. If W2.1b (SHOULD) or a MUST's blind half cannot be decided, "no MUST fails" is not "memory is fine". My #8 again: treat the sickness as the sickness — one `unknown` state, never folded into pass.

**Decision 3 — the build, and tests without circularity.**

15. **Eight pieces, each one fixture, each planted break first (AGENTS.md).** P1 find locations (F1, F2) — a fixture with every location, one with none. P2 parse headers and bodies — no judgement. P3 run `memory_index.py --check` in a fixture repo and map its output to the 9 ids (C3) — one fixture per id. P4 the git pass → the 5+2 history ids. P5 the reviewer list derived from the YAML at run time, never a hardcoded id (U4, C1). P6 not applicable (C4) — the absent fixture. P7 report (R1) and warning (R2) rendered **only** from P3–P6's data, so the report cannot differ from the checks. P8 exit codes (R3) and the read-only proof (F3, U5: `git status --short` before and after). **my #6**: 圖難於其易，為大於其細 — eight pieces, each small, each with its own bar; **my #7**: 民之從事，常於幾成而敗之。慎終如始，則無敗事 — the warning is the last piece and the most visible, so it gets the last care.
16. **Non-circular tests: the known answer must not be produced by the check's own code.** K4.3 — the fixture is two hand-written commits, and the expected answer is which lines differ, written out by hand; never re-derived by the checker. W4.2 — the expected answer is a hand-built commit sequence and a `grep -c '^  - '` count run by the test, not the checker's header parser. K6.1a/K6.2 — the expected `INDEX.md` for a two-entry fixture is a **literal byte string** written in the test; both the checker and `memory_index.py` must match it, which is a real agreement between two independent things. Rd3.1a — the expected size is `wc -l -c` in the test. P8 — expected exit codes are literals. **my #1** again: 損之又損 — the second way of computing the answer is the thing to take away. **Proposed change to the pattern:** the run pattern's "research and data, not recall" has no rule for *known answers*; add one — a trial in which the expected answer is computed by the same code as the check does not count as a trial.
17. **No committed project with memory exists here to calibrate against.** This repo has no `project-memory/`, so every fixture would be written by the same author as the checker, on a corpus the guidelines never saw. **Proposed change to the pattern:** the pattern sets the time, the pieces and the citing; it does not require a **known-empty baseline**. Add one step — before building, run the tool on the thing it will check and publish the empty answer (here: 20 of 20 not applicable, exit 0), and build at least one fixture whose memory is real, not authored by the checker. My #16: 自知者明 — check the tool against the repo before you trust its report of the repo.
18. **On the pattern itself, one point to keep.** The pattern sends a question to EJ only after three failed trials or when the time is used up (brief, "How we work"). Nine of decisions 1–3 above are *not* failed trials — they are contradictions between two of EJ's own documents, readable in one pass. **Proposed change to the pattern:** a question that two documents in the run already contradict goes to EJ on the first finding, not the third; three trials are for questions whose answer the run can find. My #18 (attributed): 且君子得其時則駕，不得其時則蓬累而行 — ask when the time is right.

## What I need to know

1. Where is a written reason written, and how is it matched to the entry it excuses? Without this, every SHOULD with "with no written reason" is undecidable, and the tool either invents a rule (forbidden) or reports false failures.
2. For a record whose `check` is `git`, does "checked by the tool" mean it returns pass/fail, or that it runs a command and may return "cannot see"? This decides W5.1, W6.1a, W6.3a, K1.1, K4.1 and the six-id C1/U4 conflict at once.
3. Beyond `AGENTS.md`, which locations are **required when absent** — `INDEX.md`, `entries/`? This decides R3's exit code and whether U3's warning is empty on this repo today.
4. Does the session-start hook (R2) get the full check set or a reduced one? Rd1.1/Rd2.3b and R2 cannot both hold as written.
5. Is the history scope the whole history of `project-memory/`, or since the memory began? No measurement exists, so this is currently a guess.

## Costs and risks

- **False comfort.** Cutting to 14 decidable ids means a repo with real violations of W2.1b, K1.1 and W5.1 reports zero failing MUSTs. That is the price of not inventing a rule. **my #8**: 知不知上，不知知病 — and the price of hiding it is worse: **do not** reuse C4's "not applicable" wording for "cannot see", or the report will read as complete, which is exactly what U4 exists to prevent. **my #4**: 天下神器，不可為也 — a wrong answer here misleads the agent it warns.
- **The hook reads memory at session start.** Honouring Rd1.1/Rd2.3b costs a reduced warning that can miss a W1.3a failure; not honouring them makes the tool the violation. **my #4** again: 為者敗之.
- **Merge-only coverage is silent coverage.** W6.2 and W6.3a work on merge commits and not on rebases. If the report does not say which history shape it looked at, it claims more than it checked. **my #8**.
- **Cost of the split.** Eight fixtures and eight sets of planted breaks, before any of it is useful. **my #6**: 天下難事必作於易，天下大事必作於細 — this is the cheap moment.
- **Caching the git pass** would mean writing outside the report, which F3 forbids. Recompute, or cache under `runs/` and say so.
- **Cuts that cost scope.** Dropping the 5 mechanically-decidable-but-reviewer records (step 5) means EJ's reviewer does five trivial checks by hand. Cheap, and it keeps C1 and U4 consistent. **my #3**: 功成而弗居。夫唯弗居，是以不去 — the smaller scope is the one that stays.

## How we would know I was right

- Run it on this repo: the report must show `project-memory/` absent, all 20 tool/git ids not applicable, exit 0, **and** an observation line naming the 5 records a tool could check but the YAML assigns to `reviewer`. If it instead reports failures, C4 or F1 is wrong.
- For each of the 9 tool ids, a fixture git repo with exactly one planted break: exactly that id fails, named by file and line, and no other id changes. Count of failing ids per fixture must be 1.
- A fixture where a claim is rewritten after the first commit: K4.3 fails. A fixture where only `covers` changes: K4.3 passes and W4.2 fails. If those two come out the same, the check is reading one field where it should read three.
- A merge commit that drops one side's `changed:` line: W6.3a fails; the same history rebased: it must say it did not look, not that it passed.
- A `state.md` line that is a written reason: the related SHOULD must not be reported as failing. This is the test for problem 9, and it is the one I most expect to fail first.
- The reviewer list must contain 33 ids and the tool-or-git list 20, read from the YAML, with no id written in the source. Change the YAML's `check` field for one id in a test and see the report move.
