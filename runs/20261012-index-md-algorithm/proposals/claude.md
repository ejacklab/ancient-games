# INDEX.md — proposal (claude)

Read in full: `docs/memory-system/SOURCE_OF_TRUTH.md`, `lit-review/claude.md` (C1–C58), `lit-review/codex.md`
(X1–X35), `lit-review/opencode.md` (O1–O43). The agy review does not exist (dropped by EJ, `state.md` log). I did not
read the other engines' stage-2 proposals. Nothing in the repo was changed.

**In one sentence:** one standard-library Python script builds `INDEX.md` from `entries/` as a pure function of the
entry files and writes it to a committed file. The same script, with `--check`, rebuilds it from a git snapshot and
compares the bytes. Whoever writes an entry runs the script, and a committed git hook runs the check on every commit or
merge that touches `project-memory/`. A conflict in `INDEX.md` is never merged by hand: it is regenerated. An index over
the size limit is never cut: the check fails, and EJ decides.

**Assumptions** (*my reading*, not stated in the design):
- The entry header is front matter between two `---` lines, written as `key: value`.
- The script lives outside `project-memory/`, so Rd1.1's layout does not change. I write `tools/memory_index.py`
  because this repo has a `tools/` folder and no `scripts/`. Any fixed path works.

## The algorithm

**The parts:**
- One script, `tools/memory_index.py`. It needs Python 3 and its standard library, nothing else.
- Two committed hook files, `.githooks/pre-commit` and `.githooks/pre-merge-commit`, with the same content.
- Two instructions in `AGENTS.md`.

There is no merge driver, no CI job (this repo has none), no session-start regeneration and no agent-specific hook.

**Building the index** (shared by both modes):

1. **Read the entry set.** Take every file directly in `project-memory/entries/` whose name matches
   `^[DFLROH]-[^/]+\.md$`, and nothing else: no subfolders, no dotfiles, not `INDEX.md`. Where the files come from
   depends on the mode:
   - **Write mode** reads the working tree.
   - **Check mode** reads git objects. With no argument it reads the staging area (`git ls-files -s`, then
     `git show :<path>`). With `--check <rev>` it reads that commit (`git ls-tree`, then `git show <rev>:<path>`).

   Decode each file as UTF-8 and turn CRLF into LF.
2. **Sort** the file names with Python's default `str` ordering, which compares code points. Never use locale
   collation or the order a directory listing returns (C2, C14, O6). Because file names start with the kind prefix, the
   index comes out grouped by kind: D, F, H, L, O, R.
3. **Parse each file.**
   - The header is the text between the first line `---` and the next `---`. From it, read only the top-level `id:`,
     `kind:` and `status:`, stripping whitespace and any surrounding quotes.
   - The **claim** is the body from after the closing `---` down to, but not including, the first line that starts
     with `**Why:**`. Drop blank lines, collapse every run of whitespace (newlines included) to one space, and strip
     the ends. W1.3 says the body opens with the one- or two-sentence claim, and this turns that claim into the one line
     K6.1 asks for. Nothing is shortened.
4. **Validate before writing anything.** Collect every problem and report all of them. The checks are:
   - the header is present;
   - `id`, `kind` and `status` are present;
   - `kind` is one of decision, fact, lesson, runbook, observation, hypothesis;
   - `status` is one of active, superseded, retired;
   - a `**Why:**` line exists and the claim is not empty;
   - no two entry files share an `id`, whatever their status.

   If any check fails, print one `<file>: <problem>` line per problem, write nothing and exit 1. These are only the
   fields the index needs. The full W1 lint is a separate check (X33, O43).
5. **Select** the entries whose `status` is `active`. Superseded and retired entries get no line, which is K6's
   "Fails if".
6. **Render** these exact bytes: UTF-8, LF line endings, one newline at the end of the file.
   ```
   # Project memory index

   <!-- GENERATED by tools/memory_index.py from project-memory/entries/. Do not edit by hand. Regenerate: python3 tools/memory_index.py -->

   - [<id>](entries/<file name>) <kind>: <claim>
   ```
   There is one `- …` line per active entry, in the order from step 2. With no active entries, the list is the single
   line `(no active entries)`. The file has no date, timestamp, count or "generated at" line (C15, O7, X8). The marker
   comment names the command that rebuilds the file (C20, O2, O39).
7. **Measure the size.** Count the lines and UTF-8 bytes of the rendered text. Compare them with `MAX_LINES` and
   `MAX_BYTES`, two constants at the top of the script whose comment cites Rd3.1 and `CACHES.md` § Example numbers by
   case. Every run prints `INDEX.md: <lines>/<MAX_LINES> lines, <bytes>/<MAX_BYTES> bytes`, so the growth is in view
   long before the limit is reached. The size is compared, not judged: there is no warning threshold.

**Write mode:** `python3 tools/memory_index.py`

8. Run steps 1–7 on the working tree.
   - If the rendered text is byte-identical to the current `project-memory/INDEX.md`, leave the file alone (C3).
   - Otherwise write a temporary file in the same folder and rename it over `INDEX.md`.
   - **If the index is over the limit, still write the whole file.** It is the true index, and K6.1 wants one line per
     active entry. Then print `over the start-file limit (Rd3.1): commits that touch project-memory/ will fail until EJ
     decides`, and exit 1.
   - Exit 0 otherwise.

   The script writes `project-memory/INDEX.md` and nothing else. It never changes an entry.

**Check mode:** `python3 tools/memory_index.py --check [<rev>]`

9. Run steps 1–7 on the git snapshot: the staging area, or `<rev>`. Compare the rendered text, byte for byte, with
   `project-memory/INDEX.md` in the same snapshot.
   - Exit 0 only if three things hold: the entries are valid, the bytes are equal, and the size is within the limit.
   - Otherwise exit 1 and print what failed. If the bytes differ, also print a unified diff (`difflib`) and the fix,
     `python3 tools/memory_index.py && git add project-memory/INDEX.md` (C54, C55, O38–O40, X31).

   Check mode reads only git objects, so it never touches the working tree and works the same in any worktree.

**When it runs, and what runs it:**

10. **The writer, right after creating or changing any entry file**, runs write mode. "The writer" is any agent or
    person, and "any entry file" means every kind and every status change, not only decisions and facts (see Design
    changes). The entry and `INDEX.md` go into **the same commit**.
    - This is `AGENTS.md` instruction 1: *"After you create or change a file in `project-memory/entries/`, run
      `python3 tools/memory_index.py` and commit `project-memory/INDEX.md` with it."*
    - It is the only trigger that every agent and every person gets, web sessions included, because it needs nothing
      installed.
11. **The git hooks, at every commit and merge that touches memory.** Each hook file does two things:
    - It runs `git diff --cached --name-only -- project-memory/`, and exits 0 if the output is empty. This keeps code
      commits from being blocked by memory.
    - Otherwise it runs `python3 tools/memory_index.py --check` (the staging area) and returns its exit code.

    The two hooks cover different commits. git's own manual (read locally, git 2.43):
    - `pre-merge-commit` runs on a merge that git completes without conflicts. A clean text merge is therefore checked,
      not trusted.
    - `pre-commit` runs on the `git commit` that concludes a conflicted merge. The manual says of a merge that stops on
      conflicts that `pre-merge-commit` "will not be executed, but the pre-commit hook will, if it is enabled".

    The hooks are switched on once per clone with `git config core.hooksPath .githooks`; worktrees share that setting.
    That command is `AGENTS.md` instruction 2.

    The check runs on the staged snapshot rather than regenerating and staging, because unstaged entries would
    otherwise leak into the commit (X15). A clone without the hooks, or a commit made with `--no-verify`, skips the
    check. The next hooked commit that touches memory checks the whole snapshot and fails until the index is fixed.
12. **Anyone, at any time:** `python3 tools/memory_index.py --check HEAD` is K6's "Fails if", runnable as written.

**Git and parallel branches:**

13. `INDEX.md` is committed (Rd1.2) and merges as normal text.
    - Each line comes from exactly one file, and the lines are sorted by file name. So entries added on different
      branches usually land on different lines and merge cleanly. *My reading*, not measured.
    - When `INDEX.md` conflicts, **nobody edits it**. First resolve the conflicting entry files (who does that is W6's
      open question). Then run write mode, `git add project-memory/INDEX.md` and commit. The `pre-commit` check
      confirms the result (X19, C38, C39).

**When the index is too big:**

14. Nothing is truncated, dropped, ranked, split or moved into an "Optional" section. The full file is written (step 8)
    and the check fails (step 9), so memory commits stop until EJ decides, for example to:
    - supersede, retire or merge entries;
    - change `MAX_LINES` / `MAX_BYTES` after measurement;
    - change K6.1 / Rd2.1 to allow a second-level index.

    The overflow mechanism is chosen when it is needed, not built in advance.

## Three supporting reasons

1. **This is the shape that ended the shared-file conflict elsewhere, and committing it is the part Rd1.2 forces.**
   - GitLab and CPython stopped writing to one shared file by hand and moved to one file per entry, with the combined
     file derived from them (C31, X17). The design already has one file per entry (W6.1).
   - A clone must be able to read the index with no generator run, which makes it a committed file (O25, C25, C34),
     not one built at read or release time (C32, O21, X20).
   - Sorting by file name puts parallel additions on different lines (C2). A conflict that still happens is resolved by
     regenerating, which FKF requires in its normative text (X19) and which mdsmith and npm automate (C38, C39).

   (findings: C31, X17, O25, C25, C34, C32, O21, X20, C2, X19, C38, C39)
2. **A deterministic generator makes K6's check exact, and one script both writes and checks.**
   - "Regenerating changes it" is a real test only if the output is a pure function of the entry files (O5). The known
     ways to break that are locale collation, directory-listing order and timestamps (C2, C9, C14, O6, C15, O7, X8),
     and steps 2 and 6 remove all three.
   - Kubernetes and Cog check generated files exactly this way: regenerate, then compare (C54, O38, C55, X31). doctoc
     shows that the writer and the checker can be one command (O40), so there is no second implementation to drift.
   - Reading git objects instead of the working tree is the same isolation Kubernetes gets from a clean worktree
     (C54), without creating one.

   (findings: O5, C2, C9, C14, O6, C15, O7, X8, C54, O38, C55, X31, O40)
3. **Failing loud on size, with no overflow mechanism yet, keeps K6.1 true and builds only what is needed.**
   - The sources disagree on overflow. Qwen Code drops lines (C46), Claude Code errors (C45, X25), mdsmith refuses
     (C52), Repomix splits (C53), and others nest or rank (O35, O36, X27, C47).
   - Every answer that keeps the file small either breaks K6.1's "one line per active entry" or changes what Rd2.1
     loads (X26, codex's "did not find" on overflow).
   - Losing lines silently is the worst outcome: past the limit, content is dropped on the next load (C45), and a long
     file gets ignored without notice (O31).
   - Headroom is large. `CACHES.md` puts the byte limit at about 107–150 lines of index (*quoted*, its table row for
     Claude Code). Karpathy reports a single index working at "~100 sources" (C51).
   - Under the owner's rule, a mechanism that is not needed is not built. The check makes the moment it becomes needed
     visible.

   (findings: C46, C45, X25, C52, C53, O35, O36, X27, C47, X26, O31, C51)

## Six must-not-dos

1. **Do not merge `INDEX.md` with `merge=union`, and do not hand-merge it.** `union` silently re-adds a line that one
   side removed, so a superseded entry comes back as active, which is exactly K6's "Fails if". It also leaves added lines
   "in random order". (finding: C36; also C35, O24, X21)
2. **Do not let the output depend on the machine.** That rules out locale collation, directory-listing order, and any
   date, timestamp or "generated at" line. Byte-identical output across machines is what stops two collaborators
   rewriting the file back and forth, and what keeps the check from raising false alarms. (finding: C2; also C14, C15,
   O6, O7, X8)
3. **Do not truncate, drop or demote lines to fit the size limit.** A cut index hides active entries from every session
   without a sign, and K6.1 requires one line per active entry. (finding: C45; also C46, O31)
4. **Do not skip a malformed entry, and do not emit a line with a hole in it.** A generator that falls back silently
   (Understory, X4) reproduces a bad input faithfully, so a freshness check alone passes it. The script fails and names
   the file. (finding: X33; also X4, O43)
5. **Do not give entries ids by "the next free number".** Two branches will both take the same number, and the clash
   shows only after the merge. Ids must be unique without coordination; blurb, reno and Beads use a datetime, a nonce or
   a hash for this. Step 4 fails on a duplicate id. (finding: C40; also C16)
6. **Do not deliver `INDEX.md` at session start through a Claude Code `SessionStart` hook's stdout.** That output is
   capped at 10,000 characters, with no setting to raise it. Past the cap only a 2,000-character preview reaches the
   agent, which is far below Rd3.1's example limit, and the agent is not told to read the rest. Load it the way Rd2.1
   says: an `AGENTS.md` instruction, or a `CLAUDE.md` import (C28). (finding: C44)

## Design changes

All of these are *proposed*; EJ decides.

1. **K6, its Open line.** Close it: the tool is `tools/memory_index.py` (the path is EJ's choice). What runs it is the
   writer (instruction 1), the committed `pre-commit` / `pre-merge-commit` hooks (instruction 2), and anyone's
   `--check HEAD`.
2. **K6.2.** Change "regenerated right after any decision or fact is written" to: *"regenerated right after any entry
   is created or changed, and committed in the same commit as that entry."* Two reasons:
   - A lesson, or a status change to `superseded`, also changes the index, and K6's "Fails if" applies to every
     regeneration.
   - A separate commit opens a window in which a branch carries the entry but not its line.
3. **K6.3 (new).** *"`INDEX.md` is never merged by hand. On a merge conflict, resolve the entries first, then
   regenerate it."* This settles W6's open question for `INDEX.md` only. It stays open for entry files.
4. **Rd3.1.** Three changes:
   - "the build checks it" becomes *"the index script checks it at every commit that touches `project-memory/`"*. There
     is no build in this repo.
   - Add: *"Over the limit, nothing is cut; memory commits fail until EJ decides."*
   - The example "about 24 KB and 200 lines" needs **one exact byte number** for `MAX_BYTES`. That is an open question
     for EJ, not a value I fill in.
5. **W1.1.** Add: *"An `id` is unique without coordination between branches; it is never the next free number."* The
   form (datetime, hash, nonce) is EJ's choice.

There are no changes to Rd1.1, W1.2 or W1.3. The script sits outside `project-memory/`, and the claim is read from the
body as it is now, with no new header field.

## Where I disagree with the other reviews

- **opencode O17, O41:** they put K6.2 on a Claude Code `PostToolUse` hook. I disagree, because that covers only Claude
  and not Codex, Qwen, opencode or people (opencode says so itself in its gaps). The `AGENTS.md` instruction plus a git
  hook covers everyone who writes.
- **opencode O16:** regenerating on `post-checkout` writes a tracked file on every branch switch and dirties the tree. I
  do not use it.
- **opencode O23, O26:** `merge=binary` and `git rerere` are not needed. With lines sorted by file name, most merges are
  clean, and the hooks check the ones that are clean but wrong. A conflict is resolved by regenerating, so there is
  nothing for rerere to remember.
- **opencode O20, O42:** they leave "fail versus push-fix in CI" open. I choose fail, at commit time: K6's "Fails if"
  is a failure, and this repo has no CI to push from.
- **opencode O30, O33:** they say "the strictest limit is Claude's 200 lines". Claude's 200 lines / 25 KB is documented
  for `MEMORY.md` only (C45, X26). The real limit depends on the load path (C44, C45, C48), and `CACHES.md` says bytes
  bind before lines. The script checks both.
- **opencode O1, O35, O37:** they suggest injecting into a region of a hand-written file, ranking, or an "Optional"
  tail. I do not adopt any of them: K6.1 makes `INDEX.md` a whole generated file with one line per active entry.
- **codex X3, X5:** the summary there comes from a frontmatter `description` field. I take the claim from the body
  instead, because W1.3 already holds it and a second copy in the header could drift from the body.
- **my own C4, C34, C47:** none of these fits this design.
  - C4: Qwen's "(also: …)" deduplication breaks one line per entry.
  - C34: fast-forward-only sync does not fit agents that work on branches and merge.
  - C47: a tree index changes Rd2.1.
