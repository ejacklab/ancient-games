## Findings

### 1. Building the lines

**X1 — my reading, S5.** miku-indexgen scans local files, parses Markdown YAML frontmatter, copies a documented whitelist of metadata, and extracts a summary from the first heading or leading body text while excluding frontmatter. It supports `status`, but its README does not document filtering entries to `status: active`. [Source](https://github.com/igapyon/miku-indexgen)

**X2 — quoted, S5.** miku-indexgen specifies: “`files[]` entries are sorted by normalized relative path using UTF-16 code unit order.” It also excludes the current run’s generated index files from the input listing, avoiding self-inclusion. [Source](https://github.com/igapyon/miku-indexgen)

**X3 — my reading, S12.** FKF derives index tables from folder contents and each file’s required `description` frontmatter, with dates excluded from domain indexes. This establishes prior art for deterministic rendering from an authored summary field rather than generating a new summary during each rebuild. [Source](https://shll.ai/fab-kit/fkf/)

**X4 — my reading, S8.** Understory sorts immediate directory entries with `localeCompare`, skips hidden entries and reserved filenames, reads `title` and `description` from frontmatter, and emits linked Markdown bullets before a separate subdirectory section. It falls back to filenames on parsing errors, does not filter by lifecycle status, and does not enforce single-line descriptions; its locale-dependent comparison also leaves cross-environment ordering unestablished. [Source](https://github.com/thecodacus/understory/blob/main/packages/core/src/okf/indexer.ts)

**X5 — quoted, S7.** OKF says: “Entries SHOULD include the description from the linked concept’s frontmatter.” Its index structure groups links and descriptions under headings and can include links to subdirectories. [Source](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)

**X6 — my reading, S6.** The mkdocstrings recipe explicitly sorts discovered source paths, converts them to relative Markdown paths, accumulates navigation entries, and writes `SUMMARY.md` from that navigation object. This is executable prior art for discovery → explicit ordering → relative links → generated Markdown navigation, although its inputs are source modules rather than memory entries. [Source](https://mkdocstrings.github.io/recipes/#generate-a-literate-navigation-file)

**X7 — my reading, S2.** Towncrier reads a fragment’s identifier and type from its filename and uses its body as the displayed content; the tutorial demonstrates grouping by type and combining identical descriptions associated with different issue IDs. That deduplication differs from K6.1’s requirement for one line per active entry. [Source](https://towncrier.readthedocs.io/en/stable/tutorial.html)

**X8 — my reading, S3.** Towncrier’s generated date comes from an explicit `--date`, then `SOURCE_DATE_EPOCH`, then the system clock. Its reproducibility controls show why identical fragment files alone do not guarantee identical output when generation also consumes changing environmental inputs. [Source](https://towncrier.readthedocs.io/en/stable/cli.html#reproducible-builds)

### 2. When it runs and what runs it

**X9 — my reading, S9.** Understory’s write and patch methods await an `afterMutation` step that regenerates the changed directory’s index and its ancestors, appends a log entry, and optionally commits. Regeneration is part of the write operation, providing a closer timing analogue to K6.2 than release-time generation. [Source](https://github.com/thecodacus/understory/blob/main/packages/core/src/okf/knowledge-base.ts)

**X10 — my reading, S3.** Towncrier exposes an on-demand `build` command, a draft mode that renders without writing files, and `--keep` to retain processed fragments. These are documented execution modes, not evidence that Towncrier automatically runs after each source-file edit. [Source](https://towncrier.readthedocs.io/en/stable/cli.html)

**X11 — my reading, S4.** Towncrier documents both checking and updating hooks for commit-time or CI execution, including an update example that retains fragments. The generator and its trigger are therefore separate configurable parts of the workflow. [Source](https://towncrier.readthedocs.io/en/stable/pre-commit.html)

**X12 — my reading, S16.** Changesets separates adding a Markdown fragment with YAML frontmatter from running `changeset version`, which consumes accumulated changesets to update versions and changelogs. Contributors can record source fragments before the combined output is generated. [Source](https://changesets.dev/guide/cli)

**X13 — my reading, S10.** Understory regenerates its compact seed overview for every new session and refreshes the tool description after its own memory mutations; its README says out-of-band edits are picked up on the next session. This is session-start generation of an agent overview, distinct from rebuilding a committed Markdown index. [Source](https://github.com/thecodacus/understory/blob/main/README.md#seed-memory)

**X14 — my reading, S19.** Git’s `pre-merge-commit` runs after a successful merge and before creating the merge commit, and can be bypassed; `post-merge` cannot change the merge outcome and does not run when merging fails with conflicts. Neither hook alone supplies a procedure for resolving a generated-file conflict that has already stopped the merge. [Source](https://git-scm.com/docs/githooks)

**X15 — quoted, S18.** pre-commit explains that it “only runs on the staged contents of files by temporarily stashing the unstaged changes while running hooks.” It also documents `pre-commit run --all-files` for CI, distinguishing commit-snapshot checks from checks over the working tree. [Source](https://pre-commit.com/)

**X16 — my reading, S17.** Changesets’ documented automation runs on pushes to `main`, creates a versioning PR, and groups concurrent workflow runs by branch. This is prior art for generating combined artifacts after contributor branches land, but does not provide immediate regeneration inside each contributor’s worktree. [Source](https://changesets.dev/guide/automating)

### 3. Git: committed or not, and parallel branches

**X17 — quoted, S1.** Towncrier contrasts fragments with “one single file which developers all write to and produce merge conflicts.” Its conflict-avoidance mechanism is separate contributor input files rather than simultaneous authoring of the combined changelog. [Source](https://towncrier.readthedocs.io/en/stable/index.html)

**X18 — my reading, S2.** Towncrier’s production command stages the generated news file and removes processed fragments with `git rm`, leaving the commit to the user. This makes the combined output a tracked release artifact; deleting consumed inputs would conflict with this project’s retained-entry requirement. [Source](https://towncrier.readthedocs.io/en/stable/tutorial.html#producing-news-files-in-production)

**X19 — quoted, S12.** FKF’s merge procedure starts with “Resolve the conflicts in the topic files only” and ends with “Take its output wholesale as the resolution.” Between those steps it reruns the generator, providing explicit prior art for resolving authoritative inputs first and replacing the conflicted generated index. [Source](https://shll.ai/fab-kit/fkf/#merge-policy-regenerate-never-hand-merge-normative)

**X20 — my reading, S6.** mkdocs-gen-files creates navigation and reference files during documentation builds without writing them into the source documentation directory or requiring them to be versioned. This avoids contributor conflicts on those outputs, but does not itself provide an already-present, clone-readable `INDEX.md`. [Source](https://mkdocstrings.github.io/recipes/#generate-pages-on-the-fly)

**X21 — quoted, S20.** Git warns that the `union` merge driver can leave added lines “in random order” and says the user should verify the result. Combining both branches’ text therefore does not establish canonical ordering or agreement with the authoritative entries. [Source](https://git-scm.com/docs/gitattributes#_built_in_merge_drivers)

**X22 — my reading, S20.** A custom Git merge driver is configured in Git configuration, while `.gitattributes` selects it for paths; the driver receives temporary ancestor/current/other files and writes its result into the current-file argument. A committed attributes file alone does not carry the driver’s executable configuration into a fresh clone. [Source](https://git-scm.com/docs/gitattributes#_defining_a_custom_merge_driver)

**X23 — my reading, S9.** Understory serializes mutations through a promise queue belonging to one `KnowledgeBase` instance. That code supports ordered writes within that instance, but does not establish coordination across separate processes, branches or worktrees. [Source](https://github.com/thecodacus/understory/blob/main/packages/core/src/okf/knowledge-base.ts)

**X24 — my reading, S14.** Claude Code’s native auto memory is machine-local, and worktrees of one repository share its memory directory. It is useful index-format prior art, but its default storage does not satisfy this design’s fresh-clone portability requirement. [Source](https://code.claude.com/docs/en/memory#storage-location)

### 4. Size: when the index outgrows the start-file limit

**X25 — quoted, S14.** Claude Code loads “The first 200 lines of `MEMORY.md`, or the first 25KB, whichever comes first.” An oversized write still succeeds, but returns an error requesting a rewrite, and content beyond the loading limit is omitted next time. [Source](https://code.claude.com/docs/en/memory#how-it-works)

**X26 — my reading, S14.** The documentation explicitly confines that limit to native `MEMORY.md`; it is not documented there as a general limit on every Markdown file an agent opens. Moving detail into topic files reduces index size, but does not eliminate the growth of an index that retains one line for every entry. [Source](https://code.claude.com/docs/en/memory#how-it-works)

**X27 — my reading, S12.** FKF uses a domains-only root index and per-domain file indexes, and applies description limits of 500 characters as guidance and more than 1,000 as a blocking condition. These are that project’s hierarchy and thresholds, not a supported replacement for Rd3’s strictest-agent limit. [Source](https://shll.ai/fab-kit/fkf/)

**X28 — my reading, S8.** Understory summarizes each subdirectory using its recursive concept count, distinct types and up to three example titles, while linking to the directory for detail. This gives a concrete deterministic progressive-disclosure algorithm, but does not enforce an overall byte or line budget. [Source](https://github.com/thecodacus/understory/blob/main/packages/core/src/okf/indexer.ts)

**X29 — quoted, S15.** llms.txt describes its `Optional` section as “links an agent can skip when a shorter context is needed.” The proposal also supports indexes at subpaths and fetching linked detail on demand, establishing selective and hierarchical discovery rather than guaranteed enumeration of every item in one startup file. [Source](https://llmstxt.org/#format)

**X30 — my reading, S5.** miku-indexgen shortens long frontmatter descriptions to 256 UTF-16 code units, including the trailing ellipsis. That bounds one metadata value; its README does not document a total-index budget or an overflow policy preserving all entries. [Source](https://github.com/igapyon/miku-indexgen)

### 5. Checking: whether the index is in step with the entries

**X31 — quoted, S21.** Cog’s maintainers document `--check` as “Check that the files would not change if run again,” with `--diff` to show a failing comparison. This is direct prior art for K6’s regenerate-and-compare freshness check; equality does not independently establish that the extraction algorithm is correct. [Source](https://cog.readthedocs.io/en/latest/running.html#continuous-integration)

**X32 — my reading, S13.** Fab documents a read-only `docs-index --check` returning 0 for clean output, 1 for benign drift or blocking findings, and 2 for destructive loss, with optional JSON diagnostics. Its current command reference identifies `memory-index` as a deprecated alias for `docs-index docs/memory`. [Source](https://shll.ai/fab-kit/commands/#fab-docs-index)

**X33 — my reading, S12.** FKF separately validates malformed frontmatter and offending descriptions because a bad source description can reproduce byte-identically in the generated index. Its maintainers explicitly distinguish source-content validation from generated-output freshness. [Source](https://shll.ai/fab-kit/fkf/#32-description-required-curated)

**X34 — my reading, S3.** Towncrier’s `check` checks whether a feature branch adds a news fragment, and skips that check when the main news file changes. This check was written for fragment-presence policy; it does not establish that the combined file equals current generator output. [Source](https://towncrier.readthedocs.io/en/stable/cli.html#towncrier-check)

**X35 — my reading, S11.** Understory’s validator checks parseable frontmatter and a non-empty type, and warns about missing title/description and certain broken links. The inspected validator does not regenerate indexes or compare their bytes, so its conformance result does not establish index freshness. [Source](https://github.com/thecodacus/understory/blob/main/packages/core/src/okf/validate.ts)

## What I looked for and did not find

- I searched the web and GitHub for generated agent-memory indexes, Markdown frontmatter indexing, fragment aggregation, generated-file merge handling, and freshness checks. I found close components and an explicit memory-index merge policy, but no inspected project implementing this exact combination of `id`, `kind`, body claim, active-only filtering, immediate regeneration and a flat startup index.
- I did not find a comparative benchmark establishing a **best** algorithm under these requirements. Conflict frequency, regeneration latency and agent recall quality were **not measured** in this review.
- I did not find a source-backed rule for extracting this design’s one- or two-sentence body claim while excluding **Why:** and **How to apply:**, preserving its meaning, and rendering one physical line. The closest sources use frontmatter descriptions or generic leading-text extraction.
- I did not find a demonstrated overflow algorithm that retains one line per active entry in a single bounded startup file for an indefinitely growing corpus. Hierarchical indexes and selective loading exist, but change that flat enumeration contract.
- I did not establish the current strictest loading limit across all agents intended to read this project’s `INDEX.md`. Claude’s native memory limit is documented, but X26 limits its applicability.
- I did not find an inspected implementation proving cross-worktree atomicity or consistent snapshots while entries are being changed. Understory’s queue establishes only the narrower scope in X23.
- Some miku-indexgen raw-source requests failed; its findings here rely on its accessible README. A search also surfaced Phoenix issue #1718 about a failed post-merge index update, but the full issue could not be opened, so it is excluded from the findings.

## Gaps and disagreements between sources

- **My reading — no established winner.** The sources support different parts of the problem: miku-indexgen supplies explicit path ordering, Understory supplies write-time regeneration, FKF supplies generated-memory merge handling, and Cog supplies regeneration equality checks. These observations do not constitute comparative proof or a stage-2 proposal.
- **My reading — summary location remains unsettled.** FKF and OKF consume authored frontmatter descriptions; miku-indexgen can derive leading-text summaries. The [accepted design](/home/smoke01/dev/ancient-games/docs/memory-system/SOURCE_OF_TRUTH.md) places the claim in the body, so these are different input contracts, not interchangeable extraction rules.
- **My reading — timing changes the conflict surface.** Towncrier and Changesets defer combined-output generation; Understory regenerates on writes. Deferral avoids frequent contributor edits to the combined artifact, while K6.2 requires regeneration immediately after decisions and facts.
- **My reading — tracking is a material tradeoff.** Build-time virtual indexes avoid tracked-output conflicts, while tracked indexes can be read directly from a clone. The former does not by itself satisfy Rd1.2’s already-readable memory index.
- **My reading — deterministic generation does not prevent textual conflicts.** FKF supplies a regeneration-based resolution procedure. Git’s union merge combines text without establishing the canonical result, and a clean textual merge does not prove freshness.
- **My reading — overflow is still a design question.** Claude truncates oversized native memory, llms.txt permits selective loading, and Understory uses hierarchy. None establishes unchanged compliance with both K6.1’s complete flat listing and Rd3’s bounded startup file.
- **My reading — validation policies differ.** Understory tolerates malformed files during indexing, whereas FKF blocks specified malformed inputs. Neither policy is automatically the missing-field and active-status policy required here.
- **My reading — version distinctions matter.** The inspected OKF specification is 0.2, while Understory identifies and emits 0.1; FKF’s specification uses `memory-index`, while its newer command reference calls it a deprecated alias. Those versions and command names should remain explicit when carrying findings into stage 2.
- **Not measured — verification limits.** External maintainers wrote the checks described above; I inspected their documentation or implementation and did not run them. Freshness equality, schema validity, merge correctness and the truth of an entry’s claim are separate properties, and no inspected check establishes all of them.

## Findings

### 1. Building the lines

- **C1** — Qwen Code builds its team-memory `MEMORY.md` index from the files in a directory, one line per file:
  `- [title](relative path) — description`, where the line is capped and an over-long description is shortened, not
  the link. *Quoted* (S36, `indexer.ts`): `` const link = `- [${title}](${encodeIndexPathTarget(doc.relativePath)})`; ``
  and the comment *"a resolving long link beats a short dead one"*. The cap is `MAX_INDEX_LINE_CHARS = 150`
  (`index-budget.ts`).
- **C2** — Qwen Code sorts that committed index by path with a code-unit comparison and says why: locale-dependent
  order made collaborators rewrite the file back and forth. *Quoted* (S36, `indexer.ts`): *"Code-unit comparison, NOT
  localeCompare: the index is committed and pushed, so its ordering must be byte-identical across machines/locales —
  otherwise two collaborators churn MEMORY.md back and forth and the ff-only sync wedges."* It also orders by path, not
  by modification time: *"docs are ordered by path (not mtime) so the committed file is deterministic across machines
  and does not churn after a git checkout."*
- **C3** — Qwen Code skips the write when the new index is byte-identical to the old one. *Quoted* (S36,
  `indexer.ts`): *"Skip a byte-identical rewrite: regenerating MEMORY.md every run would churn its mtime and produce
  no-op commits that ping-pong between collaborators."*
- **C4** — Qwen Code's team index merges entries whose descriptions are the same after normalising, into one line with
  an "(also: …)" list; the topic files are kept. *Quoted* (S36, `indexer.ts`): *"When two people save the same shared
  fact, collapsing them into one index line — listing the other files via "(also: …)" — keeps the index readable. The
  topic files themselves are never removed"*, and the match is *"Conservative (normalized-exact, not fuzzy) so two
  genuinely different facts are never silently merged."*
- **C5** — mdsmith generates an index from the front matter of files matching a glob, one row per file, with a row
  template, a `where` filter and a sort key; the default is one link per file sorted by path. *Quoted* (S8,
  generating-content.md): *"outputs `- [<basename>](<path>)` per file, sorted by path"*; `row: "| {id} |
  [{title}]({filename}) |"`; *"The filter runs after globbing and front matter parsing, but before sort and render."*
- **C6** — mdsmith's sort rule handles numeric ids and missing fields explicitly. *Quoted* (S8): *"Format:
  `[-][numeric:]KEY`. … Missing values sort as empty string."*; the `numeric:` prefix exists because ids
  *"would otherwise collate lexicographically (`100` before `52`)"*. If any value is not an integer it *"falls back to
  string compare for all entries — no error is raised"*. Gitignored files are excluded by default (*"files matched by
  `.gitignore` rules are excluded from catalog results"*).
- **C7** — mdsmith presents the same catalog as an index for coding agents, one summary line per document. *Quoted*
  (S8, progressive-disclosure.md): *"A `<?catalog?>` in the agent file keeps one `summary` line per tracked doc. The
  agent skims the index, then opens only the files a task touches."*
- **C8** — adr-tools builds its table of contents by listing files whose names start with a number, sorting the list
  with `sort`, taking each title from the file's first line, and writing one bullet per file. *Quoted* (S9, code):
  `find $adr_dir | grep -E "^$adr_dir/[0-9]+-[^/]*\\.md" | sort`; `head -1 … | cut -c 3-`;
  `echo "* [$title]($link)"`.
- **C9** — *My reading* (S9 with S29): adr-tools calls `sort` with no `LC_ALL=C`, so its order can change with the
  machine's locale — the failure S29 warns about and that C2 reports Qwen Code hitting.
- **C10** — adr-log writes one line per ADR, either to stdout, to a new `index.md`, or between markers in an existing
  file. *Quoted* (S10): `* [ADR-0000](0000-example-1.md) - Example 1`; *"Edit the <input> file directly, injecting the
  log at <!-- adrlog -->."*
- **C11** — Claude Code's auto memory keeps an index file with one line per memory file, but Claude writes it; it is
  not generated by a program. *Quoted* (S1): *"`MEMORY.md` # Index, one line per memory, loaded into every session"*;
  *"Claude keeps `MEMORY.md` concise by moving detailed notes into separate topic files."*
- **C12** — llms.txt, an index file written for LLMs, fixes a line format of one Markdown link with optional notes.
  *Quoted* (S6): *"Each "file list" is a markdown list, containing a required markdown hyperlink `[name](url)`, then
  optionally a `:` and notes about the file."*
- **C13** — Karpathy's LLM Wiki keeps an `index.md` of one-line summaries that the LLM updates, not a script.
  *Quoted* (S7): *"each page listed with a link, a one-line summary"*, optional metadata *"like date or source
  count"*, and *"The LLM updates it on every ingest."*
- **C14** — Directory listing order is not stable and sort order depends on locale; the fix is an explicit
  locale-free sort. *Quoted* (S29): *"Most filesystems do not guarantee that listing files in a directory always
  results in the same order"*; *"Different locales have different orders of e.g. uppercase characters relative to
  lowercase characters"*; its example pipes through `LC_ALL=C sort -z`.
- **C15** — A build time written into output breaks reproducibility; a date, if needed, should come from version
  control. *Quoted* (S30): *"Timestamps make the biggest source of reproducibility issues"*; *"it's best to extract
  such a date from the revision control system or from a changelog."*
- **C16** — blurb names each fragment so that sorting file names sorts entries by time and names do not collide.
  *Quoted* (S13): `Misc/NEWS.d/next/<section>/<datetime>.gh-issue-<issue_number>.<nonce>.rst`; the nonce is the first
  6 characters of a base64 MD5 of the text; this means *"All entries in `Misc/NEWS` will be sorted by time"* and a
  filename clash is *"unthinkably unlikely"*.
- **C17** — reno orders notes by a topological walk of git history, which it calls deterministic but not
  predictable. *Quoted* (S16 usage, via WebFetch): *"deterministic, but not necessarily predictable or mutable"*; the
  design page states the goal *"we do want the ordering to be predictable and consistent."*
- **C18** — towncrier names a fragment by an issue id and a type, and groups output by type in a fixed category order;
  the tutorial states no sort rule inside a category. *Quoted* (S12): *"the filename consists of the issue/ticket ID
  (or some other unique identifier) as well as the ‘type’."*
- **C19** — Tools that must fit a budget rank by importance instead of by id: Repomix sorts by git change frequency by
  default, and Aider ranks files on a graph and keeps what fits. *Quoted* (S32): `--no-git-sort-by-changes` *"Don't
  sort files by git change frequency (default: most changed files first)"*; (S31) *"selecting the most important parts
  of the codebase which will fit into the active token budget."*
- **C20** — Go's convention marks a generated file with a header line that tools can match. *Quoted* (S26):
  `^// Code generated .* DO NOT EDIT\.$`, which *"must appear before the first non-comment, non-blank text in the
  file."*
- **C21** — Cog detects hand edits to generated output with a checksum and refuses to overwrite them. *Quoted* (S24):
  *"If the generated code is edited by a misguided developer, the next time cog is run, the checksum won't match, and
  cog will stop to avoid overwriting the edited output."*

### 2. When it runs and what runs it

- **C22** — Qwen Code regenerates the team index when a memory is written and, with sync turned on, at session start
  before pulling and committing. *Quoted* (S35): *"at session start Qwen best-effort syncs the `.qwen/team-memory/`
  directory: it rebuilds the shared `MEMORY.md` index, fast-forward-pulls collaborators' updates **first**, then
  commits your team-memory changes on top, and pushes **only that sync commit**"*. The write path calls
  `rebuildTeamAutoMemoryIndex` when `params.scope === 'team'` (S36, `metadata-migration.ts` line ~620, *quoted*).
  Sync is *"Off by default."*
- **C23** — Generators run at release, at one serial point, rather than on every branch: towncrier, Changesets,
  blurb, and GitLab's old YAML process. *Quoted*: towncrier *"will remove the news files (with `git rm`) and append the
  built news … and then stage the news file changes"* and *"leaves committing the changes up to the user"* (S12);
  `changeset version` *"consumes all changesets"* (S18); blurb's `Misc/NEWS` is *"rendered on demand (e.g. when
  building a release)"* (S13); GitLab *"collect those files, compile them to Markdown, remove them from the stable
  branch"* (S14).
- **C24** — mdsmith regenerates on `mdsmith fix`, reports staleness on `mdsmith check`, and can run the fix in a
  `pre-merge-commit` hook. *Quoted* (S8): *"Both regenerate their body on `mdsmith fix` and flag stale content on
  `mdsmith check`"*; *"`mdsmith pre-merge-commit install` adds a hook that runs `mdsmith fix` after a merge and
  re-stages the `.md` files."*
- **C25** — Go never runs its generators as part of a build; generation is explicit and the result is committed.
  *Quoted* (S26): *"Go generate is never run automatically by go build, go test, and so on. It must be run
  explicitly."* (That the output is committed is *my reading* of this sentence: a `go build` from a clone must work
  without running the generator.)
- **C26** — pre-commit fails a hook that changes files, which makes a generator in a pre-commit hook force the
  regenerated file into the commit; it also offers `post-merge` and `post-checkout` stages and a CI run over all files.
  *Quoted* (S25): *"The hook must exit nonzero on failure or modify files"*; output *"Files were modified by this
  hook"*; post-merge/post-checkout hooks *"must be set as `always_run: true` or they will always be skipped"*;
  *"adding `pre-commit run --all-files` as a CI step will ensure everything stays in tip-top shape."*
- **C27** — Claude Code's SessionStart hook adds a script's stdout to the context, on startup, resume, clear, compact
  and fork. *Quoted* (S2): *"Claude Code adds a SessionStart hook's plain-text stdout to Claude's context."* *My
  reading:* generating the index at session start from a hook would never put a generated file in git, but see C44
  for the hook's size cap.
- **C28** — Claude Code loads imported files at launch: an `@path` import in `CLAUDE.md` is a way to put a file in
  the start context. *Quoted* (S1): *"Imports … don't reduce its context cost, because imported files also load at
  launch."*
- **C29** — Codex and Gemini CLI load fixed instruction files by concatenation; neither page documents loading some
  other file such as an index on its own. *Quoted*: Codex *"concatenates files from the root down, joining them with
  blank lines"* (S3); Gemini CLI *"concatenates the contents of all found files, and sends them to the model with every
  prompt"* (S4). *My reading:* for those agents, `INDEX.md` reaches session start only through an instruction, an
  import, or a hook.
- **C30** — log4brains builds its ADR site in CI and publishes it, taking some metadata from git. *Quoted* (S11):
  *"publish them automatically as a static website"*; *"ADR metadata automatically guessed from its raw text and git
  logs"*.

### 3. Git: committed or not, and parallel branches

- **C31** — The shared generated file in the open-source world first broke on parallel branches, and the fix was one
  file per entry. *Quoted* (S14): *"we'd constantly see merge conflicts in the changelog when multiple merge requests
  attempted to add an entry to the list"*; placeholder lines left *"The problem was lessened, but not solved"*; the fix
  was *"Each changelog entry would be its own YAML file in a `CHANGELOG/unreleased` folder."* blurb exists to *"rid
  CPython core development of the scourge of `Misc/NEWS` conflicts"* (S13).
- **C32** — CPython stopped committing the combined file. *Quoted* (S13): *"`Misc/NEWS` could be deleted from the
  CPython repo and thereafter rendered on demand"*. *My reading* of the directory listing (S13, 2026-10-12):
  `python/cpython` `Misc/` holds `NEWS.d` and no `NEWS`.
- **C33** — GitLab later dropped entry files altogether and generates the changelog from a commit trailer; the docs
  give no reason for the change. *Quoted* (S15): *"Each list item, or **entry**, in our CHANGELOG.md file is generated
  from the subject line of a Git commit."*
- **C34** — Qwen Code commits its generated team index, and avoids merges by only fast-forwarding: a branch that has
  diverged is left alone. *Quoted* (S36, `team-memory-sync.ts`): *"`--ff-only` never creates a merge commit or a
  conflict; a diverged branch is left untouched and surfaced as `pull-failed`."* (S35): *"A diverged branch is left
  untouched … sync simply does nothing that session; resolve the divergence (`git pull`) and it resumes."* Neither
  source says what happens to `MEMORY.md` when a person merges two diverged branches by hand.
- **C35** — git's built-in `union` driver keeps lines from both sides without conflict markers, and git warns about
  it. *Quoted* (S19): *"take lines from both versions, instead of leaving conflict markers. This tends to leave the
  added lines in the resulting file in random order and the user should verify the result. Do not use this if you do
  not understand the implications."*
- **C36** — `union` silently brings back removed lines. *Quoted* (S20): *"if one side removes a line and the other adds
  in the same place, it will re-add the removed line"*; *"This will happen silently without warning, without any merge
  conflict being reported."* *My reading:* for `INDEX.md` a line disappears when an entry is superseded, so `union`
  could put a superseded entry back as active — the case K6 says must fail.
- **C37** — A custom merge driver is defined in git config, not in `.gitattributes`, so a fresh clone does not have it
  until something installs it. *Quoted* (S19): *"The definition of a merge driver is done in the `.git/config` file,
  not in the `gitattributes` file"*; the driver *"is expected to leave the result of the merge in the file named with
  `%A` … and exit with zero status if it managed to merge them cleanly"*. mdsmith says the same of its own install:
  *"Both are git-internal and untracked"* (S8). gh-aw removed a `merge=ours` line because without config it did
  nothing: *"`merge=ours` is not a built-in git merge driver — without `merge.ours.driver` configured it is inert,
  falsely implying generated-file conflicts are auto-resolved."* (S21).
- **C38** — mdsmith's merge driver resolves a conflict in a generated block by regenerating it. *Quoted* (S8): *"On a
  conflict it re-runs the directive and keeps the regenerated body, so the conflict never reaches you"*; it *"strips
  conflict markers in those blocks and runs `mdsmith fix` to regenerate them. It exits non-zero if any unresolved
  conflict markers remain."* In CI and merge queues it uses `ci-install`, which checks the committed `.gitattributes`
  and *"never writes the tracked file"*.
- **C39** — npm resolves a lockfile conflict by regenerating the lockfile, and commits the lockfile. *Quoted* (S22
  v10): *"This file is intended to be committed into source repositories"*. (S22 v6, *my summary* — the fetch tool
  would not return the section verbatim): since npm 5.7.0, fix `package.json` conflicts by hand and run `npm install`
  again, and npm writes a merged lockfile; `npm-merge-driver` automates this in git; one short quote: *"you will have
  to resolve that by hand and run `npm install` manually, even with the merge driver."*
- **C40** — Random or hash ids in file names keep parallel branches from creating the same file name. *Quoted*:
  reno identifies each note by *"the unique identifier (a 16-character hexadecimal SHA) embedded in its filename"*
  (S16); blurb's nonce (C16); Beads: *"Hash-based IDs (`bd-a1b2`) prevent merge collisions in
  multi-agent/multi-branch workflows."* (S33); log4brains: *"No required file numbering schema (i.e., `adr-0001.md`,
  `adr-0002.md`...): avoids git merge issues"* (S11).
- **C41** — GitHub can mark a committed generated file so its diff is collapsed. *Quoted* (S27): matching paths are
  *"ignored for the repository's language statistics and hidden by default in diffs."* gh-aw writes
  `.github/workflows/*.lock.yml linguist-generated=true` for its committed generated files (S21, *quoted*).
- **C42** — A merge queue checks each pull request against the base branch plus the pull requests ahead of it, so a
  check runs on the result that will actually land. *Quoted* (S28): changes are *"grouped into a `merge_group` with
  the latest version of the `base_branch`"* and *"changes from pull requests ahead of it in the queue"*, for
  *"ensuring the branch is never broken by incompatible changes."* *My reading:* this is where a "regenerate and
  compare" check would catch two branches that each merged cleanly but left `INDEX.md` out of step.
- **C43** — Two tools that started from files in git moved state elsewhere, keeping files as an export or a rebuildable
  index. *Quoted*: Beads' `.beads/issues.jsonl` *"is an export for viewers and interchange, not the source of truth or
  a backup"*, with Dolt's *"cell-level merge"* now underneath (S33); ai-memory: *"The database is a derived index that
  can always be rebuilt from the files."* (S34). reno added a cache file for copies without git history: *"a reno
  cache file that can be used to build release notes documents without the full Git history present"* (S17).

### 4. Size

- **C44** — Claude Code's SessionStart hook output is capped at 10,000 characters, with no setting to raise it; past
  that, only a 2,000-character preview reaches the context. *Quoted* (S2): *"capped at 10,000 characters"*; *"Claude
  Code saves the output to a file in the session directory and replaces it with the file path and a preview of up to
  the first 2,000 characters"*; *"Claude Code doesn't ask Claude to read the file, so keep anything Claude must always
  see within the cap"*; *"this cap has no setting or environment variable to raise it."*
- **C45** — Claude Code loads the first 200 lines or 25 KB of `MEMORY.md`, warns when the file is near the limit, and
  errors when it is over; that limit is for `MEMORY.md` only. *Quoted* (S1): *"The first 200 lines of `MEMORY.md`, or
  the first 25KB, whichever comes first, are loaded"*; near a limit it reminds Claude to *"keep one line per entry,
  move detail into topic files, and merge or drop stale entries"*; over it, *"everything past the limit is dropped on
  the next load"*; *"This limit applies only to `MEMORY.md`. Claude Code loads a CLAUDE.md file of up to 4 MiB in full
  and skips a larger file."* Guidance for CLAUDE.md: *"target under 200 lines per CLAUDE.md file."*
- **C46** — Qwen Code caps its generated index at 200 lines and 25,000 UTF-16 code units; under pressure it keeps
  short entries first, keeps the original order, drops whole lines, and appends a warning. *Quoted* (S35): *"Its
  generated body and the portion loaded into prompts share a limit of 200 lines and 25,000 UTF-16 code units"*;
  *"complete ordinary entries (up to 150 code units) get space before longer entries, and retained entries keep their
  original order. An entry that cannot fit is skipped whole, so its Markdown link is never cut in the middle."* (S36,
  `index-budget.ts`): the warning text is *"> WARNING: MEMORY.md is too large; only part of it was written. Keep index
  entries concise and move detail into topic files."*
- **C47** — Qwen Code also offers a structured mode that replaces the flat index with a tree and loads only the
  relevant subtree. *Quoted* (S35): *"The structured protocol replaces that with a hierarchical memory tree, injects
  only the subtree relevant to your current request, and gives Qwen a `search_memory` tool to pull full entries on
  demand"*.
- **C48** — Codex stops adding instruction files at 32 KiB by default; the limit is configurable. *Quoted* (S3):
  *"(32 KiB by default)"*; Codex *"stops adding files once the combined size reaches the limit defined by
  `project_doc_max_bytes`."* The page does not say whether a file that partly fits is cut.
- **C49** — Gemini CLI and the AGENTS.md page state no size limit for context files. *Found nothing* (S4, S5).
- **C50** — llms.txt keeps the file small by pushing detail behind links, and marks a section agents may drop.
  *Quoted* (S6): *"The file itself stays small enough to fit in context. The detail lives behind the links"*; the
  "Optional" section holds *"links an agent can skip when a shorter context is needed."* No byte or token limit is
  given.
- **C51** — Karpathy reports the single index working only at moderate scale. *Quoted* (S7): it *"works surprisingly
  well at moderate scale (~100 sources, ~hundreds of pages)"*.
- **C52** — mdsmith caps the number of files a catalog reads and, over the cap, leaves the old output instead of
  writing a partial one; it also checks file length and token budget. *Quoted* (S8): *"A `<?catalog?>` directive
  matches at most 10,000 files. When the glob resolves more than that limit, mdsmith emits a diagnostic and leaves the
  generated section unchanged"*; default rules `max-file-length` *"`max: 300` lines"* and `token-budget` *"`max:
  8000`, `mode: heuristic`"*.
- **C53** — When a combined file is too big, Repomix splits it into numbered parts on directory boundaries, and Aider
  keeps the top-ranked parts within a token budget. *Quoted* (S32): *"Split output into multiple numbered files"*;
  *"A single file or directory will never be split across multiple output files."* (S31): `--map-tokens` *"defaults to
  1k tokens"*, and the map *"will usually stay within that setting's value"*.

### 5. Checking that the index is in step

- **C54** — Kubernetes checks generated files by regenerating them in a clean git worktree of HEAD and failing if
  `git status` shows any change. *Quoted* (S23, code): `git worktree add -f -q "${_tmpdir}" HEAD`; `"$@"`;
  `diffs=$(git status --porcelain | wc -l)`; `if [[ ${diffs} -gt 0 ]]; then … git diff >&2 … return 1`. The comment:
  *"This function verifies whether generated files are up-to-date."*
- **C55** — Cog has a check mode that reports whether a run would change any file, and a diff option. *Quoted* (S24):
  *"use the `--check` option to run cog just to check that the files would not change if run again"*; *"The `--diff`
  option will show a unified diff of the change that caused `--check` to fail."* The page states no exit status.
- **C56** — mdsmith's `check` reports a stale generated block, and its `ci-install` fails when the committed
  `.gitattributes` has drifted. *Quoted* (S8): *"`mdsmith check` flags the index when it drifts; `mdsmith fix`
  rebuilds it"*; `ci-install` *"exits non-zero when `.gitattributes` is missing, has no managed block, or has
  drifted."*
- **C57** — Changesets and towncrier check that a branch added a fragment, not that a combined file is current.
  *Quoted*: `changeset status` exits `1` when *"there are changes to packages but no changesets are present"* (S18);
  towncrier check *"compares the current branch against `origin/main`"* (S12). *My reading:* this is a different
  check from K6's "regenerating changes nothing".
- **C58** — Claude Code checks the index's size at every write. *Quoted* (S1): *"After Claude writes to `MEMORY.md`,
  Claude Code measures the file against the 200-line and 25KB read limits."*

## Gaps and disagreements between sources

- **Commit the combined file, or not.** Qwen Code (C34), npm (C39), Go (C25) and gh-aw (C41) commit generated output;
  CPython (C32), log4brains (C30) and GitLab today (C33) do not, and build it on demand or at release. Towncrier and
  Changesets (C23) commit it, but only at release, so working branches never touch it.
- **What to do when two branches meet.** Three answers, each from a different source: avoid the merge
  (Qwen Code, fast-forward only, C34); regenerate inside the merge (mdsmith, C38; npm, C39); or take both sides
  (`union`, C35), which the git manual and a bug report warn against (C35, C36). The merge-driver answer depends on
  per-clone config that a fresh clone lacks (C37).
- **Order.** Qwen Code and mdsmith sort by path with a locale-free or explicit comparison (C2, C5); adr-tools uses
  locale-dependent `sort` (C8, C9); blurb sorts by a time stamp in the file name (C16); reno by git topology (C17);
  Repomix and Aider by importance (C19). Sorting by importance and truncating fits a budget; sorting by path keeps the
  file byte-stable. No source does both.
- **Size limits differ by agent and by how the file is loaded.** Claude Code: 200 lines / 25 KB for `MEMORY.md`, but
  4 MiB for a CLAUDE.md and its imports, and 10,000 characters for SessionStart hook output (C44, C45). Qwen Code:
  200 lines / 25,000 UTF-16 code units (C46). Codex: 32 KiB across all instruction files (C48). Gemini CLI and
  AGENTS.md: none stated (C49). *My reading:* the "strictest limit" of Rd3 depends on which load path is chosen, not
  only on which agents read the file.
- **What to do when the index is too big.** Qwen Code drops whole lines, short ones first, and warns (C46); Claude
  Code errors and asks for a rewrite (C45); mdsmith refuses to write a partial result (C52); Codex stops adding files
  (C48); Repomix splits (C53); llms.txt and Qwen's structured mode move detail behind links or a tree (C47, C50).
- **Who writes the index.** Claude Code's `MEMORY.md` (C11) and Karpathy's `index.md` (C13) are written by the model;
  Qwen Code's (C1) and mdsmith's (C5) are generated by code. Only the generated ones can be checked by regenerating
  (C54–C56).
- **Source quality.** mdsmith (21 stars) and ai-memory are small projects; Qwen Code's team memory is off by default
  (C22) and n is unknown for how often it is used. The vendor limits (S1, S2, S3, S35) are documented behaviour, not
  measured by me.

## Findings

### 1. Building the lines — what is read, what is written, the order, and stability

**O1** — The dominant prior-art shape is *injecting a delimited region into a hand-written file*, not writing a whole separate file. Both tools I read mark the generated region with HTML comments: doctoc — "The pragma is the opening and closing comment blocks to mark the location of the doctoc contents, i.e. `<!-- START doctoc ... -->`"; terraform-docs ships this as its default `output.template`: `<!-- BEGIN_TF_DOCS -->` / `{{ .Content }}` / `<!-- END_TF_DOCS -->`, with `mode: inject`. **quoted** [S9, S11]

**O2** — The marker doubles as the machine-readable "do not hand-edit" rule, written into the file itself. doctoc emits, inside the region: `<!-- DON'T EDIT THIS SECTION, INSTEAD RE-RUN doctoc TO UPDATE -->`. **quoted** [S9]

**O3** — Two escape hatches exist for individual files: an explicit skip marker (`just add <!-- DOCTOC SKIP --> to the top of the file you wish to ignore`) and a configurable insertion marker (mdbook-toc's `marker`, default `<!-- toc -->`, with GitLab and GitHub markers supported). **quoted** [S9, S10]

**O4** — Order is a declared, versioned configuration value in real tools, not an accident of directory traversal: terraform-docs' config carries `sort:` / `enabled: true` / `by: name`. **quoted** [S11] · **my reading**: if the order is left unspecified, the same set of files can yield two different files after an unrelated filesystem change, which breaks any "regenerate and diff" check [S12].

**O5** — Bit-for-bit stability of a generated artifact is a named, defined property with a named verification method, not an aspiration. Reproducible Builds: "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts" and "The reproducibility of artifacts is verified by bit-by-bit comparison." **quoted** [S22] · **my reading**: `K6.1`'s "never edited by hand" is the weaker half of this; the stronger half, that the generator is a pure function of `entries/`, is what makes `K6`'s "Fails if regenerating `INDEX.md` changes it" a usable check.

**O6** — The specific way sorting breaks determinism is collation order. Reproducible Builds, on locale: "tools which output is influenced by the current locale can make locale a source of reproducibility issues"; "Common sorting functions are affected by the `LC_COLLATE` environment variable, which can be overridden by `LC_ALL`. Some locales can be quite surprising" — demonstrated with `LC_ALL=fr_FR.UTF-8 sort` yielding `a B c` and `LC_ALL=C sort` yielding `B a c`, because "The C locale will sort according to the byte values and is always available". **quoted** [S23] · **my reading**: this is the failure that turns a "check" into a false alarm, and no tool I read pins locale.

**O7** — The same page names the other three volatile inputs a generator must not absorb: time format (`LC_TIME`), default character encoding (`LC_CTYPE`), and system timezone/`TZ`. **quoted** [S23] · **my reading**: an index that embeds a generation timestamp or a "generated at" line is non-deterministic by construction.

**O8** — There is a direct format precedent for "one line per item, with a short label": llms.txt's file list is "a markdown list, containing a required markdown hyperlink `[name](url)`, then optionally a `:` and notes about the file." **quoted** [S16] · **my reading**: `K6.1`'s "id, kind and one-line claim" is the same shape with a link replaced by an id.

**O9** — The agent-facing index standard states the size property of the index file explicitly, and locates the detail elsewhere: "Agents are expected to view or search llms.txt to find the information they need, then follow the relevant links… **The file itself stays small enough to fit in context. The detail lives behind the links, and is fetched only when needed.**" **quoted** [S16]

**O10** — Treating the header as a machine-readable contract is universal across agent tools, which is what lets a generator rely on it. Cursor: "Each rule is an `.mdc` file… A plain `.md` file in `.cursor/rules` is ignored by the rules system because it has no frontmatter to specify `description`, `globs`, and `alwaysApply`." Agent Skills require YAML frontmatter with `name` and `description`. **quoted** [S18, S20] · **my reading**: `W1.2`'s field list is the same kind of contract, but unlike these tools nothing in the design currently *validates* it — see O42.

**O11** — The closest tool I found to "generate a table of one line per source item from parsed attributes" is terraform-docs, which renders per-item rows for inputs, outputs, modules, providers, requirements and resources through named template variables (`{{ .Inputs }}`, `{{ .Outputs }}`, …). **quoted** [S11] · **my reading**: its input is code, not markdown files with headers; I did not find a tool that does the latter (see "did not find" §1).

### 2. When it runs and what runs it

**O12** — The in-repo, no-service trigger is the git hook. `pre-commit`: "This hook is invoked by `git commit`, and can be bypassed with the `--no-verify` option… Exiting with a non-zero status from this script causes the `git commit` command to abort before creating a commit." **quoted** [S4]

**O13** — The catch that makes hook-only designs fragile: hooks live outside version control. `githooks(5)`: "By default the hooks directory is `$GIT_DIR/hooks`, but that can be changed via the `core.hooksPath` configuration variable." Pro Git is blunter: "**It's important to note that client-side hooks are not copied when you clone a repository.** If your intent with these scripts is to enforce a policy, you'll probably want to do that on the server side". **quoted** [S4, S8]

**O14** — The established fix for O13 is a hook manager whose configuration is a committed file. Lefthook: "A Git hooks manager for Node.js, Ruby, Python and many other types of projects… Configure your hooks, install them once and forget about it: rely on the magic underneath", with the config in a committed `lefthook.yml` and activation by `lefthook install`. Both tools I read ship a literal in-repo pre-commit block as the documented install path (doctoc and terraform-docs). **quoted** [S9, S11, S24] · **my reading**: I did not verify in Lefthook's README how it points git at the committed scripts; `core.hooksPath` [S4] is git's own mechanism for that and I did not confirm Lefthook's use of it from the page I read.

**O15** — "At merge" has a native hook with exactly one limitation that matters here. `post-merge`: "This hook is invoked by `git merge`, which happens when a `git pull` is done on a local repository… This hook cannot affect the outcome of `git merge` and is not executed, if the merge failed due to conflicts." **quoted** [S4] · **my reading**: a `post-merge` regeneration is skipped on precisely the conflicted merges where the shared generated file is most likely stale, so `post-merge` cannot be the only trigger.

**O16** — `post-checkout` has broader reach: it fires on `git checkout`/`git switch`, and "It is also run after `git clone`, unless the `--no-checkout` (`-n`) option is used", and likewise for `git worktree add`. **quoted** [S4] · **my reading**: given W6.2 (each agent on its own branch or worktree), this is the one git hook that fires for every kind of branch movement in this design, and it is the only one that also fires on a fresh clone.

**O17** — "At session start" is a first-class, agent-side trigger point. Claude Code's `SessionStart` event: "When a session begins or resumes", with matcher values `startup`, `resume`, `clear`, `compact`, `fork`. The same doc's worked example for "a linting script only when Claude writes or edits a file" uses `PostToolUse` with `matcher: "Edit|Write"` — which is the shape of `K6.2`'s "regenerated right after any decision or fact is written". **quoted** [S2] · **my reading**: `PostToolUse`/`Write|Edit` + a path filter is the mechanism that matches K6.2 most literally, and it fires in worktrees because hooks run with `cwd` following the session [S2].

**O18** — There is a hook that fires *when an instruction file is loaded into context*, which is the exact moment Rd2.1 cares about: `InstructionsLoaded` — "When a CLAUDE.md or `.claude/rules/*.md` file is loaded into context. Fires at session start and when files are lazily loaded during a session", matcher values `session_start`, `nested_traversal`, `path_glob_match`, `include`, `compact`. **quoted** [S2]

**O19** — The vendor's own position is that a hook, not an instruction, is what guarantees a start-of-session read: "Hooks run scripts automatically at specific points in Claude's workflow. Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." **quoted** [S1] · **my reading**: this is external support for the design's premise in Rd2.1 that "agents skip optional reads", and against `AGENTS.md` text alone as the enforcement mechanism.

**O20** — In CI the common pattern for a committed generated file is to *push the regeneration back onto the PR branch* rather than fail. terraform-docs' documented GitHub Actions workflow: `on: - pull_request`, `output-method: inject`, `git-push: "true"`. **quoted** [S11]

**O21** — Read-time generation is also a supported mode, and a real one: mdbook-toc is an mdBook preprocessor, so the index is produced by `mdbook path/to/book` at build time, not at commit time; doctoc additionally offers `-s/--stdout` and `--dryrun`. **quoted** [S9, S10] · **my reading**: read-time generation is incompatible with `Rd1.2` (fresh clone, no cache) and with `Rd2.1` (every agent reads a file at session start).

### 3. Git — committed or not, and parallel branches

**O22** — Generated files are conventionally *marked* so review tooling collapses them. Linguist: `linguist-generated` → "Excluded from stats, hidden in diffs", and "unlike vendored and documentation files, these files are suppressed in diffs". GitHub Docs: "you can mark them with the `linguist-generated` attribute in a `.gitattributes` file… to mark or unmark paths that you would like to be ignored for the repository's language statistics and hidden by default in diffs". **quoted** [S14, S15]

**O23** — Git already ships merge semantics for "a file that cannot be line-merged". The built-in `binary` driver: "Keep the version from your branch in the work tree, but leave the path in the conflicted state for the user to sort out. This is suitable for binary files that do not have a well-defined merge semantics." Setting the `merge` attribute unset gives: "Take the version from the current branch as the tentative merge result, and declare that the merge has conflicts." **quoted** [S5] · **my reading**: "take one side, mark the path unresolved, regenerate" is already a coherent git-native policy; the design's `INDEX.md` is a candidate for `merge=binary`.

**O24** — The opposite driver is documented as unsafe for exactly this case. `union`: "Run 3-way file level merge for text files, but take lines from both versions, instead of leaving conflict markers. **This tends to leave the added lines in the resulting file in random order and the user should verify the result.**" **quoted** [S5] · **my reading**: a union merge on a generated index preserves deleted entries as stale lines and can reorder them, so it turns a mechanical problem into a silent-correctness one — the opposite of K6's "Fails if".

**O25** — The commit-or-not decision has a documented rule of thumb from a project with the same shape of problem (a machine-written file that must be readable from a clone). Cargo: "Cargo.lock contains exact information about your dependencies. **It is maintained by Cargo and should not be manually edited.**" and "**When in doubt, check Cargo.lock into the version control system (e.g. Git).**" **quoted** [S21] · **my reading**: `Rd1.2` (a fresh clone can read it, no cache) forces the commit side of this trade-off; the cost is exactly the merge handling in O23–O24.

**O26** — Repeated identical conflicts can be *learned* rather than resolved by hand: `git rerere` "assists the developer in this process by recording conflicted automerge results and corresponding hand resolve results on the initial manual merge, and applying previously recorded hand resolutions to their corresponding automerge results", and `git merge` "automatically invokes `git rerere` upon exiting with a failed automerge". **quoted** [S6] · **my reading**: this is what makes "resolve by regenerating" affordable across many parallel branches touching the index the same way. Its stated limit: "'git rerere' relies on the conflict markers in the file to detect the conflict."

**O27** — Git explicitly forbids the obvious shortcut of hiding local edits to a tracked file. `git update-index(1)`: "**Users often try to use the assume-unchanged and skip-worktree bits to tell Git to ignore changes to files that are tracked. This does not work as expected**, since Git may still check working tree files against the index when performing certain operations. **In general, Git does not provide a way to ignore changes to tracked files, so alternate solutions are recommended.**" And on `--assume-unchanged`: "Git will fail (gracefully) in case it needs to modify this file in the index e.g. when merging in a commit". **quoted** [S7]

**O28** — If the index is produced *by a git filter* rather than committed directly, git has a setting for the resulting spurious conflicts: "by setting the `merge.renormalize` configuration variable… Git can be told to run a virtual check-out and check-in of all three stages of each file that needs a three-way content merge… **This prevents changes caused by check-in conversion from causing spurious merge conflicts** when a converted file is merged with an unconverted file." **quoted** [S5] · **my reading**: the design says nothing about a clean/smudge filter for `INDEX.md`; this is the documented cost of that route if stage 2 picks it.

**O29** — `.gitattributes` is the only per-path, versioned, in-repo mechanism git provides for file behaviour, and it is designed to be shared: "Attributes which should be version-controlled and distributed to other repositories (i.e., attributes of interest to all users) should go into `.gitattributes` files." **quoted** [S5] · **my reading**: whatever git-side policy is chosen for `INDEX.md` (O22, O23, O28) is expressed there, so it is itself subject to merge — but a one-file attributes entry is a far smaller conflict surface than the index body.

### 4. Size — what happens when the index outgrows the start-file limit

**O30** — The published size ceiling for a start-of-session instruction file is **lines**, and the strictest one I found is Claude Code's: "**Aim to keep CLAUDE.md under 200 lines by including only essentials.**" **quoted** [S3] · **my reading**: this is a primary-source corroboration of the 200-line figure in `Rd3.1`'s example, and it is the number `INDEX.md` would have to clear.

**O31** — The failure mode of overshooting is silent degradation, not an error. Anthropic: "**Bloated CLAUDE.md files cause Claude to ignore your actual instructions!**" and "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." Elsewhere on the same page: "If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise." **quoted** [S1]

**O32** — The vendor's own remedy for an oversized checked-in file is *pruning by a tool*, not splitting: "For a checked-in CLAUDE.md, run `/doctor` and Claude proposes cuts for content it can derive from the codebase." With the test to apply: "Keep it concise. For each line, ask: *'Would removing this cause Claude to make mistakes?'* If not, cut it." **quoted** [S1] · **my reading**: for a generated file, "cut it" is a change to the generator's rules (drop `covers`, shorten claims), which is a cheap response to `Rd3.1` — no structural change to `K6.1`.

**O33** — Cursor's ceiling is the same unit but larger, and it prescribes the other response — split and scope: "Keep rules under 500 lines / Split large rules into multiple, composable rules / Provide concrete examples or referenced files / … Reference files instead of copying their contents. This keeps rules short and prevents them from becoming stale as code changes." **quoted** [S20] · **my reading**: among the agents whose docs I read, 200 lines (Claude Code) is stricter than 500 lines (Cursor `.cursor/rules`), so `Rd3.1`'s "strictest limit" is the Claude Code figure on current published docs.

**O34** — The general pattern for "a file that must not grow past a budget" is progressive disclosure with a tiny always-loaded part. Agent Skills: "This filesystem-based architecture enables **progressive disclosure**: Claude loads information in stages as needed, rather than consuming context upfront", with the table giving Level 1 metadata "~100 tokens per Skill", Level 2 instructions "Under 5k tokens", Level 3 "None until accessed", and the conclusion "Progressive disclosure ensures only relevant content occupies the context window at any given time." **quoted** [S18] · **my reading**: the design's `INDEX.md` line is exactly Level 1 and the entry body is Level 2/3 — the design is already shaped like this; what is missing is any stated budget for the line.

**O35** — The other budgeted-index answer is *rank and select*, not truncate. aider: "Of course, for large repositories even just the repo map might be too large for the LLM's context window. Aider solves this problem by sending just the most relevant portions of the repo map… Aider optimizes the repo map by **selecting the most important parts of the codebase which will fit into the active token budget**", governed by `--map-tokens`, "which defaults to 1k tokens". **quoted** [S17] · **my reading**: selection needs a relevance signal, and the design already has three candidates in every header — `kind`, `status`, `covers` — which is what makes this option available at all.

**O36** — Hierarchical indexes are the fallback that keeps the root file small, and two independent vendors ship nesting as the answer. AGENTS.md: "**Large monorepo? Use nested AGENTS.md files for subprojects** — Place another `AGENTS.md` inside each package. Agents automatically read the nearest file in the directory tree, so the closest one takes precedence"; its FAQ adds "the main OpenAI repo has 88 AGENTS.md files". Cursor: "You can place `AGENTS.md` files in any subdirectory of your project, and they will be automatically applied when working with files in that directory or its children… Instructions from nested `AGENTS.md` files are combined with parent directories, with more specific instructions taking precedence." llms.txt specifies the same resolution rule for files: "A file covers the URLs under its path, and where more than one file applies, agents should use the most specific one." **quoted** [S16, S19, S20] · **my reading**: a second-level index (per kind, or per top-level path in `covers`) is the standard-shaped answer to `Rd3.1`, and both vendors place the precedence rule in the reader, not the generator.

**O37** — llms.txt adds a cheap convention for the "some entries matter more" case: "The `## Optional` section is used, by convention, for secondary information: **links an agent can skip when a shorter context is needed.**" **quoted** [S16] · **my reading**: a fixed-size file that keeps every entry but marks a demotable tail is an alternative to dropping entries, and it costs the generator one field.

### 5. Checking — how anyone can tell the index is in step

**O38** — The canonical check, implemented in a real repo, is *regenerate in a throwaway worktree at HEAD, then ask git whether anything changed*. Kubernetes' `kube::verify::generated` requires `kube::util::ensure_clean_working_dir`, then `git worktree add -f -q "${_tmpdir}" HEAD`, runs the generator (`"$@"`), then: `diffs=$(git status --porcelain | wc -l)` and, if non-zero, echoes the header, `git status`, `git diff`, and the tail, then `return 1`. **quoted** [S12] · **my reading**: this is `K6`'s "Fails if regenerating `INDEX.md` changes it" expressed as a shell function, and the worktree step means the check never touches the developer's dirty tree — which matters when several agents share a worktree's parent repo.

**O39** — The check carries the human's next action in its own output. `hack/verify-codegen.sh`: `kube::verify::generated "Generated files need to be updated" "Please run 'hack/update-codegen.sh'" hack/update-codegen.sh "$@"`. **quoted** [S13] · **my reading**: an index check that says only "out of date" costs a reader the derivation of the fix; naming the command is nearly free.

**O40** — The generator can also *be* the check, via a non-writing mode with a distinct exit code. doctoc: "Use the `--dryrun` option to not write changes to files but instead **return an exit code of 1 to indicate files are out of date and should be updated**. This is useful in CI environments where you want to check if your docs are up to date as part of your build process", with the exit-code table giving `1 | Document out of date | One or more files are out of date and need to be updated, but weren't updated because doctoc was run with --dryrun`. **quoted** [S9] · **my reading**: this makes "is the index in step" answerable by the same command that makes it, with no second implementation to keep in sync.

**O41** — The check belongs where the person who caused the drift cannot skip it — the commit. doctoc documents itself "as a [pre-commit](http://pre-commit.com) hook", terraform-docs documents a `terraform-docs-go` hook with `args: ["markdown", "table", "--output-file", "README.md", …]`. **quoted** [S9, S11] · **my reading**: with `K6.2` ("regenerated right after any decision or fact is written") implemented as an agent `PostToolUse` hook [S2], a commit-time check is redundant for agents but still needed for people, and bypassable via `--no-verify` [S4].

**O42** — The failing CI variant and the self-healing CI variant both exist, and the choice is policy, not fact. Compare O38 (`return 1`) with O20 (`git-push: "true"` onto the PR branch). **quoted** [S12, S11] · **my reading**: `K6`'s stated "Fails if" selects the first; `K6.2`'s "so the next session sees it" selects the second. I found no source that argues for one over the other, and I am not proposing one here.

**O43** — Validating the *header* is a separate check from validating the *index*, and the ecosystem's answer is a schema-validating linter over frontmatter. What I could verify is only the requirement, not the tool: Cursor's rule system silently ignores a file with no frontmatter [S20], and Agent Skills states hard field limits ("`name`: Maximum 64 characters"; "`description`: … Maximum 1024 characters"). **quoted** [S20, S18] · **my reading**: `W1.1`'s "Fails if a lint over `entries/` finds a missing field or section" has no named tool in the open-source world that I was able to read a primary source for (see "did not find" §3), so a generator that trusts the header will emit an index line with a hole in it unless the check is written.

## What I looked for and did not find

1. **No tool that generates an index of many small frontmatter-carrying markdown files, one line per file, committed to git and verified in CI.** I found index generators that read *one* file's headings (doctoc [S9], mdbook-toc [S10]), injectors that read *code* (terraform-docs [S11]), and a standard that specifies an index's *format* (llms.txt [S16]). None combines "read N headered files" → "write one committed index file". I did not search exhaustively; this is what four rounds of targeted fetching found.

2. **No primary source for a documented merge policy for a committed generated index shared across many parallel branches.** I found every underlying git mechanism (merge drivers [S5], `rerere` [S6], `linguist-generated` [S14, S15], `merge.renormalize` [S5], and the explicit prohibition in O27 [S7]) but no write-up that assembles them into a policy, and no tool docs that discuss parallel branches touching their generated output. The closest real-world behaviour is Kubernetes' verify script [S12], which sidesteps conflict resolution entirely by regenerating in a fresh worktree and asserting zero diff.

3. **No frontmatter schema-validating linter verified.** `https://raw.githubusercontent.com/unifiedjs/remark-lint-frontmatter/main/readme.md`, `https://raw.githubusercontent.com/remarkjs/remark-lint-frontmatter/main/readme.md` and `https://raw.githubusercontent.com/remarkjs/remark/main/packages/remark-lint-frontmatter/readme.md` all returned HTTP 404. I therefore make **no claim** about `remark-lint-frontmatter` or any comparable tool's behaviour, and O42 stands on the requirement only.

4. **No non-failing "verify-only" mode confirmed in terraform-docs.** I went looking for something equivalent to doctoc's `--dryrun` [S9]. The README I read [S11] documents `output.mode` values `inject` and `replace` only. I did not read its user guide, so I make no claim that a check mode does or does not exist there.

5. **No documented size limit found for Gemini CLI's `GEMINI.md`, Cursor's `AGENTS.md`, or GitHub Copilot instruction files.** I found Cursor's "under 500 lines" for `.cursor/rules` [S20] and Claude Code's "under 200 lines" for `CLAUDE.md` [S3]; I did not read Gemini CLI's or Copilot's documentation. This bears directly on `Rd3.1`'s "strictest limit among the agents" — the answer below is the strictest of the two agents I checked, not of all of them.

6. **No source expresses a start-file size limit in bytes.** Every figure I found is in lines or tokens: 200 lines [S3], 500 lines [S20], "~100 tokens per Skill" and "Under 5k tokens" [S18], "defaults to 1k tokens" [S17]. The 24 KB figure in `CACHES.md` is not corroborated by anything I read. I did not read `CACHES.md` itself — it is cited by `SOURCE_OF_TRUTH.md` `Rd3.1` and I took the figure from there.

7. **protobuf's "DO NOT EDIT" generated-file convention: not obtained.** `https://protobuf.dev/programming-guides/dos-donts/` returned only a redirect URL with no content, and `https://developers.google.com/protocol-buffers/docs/dos-donts` returned 404. I therefore make no claim about that convention, including the "embed the generating command in the header" variant. The nearest thing I did verify is the in-file marker text [S9, S11].

8. **Two `git` pages I needed were 404 on raw and too noisy on HTML.** `Documentation/githooks.txt` and `Documentation/gitattributes.txt` no longer exist upstream (the tree has moved to `.adoc`); I used the `.adoc` sources and the HTML pages' version banners instead. The Pro Git book page [S8] and reproducible-builds pages [S22, S23] returned mostly navigation chrome; I recovered the needed passages from the saved fetch output, and the reproducible-builds "Stable order for inputs" page 404'd, so I used the "Locales" page [S23], which carries the collation-order material directly.

## Gaps and disagreements between sources

**Lines vs bytes vs tokens.** Claude Code says 200 lines [S3]; Cursor says 500 lines [S20]; Agent Skills quotes token counts [S18]; aider quotes a token budget [S17]. No source converts between them. `Rd3.1` needs a single number to compare against, and none of these documents supplies one in a common unit. This is a disagreement in kind, not in degree, and it is unresolvable from the sources — it needs the measurement `SOURCE_OF_TRUTH.md` already anticipates ("where a limit applies, it is a comparison that measurement decides").

**Three different answers to "the file is too long."** Anthropic says prune, and ships a tool that proposes cuts [S1, O32]. Cursor says split into composable rules and nest [S20, O36]. Anthropic's costs page says move it out of context entirely into skills [S3]. For a *generated* file these are not equivalent: pruning changes only the generator's content rules, while splitting changes the generator's structure and therefore `K6.1` itself. No source I read addresses the generated case specifically.

**Fail the build, or fix the build.** Kubernetes' check returns 1 and names the command to run [S12, S13]. The terraform-docs action regenerates and pushes to the PR branch, passing [S11]. Both are committed generated files in real repos. The sources do not disagree on any fact — only on policy — and `SOURCE_OF_TRUTH.md` pulls in both directions: `K6`'s "**Fails if** regenerating `INDEX.md` changes it" argues for the first, `K6.2`'s "regenerated right after any decision or fact is written, so the next session sees it" for the second. I found no source that adjudicates.

**Hook coverage is narrower than its reputation.** `post-merge` "is not executed, if the merge failed due to conflicts" [S4], and client-side hooks "are not copied when you clone a repository" [S8]. So a git-hook trigger is, in my reading, necessary but not sufficient: it does not fire on the conflicted merges most likely to have left a shared generated file stale, and it does not fire at all for anyone who has not installed it — which, for "several agents at once, each on its own branch or worktree" [S4, W6.2], is everyone who has not run the installer. Agent-side hooks [S2, O17–O19] inherit the same gap: they cover agents, not people, and they need the agent to actually write through a tool the hook can see.

**Determinism is assumed by the tools, enforced by nobody.** terraform-docs documents `sort.by: name` [S11, O4] but nothing I read pins locale, and reproducible-builds names locale collation as the trap [S23, O6] in a document about binaries, not markdown. In my reading, nothing in the prior art stops a generator producing a byte-different index on a machine with a different locale, and a naive adoption of the Kubernetes check [S12] would report that as drift — which is exactly the failure `K6`'s "Fails if" clause would turn into a false alarm that trains people to ignore the check.

**"Checked in git" and "never edited by hand" are separate properties and the sources treat them separately.** Cargo says a generated file "should not be manually edited" and, separately, "check it into version control" [S21, O25]. Linguist/`gitattributes` adds a third, orthogonal property — collapse it in review [S14, S15, O22]. Nothing I read requires any of the three to imply the others, and nothing requires the file to be *reproducible*, which is the fourth and separate property from reproducible-builds [S22, O5].

**Escape hatches are all or nothing.** doctoc offers per-file skip [S9, O3] and terraform-docs offers `sections.hide`/`show` [S11]; neither offers a way to demote rather than drop, and llms.txt's `## Optional` is the only convention I found for the middle case [S16, O37]. If `Rd3.1` is ever hit, that is a discrepancy between what the design may need and what the tooling it would borrow offers.

## Why we need this memory

The context window is cleared at the start of every session, so anything learned is lost unless it is written down.
Project memory is plain markdown files kept in the repo with the code. Every agent and every person reads the same
files, a fresh clone has all of it, and every change shows up as a git diff. Reading it needs no private agent store,
database or outside service.

## Who it is for

Every agent and every person working on this project. There are no owners and no approval gate: anyone may change any
entry, and every change is logged. EJ decides the questions listed as not decided.

Two other kinds of memory are outside this design, and both live outside the repo: memory about one person across
projects (user memory), and memory
belonging to one agent name (agent memory, kept in the home folder at `~/.claude/agent-memory/<name>/`, the way Claude
Code does it).

## What it is for

It holds what the code cannot tell you, as typed entries:

- **Requirements, written before the code.** A **decision** is a choice the code must follow, with the reason. A
  **fact** is a truth or outside constraint the code must respect.
- **What was learned, written after.** A **lesson** comes from a failure or a human correction. An **observation**
  records what was seen. A **hypothesis** is a guess, labelled as one.
- A **runbook** says how to run or fix something; where possible it points at a script.

The order of work is: change the decision or fact first, then the code. Work that has to go the other way is a matter
for the project's workflow, not for memory. A decision about this project is a project entry, whoever made it, EJ
included.

A decision is **started** when it is written: we decided to build something, and why. It is **complete** when the
time, the result and the test results are added to it (EJ, 2026-10-12).

## What will be put in

**An entry** is one markdown file. Its header holds: `id`, `kind`, `status`, `author`, the date it was recorded,
`covers` (the code paths it is about), its source or evidence, links (`depends_on`, `supersedes`, `superseded_by`), a
`changed:` log, and, on a decision once its work is complete, `done:` (the time, the result and the test results). Its
body is the claim in one or two sentences, then **Why:**, then **How to apply:**.

**Changing entries.** Anyone may change any entry, and `AGENTS.md` too. Each change adds one line to the entry's
`changed:` log: the time, and who made it — the model ID for an agent, the name for a person. Files that are not entries
rely on git history. Each new entry gets its own file, so agents never append to one shared file. Two writers must not
edit the same file at the same time: each agent works on its own branch or worktree, and git shows a merge conflict when
two edits
touch the same lines. Edits to different lines of one file merge without warning even if they contradict each other,
so a clean merge does not mean the file is consistent.

**When to write.**

| When | What |
|---|---|
| Immediately | Decisions and facts, before the code — and `INDEX.md` is regenerated right after, so the next session sees them. A human correction. The state of unfinished work before a handoff, an interruption or a context reduction. |
| When the work a decision governs is complete | The decision's `done:` line: the time, the result and the test results. |
| At the end of a task | Other lessons, observations and hypotheses; merging duplicates; runbooks. |

**Keeping it current.** Entries may go out of date while work goes on; that is accepted. Nothing watches for it: there
is no drift-check script and no background subagent. Whoever reads a decision or fact checks it against the code before
acting on it. When they no longer match, the reader does not change the entry: it reports to EJ which entry, what the
entry says, and what the code does instead, and EJ decides whether the entry is updated or the code is fixed.

**Still open:** which tool generates `INDEX.md` and what runs it (K6); who resolves a git merge conflict (W6). Whether a
changed decision is edited in place or superseded is proposed in K4.3.

## What will not be put in

- Anything that can be read directly from the code, the tests or the commit log (W3.1). The memory itself lives in git.
- Credentials or sensitive data.
- Guesses not labelled as a hypothesis.
- Raw transcripts, or another agent's private state.
- Work described as "verified" when it is only implemented.

An entry is never deleted: it is marked `superseded` or `retired` and linked to what replaced it. Age alone never
expires an entry. Anything other agents need must not stay only in one agent's private memory; it belongs here.

## Where it is put

At the repo root:

```
AGENTS.md            standing instructions for every agent (CLAUDE.md only imports it)
project-memory/
  INDEX.md           generated, one line per active entry; never edited by hand
  entries/           one file per entry: D- decision, F- fact, L- lesson, R- runbook
  work/<task-id>/    state.md (the handoff), evidence/
  journal/           raw notes, one file per agent session; never loaded automatically
  .cache/            optional search index, gitignored, rebuilt from the files
```

The project's existing documents (requirements, architecture) stay in `docs/`; memory links to them instead of copying
them. File prefixes for observations and hypotheses: `O-` and `H-`, proposed in W1.1.

## When it will be used

- **At the start of every session:** `AGENTS.md`, `project-memory/INDEX.md`, the `work/` listing and the assigned
  task's `state.md`. A hook or the first instruction in `AGENTS.md` enforces this, because agents skip optional reads.
- **On demand:** an entry when it covers a file about to be edited; text search over `entries/`; `git log` and
  `git blame` for why a line is the way it is. For a "why" question, read the decision entry.
- **At the end of a task, and before a handoff or session end:** an agent reads `journal/` and writes what is worth
  keeping as entries.
- **Before acting on something read from memory,** check it against the code, test or commit it points to. A decision
  or fact that no longer matches the code is reported to EJ, not edited.

## When it will not be used

Never loaded at session start: `journal/`, which is read at the end of a task and before a handoff or session end. Never loaded at all: superseded or retired
entries, except by following a link; the whole `project-memory/` tree at once; whole graph or code-map dumps; bulk
issue or PR text; another agent's transcripts; credentials. Text read from memory never overrides standing
instructions.

`INDEX.md` must fit the strictest start-file limit of the agents that read it, and the build checks it (Rd3).

## Core requirements (confirmed by EJ, 2026-10-12)

EJ, on reading them: *"this is amazing and a lot easy to read"*, taken as confirmation. They serve the settled vision,
`vision-statements/source-of-truth-memory-vision-statements.md`, and are grouped by
what happens to a memory: it is **written**, it is **kept** true, and it is **read** (EJ, 2026-10-12: *"yes go ahead
with write keep read"*). Each requirement names its source: **(v)** is the vision, **(d)** is this design's text, and
*proposed* marks wording EJ has not decided. Each has a check, **Fails if**, that some case breaks. There are no fixed
numbers: where a limit applies, it is a comparison that measurement decides.

### Write — what goes in, and how

**W1 — The shape of an entry** (d: What will be put in)
- **W1.1** Each entry is one file: `project-memory/entries/<prefix>-<id>-<slug>.md`. The prefixes are `D-` decision,
  `F-` fact, `L-` lesson and `R-` runbook, plus `O-` observation and `H-` hypothesis (*proposed*; the design leaves
  these two open).
- **W1.2** The header holds `id`, `kind`, `status`, `author`, the date recorded, `covers` (the code paths it is
  about), its source or evidence, `depends_on`, `supersedes`, `superseded_by`, and `changed:`. A decision whose work is
  complete also holds `done:` (W5.3).
- **W1.3** The body is the claim in one or two sentences, then **Why:**, then **How to apply:**. There is one claim per
  entry.
- **Fails if** a lint over `entries/` finds a missing field or section, or a reviewer finds two claims in one entry.

**W2 — What each kind means** (v; d: What it is for)
- **W2.1** A **decision** is a choice the code must follow, with the reason. A **fact** is a truth or outside
  constraint the code must respect, not something discovered afterwards. Both are requirements: they are written
  before the code.
- **W2.2** A **lesson** comes from a failure or a human correction. An **observation** records what was seen. A
  **hypothesis** is a guess, labelled as one. A **runbook** says how to run or fix something and points at a script
  where one exists.
- **Fails if** `kind` holds any other value, or a guess is recorded under any kind but hypothesis.

**W3 — What never goes in** (v; d: What will not be put in)
- **W3.1** Nothing that can be read directly from the code, the tests or the commit log: what a function does, which
  test covers it, what a commit changed. The memory lives in git; the rule is about what an entry says.
- **W3.2** No credentials or sensitive data.
- **W3.3** No raw transcripts, and nothing from another agent's private state.
- **W3.4** No work described as "verified" when it is only implemented.
- **W3.5** No user memory (one person, across projects) and no agent memory (one agent name). Both live in the home
  folder.
- **W3.6** No copy of the project's existing documents (requirements, architecture in `docs/`): an entry links to them.
- **Fails if** a secret scanner finds a credential (W3.2). For W3.1 and W3.3–W3.6, a reviewer finds such content.
  Those are judged checks.

**W4 — Who writes, and the change log** (v: no owners, every change logged)
- **W4.1** Anyone, agent or person, may create or change any entry, and `AGENTS.md` too. There is no owner and no
  approval: `status` is only `active`, `superseded` or `retired`.
- **W4.2** Every change to an entry adds one line to its `changed:` log: the time, and who made it (the model ID for an
  agent, the name for a person). Earlier lines are never edited.
- **W4.3** Files that are not entries (`state.md`, `journal/`, `AGENTS.md`) rely on git history.
- **Fails if** git shows a change to an entry with no matching `changed:` line, or a `status` outside the three.

**W5 — When to write** (d: When to write)
- **W5.1** Written immediately: a decision or fact, before the code it governs; a human correction; and the state of
  unfinished work, before a handoff, an interruption or a context reduction.
- **W5.2** Written at the end of a task: other lessons, observations, hypotheses, and runbooks.
- **W5.3** A decision is started when it is written. When the work it governs is complete, the agent or person who did
  the work adds `done:` to it: the time, the result and the test results (EJ, 2026-10-12).
- **Fails if** a commit changes code under a new decision with no entry in that commit or an earlier one. For a human
  correction, it fails if the session ends without one (judged). For W5.3, it fails if a task's `state.md` says its
  work is complete and the decision it carried out has no `done:` line.

**W6 — Writers do not collide** (d: Changing entries)
- **W6.1** Each new entry gets its own file. Agents never append to one shared file; `journal/` has one file per agent
  session.
- **W6.2** Each agent works on its own branch or worktree, so two edits to the same lines meet as a merge conflict, not
  a silent overwrite.
- **Open:** who resolves a merge conflict.
- **Fails if** an edit to an entry is lost without a conflict.

### Keep — memory stays true, and nothing is lost

**K1 — The decision or fact first, then the code** (v; d: What it is for)
- **K1.1** To change behaviour that a decision or fact governs, change the entry first, then the code. Work that has to
  go the other way is a matter for the project's workflow, not for memory.
- **Fails if** git shows a commit changing the behaviour a decision or fact governs, with no change to that entry in the
  same commit or an earlier one (judged).

*K2 (the drift-check script) and K3 (the background subagent) were removed by EJ on 2026-10-12. Their numbers are not
reused, because other text cites K4–K6. A mismatch between a decision and the code is now caught when the decision is
read (Rd5).*

**K4 — Never deleted, never expired by age** (v: nothing lost; d: What will not be put in)
- **K4.1** An entry is never deleted. It is marked `superseded` or `retired`, links to what replaced it
  (`superseded_by`), and keeps its old body.
- **K4.2** Age alone never expires an entry. An entry is found out of date only when someone reads it and checks it
  against the code (Rd5).
- **K4.3** *Proposed:* a decision refined without changing its meaning is edited in place, with a `changed:` line; a
  decision replaced by a different one gets a new entry that supersedes it. The design leaves this open.
- **Fails if** git shows an entry file deleted, or a `superseded` or `retired` entry has no link.

**K5 — The journal becomes entries** (v: nothing lost between sessions)
- **K5.1** Task and project memory keep `journal/`: raw notes, one file per agent session, appended to and never
  edited.
- **K5.2** At the end of a task, and before a handoff or session end, an agent reads the journal written since the
  last read, writes what is worth keeping as entries, and logs that read in the task's `state.md`. A session cut off
  before it can read loses nothing: the next read covers it (EJ, 2026-10-12: no separate milestones, the start and the
  end already cover them).
- **Fails if** a task's `state.md` shows it complete or handed off with no journal-read log line.

**K6 — `INDEX.md` stays in step** (d: Where it is put; When to write)
- **K6.1** `INDEX.md` is generated from `entries/`: one line per active entry, showing its id, kind and one-line
  claim. It is never edited by hand.
- **K6.2** It is regenerated right after any decision or fact is written, so the next session sees it.
- **Open:** which tool generates it and what runs it (a build detail).
- **Fails if** regenerating `INDEX.md` changes it, meaning it was out of step, or it lists a superseded entry as
  active.

### Read — the right memory reaches the agent at the right time

**Rd1 — Where it lives, and readable from a clone alone** (v: plain files; never a database or service)
- **Rd1.1** `AGENTS.md` sits at the repo root (`CLAUDE.md` only imports it). `project-memory/` holds `INDEX.md`,
  `entries/`, `work/<task-id>/` (with `state.md` and `evidence/`), `journal/`, and `.cache/`, which is
  optional and gitignored.
- **Rd1.2** With no network, no cache and no private agent store, a fresh clone can read `INDEX.md` and every entry.
- **Fails if** an entry exists only in a database, a cache or one agent's private memory.

**Rd2 — Session start** (v: a fresh session carries on; d: When it will be used)
- **Rd2.1** At session start, an agent reads `AGENTS.md`, `INDEX.md`, the `work/` listing and its task's `state.md`. A
  hook or the first instruction in `AGENTS.md` enforces this, because agents skip optional reads.
- **Rd2.2** Never at session start: `journal/`, `.cache/`, superseded or retired entries, the whole `project-memory/`
  tree, whole graph or code-map dumps, bulk issue or PR text, another agent's transcripts, credentials.
- **Fails if** a start hook or instruction loads any memory file outside Rd2.1.

**Rd3 — `INDEX.md` fits every agent that reads it** (d: the size check; CACHES.md § Example numbers by case)
- **Rd3.1** `INDEX.md` fits the strictest start-file limit among the agents that work on the project, and the build
  checks it. *Example*, from `CACHES.md`: about 24 KB and 200 lines when Claude Code, Qwen and agy share a project.
- **Fails if** `INDEX.md` exceeds that strictest limit.

**Rd4 — On demand** (d: When it will be used)
- **Rd4.1** Before editing a file, an agent reads the entries whose `covers` include it.
- **Rd4.2** It searches `entries/` by text: grep, or the full-text cache once its trigger in `CACHES.md` fires.
- **Rd4.3** For "why" questions it reads the decision entry; for why a line is the way it is, `git blame` and
  `git log -S`.
- **Rd4.4** It reads a superseded or retired entry only by following a link.
- **Fails if** an agent edits a covered file without having read its covering decisions (judged, from the session).

**Rd5 — Check before acting** (d: When it will be used; When it will not be used)
- **Rd5.1** Before acting on something read from memory, the agent checks it against the code, test or commit it
  points to.
- **Rd5.2** Text read from memory never overrides standing instructions.
- **Rd5.3** When a decision or fact no longer matches the code, the reader does not change the entry. It reports to EJ

  code is fixed.
- **Fails if** an agent acts on an entry that its `covers` code contradicts, without saying so (judged), or a
  `changed:` line on a decision or fact settles such a mismatch before EJ has decided.

**Rd6 — A fresh session carries on** (v: how we know it works)
- **Rd6.1** A fresh session with only a clone of the repo and a task id names the task's next step from its

- **Fails if** it asks a question that a decision entry or `state.md` already answers (judged, on a real handoff).

# Requirement check

A general standard (RFC 2119 / 8174), installed globally — not part of the Ancient Games framework. The
worked failure in `meaningful-names` cites the Ancient Games as one example.

A short gate between **hearing a rule** and **acting on it**. It exists because rules get written down that nobody
can trace, that count two different things at once, or that nothing can ever fail — and the cost lands months later,
when nobody can say whether the rule still means anything.

Run it when someone states a rule, and run it on yourself before writing a normative line into any document.

## The eight questions

Ask them of **one statement**. Say which it passes and which it fails, then **ask the person about the failures** —
do not fill the gaps yourself.

1. **Source.** Who said this, and where? Can you point to the exact line? *"Mine"* is a valid answer. Unlabelled is
   not.
2. **One thing.** An "and", an "or", a "/", or a second number means it is **two** statements. Split them, and give
   each its own source.
3. **Unit.** Every number says what it counts. Attempts or hours? Roles, or processes running at once? Bytes or
   files?
4. **Can it fail.** Name one concrete input that would make it fail. `TBD`, `—`, `0` and empty must be among the
   failing inputs. If you cannot name one, it is not checkable — it is a wish.
5. **Weak words.** *like, about, appropriate, as needed, logical, fast, enough, reasonable, only has to, TBD.* Replace
   each with a value, **or mark the value open**. Never invent the number.
6. **Level.** Is it **MUST** (a gate that stops work), **SHOULD** (a default that may be overridden with a stated
   reason), or **guidance**? A safety bound earns MUST. **A method does not** — see the RFC note below.
7. **Basis.** Measured, quoted from a source, or a guess? A guess is fine **if it is labelled** — `n=0`, with when it
   will be looked at again.
8. **Links.** Does it claim a relation to another rule — *"half of"*, *"pairs with"*, *"the same as"*, *"the runtime
   part"*? The person probably did not say that. **A link is its own claim and needs its own source.**

## Two rules for the agent

- **Never fill a gap with your own value.** A missing unit, threshold or test goes back as a question. Inventing it
  is exactly how a rule becomes unattributable later, and the invention is indistinguishable from the original by
  the time anyone notices.
- **Never add structure that was not given.** No halves, no numbered reasons, no ordered pairs, no named phases,
  unless the person said so. Quote them, state the operative sentence, stop. If a relationship between two rules is
  wanted, that is a separate claim with its own evidence.

## Two verified facts, worth quoting

- **RFC 2119 §6, "Guidance in the use of these Imperatives":** imperatives *"must be used with care and sparingly…
  they MUST only be used where it is actually required… they must not be used to try to impose a particular method."*
  Most design rules are method. Method does not earn MUST.
- **RFC 8174 (updates 2119):** the key words *"have the meanings specified herein only when they are in all
  capitals."* Lowercase *must* and *should* carry no defined requirement meaning. If nothing marks which lines are
  requirements, a reader cannot tell rules from explanation.

## How to answer

Evaluate first, in a table or a short list — **pass / FAIL per question**. Then ask the failing ones as questions,
one line each, with the options if you can see them. Two or three real questions beat eight formalities.

Do not report a rule as complete when you chose its missing value. Say which values you left open.

## A worked failure

> *"At most 5 subagent roles per run and at most 3 running at once."*

Four of the eight fail: **Source** — nobody could name one; **One thing** — a count of roles *and* a count of
concurrent processes; **Unit** — two different units, one word ("subagent") used for both; **Level** — a method
preference written as a cap. The sentence would not parse, and it took four days to find out why. The checklist
catches it in thirty seconds.

The same checklist, run on *"No single call runs longer than the ceiling: 8 hours"*, passes all eight — because it
names who set it, counts one thing, uses a unit, and some input (a 40-hour plan) makes it fail.

## Limits

The quality characteristics behind these questions (necessary, appropriate, unambiguous, complete, singular,
feasible, verifiable, correct, conforming) come from requirements-engineering sources — IEEE 830, ISO/IEC/IEEE 29148
and the INCOSE *Guide to Writing Requirements* — which were **not read** when this skill was written: they are
paywalled or blocked, and the list is recalled rather than verified. The two RFC points above **were** read, and the
quotes are checked. Treat the rest as a good working list, not as a citation.

## Findings

### 1. Building the lines

- **C1** — Qwen Code builds its team-memory `MEMORY.md` index from the files in a directory, one line per file:
  `- [title](relative path) — description`, where the line is capped and an over-long description is shortened, not
  the link. *Quoted* (S36, `indexer.ts`): `` const link = `- [${title}](${encodeIndexPathTarget(doc.relativePath)})`; ``
  and the comment *"a resolving long link beats a short dead one"*. The cap is `MAX_INDEX_LINE_CHARS = 150`
  (`index-budget.ts`).
- **C2** — Qwen Code sorts that committed index by path with a code-unit comparison and says why: locale-dependent
  order made collaborators rewrite the file back and forth. *Quoted* (S36, `indexer.ts`): *"Code-unit comparison, NOT
  localeCompare: the index is committed and pushed, so its ordering must be byte-identical across machines/locales —
  otherwise two collaborators churn MEMORY.md back and forth and the ff-only sync wedges."* It also orders by path, not
  by modification time: *"docs are ordered by path (not mtime) so the committed file is deterministic across machines
  and does not churn after a git checkout."*
- **C3** — Qwen Code skips the write when the new index is byte-identical to the old one. *Quoted* (S36,
  `indexer.ts`): *"Skip a byte-identical rewrite: regenerating MEMORY.md every run would churn its mtime and produce
  no-op commits that ping-pong between collaborators."*
- **C4** — Qwen Code's team index merges entries whose descriptions are the same after normalising, into one line with
  an "(also: …)" list; the topic files are kept. *Quoted* (S36, `indexer.ts`): *"When two people save the same shared
  fact, collapsing them into one index line — listing the other files via "(also: …)" — keeps the index readable. The
  topic files themselves are never removed"*, and the match is *"Conservative (normalized-exact, not fuzzy) so two
  genuinely different facts are never silently merged."*
- **C5** — mdsmith generates an index from the front matter of files matching a glob, one row per file, with a row

## Gaps and disagreements between sources

- **Commit the combined file, or not.** Qwen Code (C34), npm (C39), Go (C25) and gh-aw (C41) commit generated output;
  CPython (C32), log4brains (C30) and GitLab today (C33) do not, and build it on demand or at release. Towncrier and
  Changesets (C23) commit it, but only at release, so working branches never touch it.
- **What to do when two branches meet.** Three answers, each from a different source: avoid the merge
  (Qwen Code, fast-forward only, C34); regenerate inside the merge (mdsmith, C38; npm, C39); or take both sides
  (`union`, C35), which the git manual and a bug report warn against (C35, C36). The merge-driver answer depends on
  per-clone config that a fresh clone lacks (C37).
- **Order.** Qwen Code and mdsmith sort by path with a locale-free or explicit comparison (C2, C5); adr-tools uses
  locale-dependent `sort` (C8, C9); blurb sorts by a time stamp in the file name (C16); reno by git topology (C17);
  Repomix and Aider by importance (C19). Sorting by importance and truncating fits a budget; sorting by path keeps the
  file byte-stable. No source does both.
- **Size limits differ by agent and by how the file is loaded.** Claude Code: 200 lines / 25 KB for `MEMORY.md`, but
  4 MiB for a CLAUDE.md and its imports, and 10,000 characters for SessionStart hook output (C44, C45). Qwen Code:

## Findings

### 1. Building the lines — what is read, what is written, the order, and stability

**O1** — The dominant prior-art shape is *injecting a delimited region into a hand-written file*, not writing a whole separate file. Both tools I read mark the generated region with HTML comments: doctoc — "The pragma is the opening and closing comment blocks to mark the location of the doctoc contents, i.e. `<!-- START doctoc ... -->`"; terraform-docs ships this as its default `output.template`: `<!-- BEGIN_TF_DOCS -->` / `{{ .Content }}` / `<!-- END_TF_DOCS -->`, with `mode: inject`. **quoted** [S9, S11]

**O2** — The marker doubles as the machine-readable "do not hand-edit" rule, written into the file itself. doctoc emits, inside the region: `<!-- DON'T EDIT THIS SECTION, INSTEAD RE-RUN doctoc TO UPDATE -->`. **quoted** [S9]

**O3** — Two escape hatches exist for individual files: an explicit skip marker (`just add <!-- DOCTOC SKIP --> to the top of the file you wish to ignore`) and a configurable insertion marker (mdbook-toc's `marker`, default `<!-- toc -->`, with GitLab and GitHub markers supported). **quoted** [S9, S10]

**O4** — Order is a declared, versioned configuration value in real tools, not an accident of directory traversal: terraform-docs' config carries `sort:` / `enabled: true` / `by: name`. **quoted** [S11] · **my reading**: if the order is left unspecified, the same set of files can yield two different files after an unrelated filesystem change, which breaks any "regenerate and diff" check [S12].

**O5** — Bit-for-bit stability of a generated artifact is a named, defined property with a named verification method, not an aspiration. Reproducible Builds: "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts" and "The reproducibility of artifacts is verified by bit-by-bit comparison." **quoted** [S22] · **my reading**: `K6.1`'s "never edited by hand" is the weaker half of this; the stronger half, that the generator is a pure function of `entries/`, is what makes `K6`'s "Fails if regenerating `INDEX.md` changes it" a usable check.

**O6** — The specific way sorting breaks determinism is collation order. Reproducible Builds, on locale: "tools which output is influenced by the current locale can make locale a source of reproducibility issues"; "Common sorting functions are affected by the `LC_COLLATE` environment variable, which can be overridden by `LC_ALL`. Some locales can be quite surprising" — demonstrated with `LC_ALL=fr_FR.UTF-8 sort` yielding `a B c` and `LC_ALL=C sort` yielding `B a c`, because "The C locale will sort according to the byte values and is always available". **quoted** [S23] · **my reading**: this is the failure that turns a "check" into a false alarm, and no tool I read pins locale.

**O7** — The same page names the other three volatile inputs a generator must not absorb: time format (`LC_TIME`), default character encoding (`LC_CTYPE`), and system timezone/`TZ`. **quoted** [S23] · **my reading**: an index that embeds a generation timestamp or a "generated at" line is non-deterministic by construction.

**O8** — There is a direct format precedent for "one line per item, with a short label": llms.txt's file list is "a markdown list, containing a required markdown hyperlink `[name](url)`, then optionally a `:` and notes about the file." **quoted** [S16] · **my reading**: `K6.1`'s "id, kind and one-line claim" is the same shape with a link replaced by an id.

**O9** — The agent-facing index standard states the size property of the index file explicitly, and locates the detail elsewhere: "Agents are expected to view or search llms.txt to find the information they need, then follow the relevant links… **The file itself stays small enough to fit in context. The detail lives behind the links, and is fetched only when needed.**" **quoted** [S16]

**O10** — Treating the header as a machine-readable contract is universal across agent tools, which is what lets a generator rely on it. Cursor: "Each rule is an `.mdc` file… A plain `.md` file in `.cursor/rules` is ignored by the rules system because it has no frontmatter to specify `description`, `globs`, and `alwaysApply`." Agent Skills require YAML frontmatter with `name` and `description`. **quoted** [S18, S20] · **my reading**: `W1.2`'s field list is the same kind of contract, but unlike these tools nothing in the design currently *validates* it — see O42.

**O11** — The closest tool I found to "generate a table of one line per source item from parsed attributes" is terraform-docs, which renders per-item rows for inputs, outputs, modules, providers, requirements and resources through named template variables (`{{ .Inputs }}`, `{{ .Outputs }}`, …). **quoted** [S11] · **my reading**: its input is code, not markdown files with headers; I did not find a tool that does the latter (see "did not find" §1).

### 2. When it runs and what runs it

**O12** — The in-repo, no-service trigger is the git hook. `pre-commit`: "This hook is invoked by `git commit`, and can be bypassed with the `--no-verify` option… Exiting with a non-zero status from this script causes the `git commit` command to abort before creating a commit." **quoted** [S4]

**O13** — The catch that makes hook-only designs fragile: hooks live outside version control. `githooks(5)`: "By default the hooks directory is `$GIT_DIR/hooks`, but that can be changed via the `core.hooksPath` configuration variable." Pro Git is blunter: "**It's important to note that client-side hooks are not copied when you clone a repository.** If your intent with these scripts is to enforce a policy, you'll probably want to do that on the server side". **quoted** [S4, S8]

**O14** — The established fix for O13 is a hook manager whose configuration is a committed file. Lefthook: "A Git hooks manager for Node.js, Ruby, Python and many other types of projects… Configure your hooks, install them once and forget about it: rely on the magic underneath", with the config in a committed `lefthook.yml` and activation by `lefthook install`. Both tools I read ship a literal in-repo pre-commit block as the documented install path (doctoc and terraform-docs). **quoted** [S9, S11, S24] · **my reading**: I did not verify in Lefthook's README how it points git at the committed scripts; `core.hooksPath` [S4] is git's own mechanism for that and I did not confirm Lefthook's use of it from the page I read.

**O15** — "At merge" has a native hook with exactly one limitation that matters here. `post-merge`: "This hook is invoked by `git merge`, which happens when a `git pull` is done on a local repository… This hook cannot affect the outcome of `git merge` and is not executed, if the merge failed due to conflicts." **quoted** [S4] · **my reading**: a `post-merge` regeneration is skipped on precisely the conflicted merges where the shared generated file is most likely stale, so `post-merge` cannot be the only trigger.

**O16** — `post-checkout` has broader reach: it fires on `git checkout`/`git switch`, and "It is also run after `git clone`, unless the `--no-checkout` (`-n`) option is used", and likewise for `git worktree add`. **quoted** [S4] · **my reading**: given W6.2 (each agent on its own branch or worktree), this is the one git hook that fires for every kind of branch movement in this design, and it is the only one that also fires on a fresh clone.

**O17** — "At session start" is a first-class, agent-side trigger point. Claude Code's `SessionStart` event: "When a session begins or resumes", with matcher values `startup`, `resume`, `clear`, `compact`, `fork`. The same doc's worked example for "a linting script only when Claude writes or edits a file" uses `PostToolUse` with `matcher: "Edit|Write"` — which is the shape of `K6.2`'s "regenerated right after any decision or fact is written". **quoted** [S2] · **my reading**: `PostToolUse`/`Write|Edit` + a path filter is the mechanism that matches K6.2 most literally, and it fires in worktrees because hooks run with `cwd` following the session [S2].

**O18** — There is a hook that fires *when an instruction file is loaded into context*, which is the exact moment Rd2.1 cares about: `InstructionsLoaded` — "When a CLAUDE.md or `.claude/rules/*.md` file is loaded into context. Fires at session start and when files are lazily loaded during a session", matcher values `session_start`, `nested_traversal`, `path_glob_match`, `include`, `compact`. **quoted** [S2]

**O19** — The vendor's own position is that a hook, not an instruction, is what guarantees a start-of-session read: "Hooks run scripts automatically at specific points in Claude's workflow. Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." **quoted** [S1] · **my reading**: this is external support for the design's premise in Rd2.1 that "agents skip optional reads", and against `AGENTS.md` text alone as the enforcement mechanism.

**O20** — In CI the common pattern for a committed generated file is to *push the regeneration back onto the PR branch* rather than fail. terraform-docs' documented GitHub Actions workflow: `on: - pull_request`, `output-method: inject`, `git-push: "true"`. **quoted** [S11]

**O21** — Read-time generation is also a supported mode, and a real one: mdbook-toc is an mdBook preprocessor, so the index is produced by `mdbook path/to/book` at build time, not at commit time; doctoc additionally offers `-s/--stdout` and `--dryrun`. **quoted** [S9, S10] · **my reading**: read-time generation is incompatible with `Rd1.2` (fresh clone, no cache) and with `Rd2.1` (every agent reads a file at session start).

### 3. Git — committed or not, and parallel branches

**O22** — Generated files are conventionally *marked* so review tooling collapses them. Linguist: `linguist-generated` → "Excluded from stats, hidden in diffs", and "unlike vendored and documentation files, these files are suppressed in diffs". GitHub Docs: "you can mark them with the `linguist-generated` attribute in a `.gitattributes` file… to mark or unmark paths that you would like to be ignored for the repository's language statistics and hidden by default in diffs". **quoted** [S14, S15]

**O23** — Git already ships merge semantics for "a file that cannot be line-merged". The built-in `binary` driver: "Keep the version from your branch in the work tree, but leave the path in the conflicted state for the user to sort out. This is suitable for binary files that do not have a well-defined merge semantics." Setting the `merge` attribute unset gives: "Take the version from the current branch as the tentative merge result, and declare that the merge has conflicts." **quoted** [S5] · **my reading**: "take one side, mark the path unresolved, regenerate" is already a coherent git-native policy; the design's `INDEX.md` is a candidate for `merge=binary`.

**O24** — The opposite driver is documented as unsafe for exactly this case. `union`: "Run 3-way file level merge for text files, but take lines from both versions, instead of leaving conflict markers. **This tends to leave the added lines in the resulting file in random order and the user should verify the result.**" **quoted** [S5] · **my reading**: a union merge on a generated index preserves deleted entries as stale lines and can reorder them, so it turns a mechanical problem into a silent-correctness one — the opposite of K6's "Fails if".

**O25** — The commit-or-not decision has a documented rule of thumb from a project with the same shape of problem (a machine-written file that must be readable from a clone). Cargo: "Cargo.lock contains exact information about your dependencies. **It is maintained by Cargo and should not be manually edited.**" and "**When in doubt, check Cargo.lock into the version control system (e.g. Git).**" **quoted** [S21] · **my reading**: `Rd1.2` (a fresh clone can read it, no cache) forces the commit side of this trade-off; the cost is exactly the merge handling in O23–O24.

**O26** — Repeated identical conflicts can be *learned* rather than resolved by hand: `git rerere` "assists the developer in this process by recording conflicted automerge results and corresponding hand resolve results on the initial manual merge, and applying previously recorded hand resolutions to their corresponding automerge results", and `git merge` "automatically invokes `git rerere` upon exiting with a failed automerge". **quoted** [S6] · **my reading**: this is what makes "resolve by regenerating" affordable across many parallel branches touching the index the same way. Its stated limit: "'git rerere' relies on the conflict markers in the file to detect the conflict."

**O27** — Git explicitly forbids the obvious shortcut of hiding local edits to a tracked file. `git update-index(1)`: "**Users often try to use the assume-unchanged and skip-worktree bits to tell Git to ignore changes to files that are tracked. This does not work as expected**, since Git may still check working tree files against the index when performing certain operations. **In general, Git does not provide a way to ignore changes to tracked files, so alternate solutions are recommended.**" And on `--assume-unchanged`: "Git will fail (gracefully) in case it needs to modify this file in the index e.g. when merging in a commit". **quoted** [S7]

**O28** — If the index is produced *by a git filter* rather than committed directly, git has a setting for the resulting spurious conflicts: "by setting the `merge.renormalize` configuration variable… Git can be told to run a virtual check-out and check-in of all three stages of each file that needs a three-way content merge… **This prevents changes caused by check-in conversion from causing spurious merge conflicts** when a converted file is merged with an unconverted file." **quoted** [S5] · **my reading**: the design says nothing about a clean/smudge filter for `INDEX.md`; this is the documented cost of that route if stage 2 picks it.

**O29** — `.gitattributes` is the only per-path, versioned, in-repo mechanism git provides for file behaviour, and it is designed to be shared: "Attributes which should be version-controlled and distributed to other repositories (i.e., attributes of interest to all users) should go into `.gitattributes` files." **quoted** [S5] · **my reading**: whatever git-side policy is chosen for `INDEX.md` (O22, O23, O28) is expressed there, so it is itself subject to merge — but a one-file attributes entry is a far smaller conflict surface than the index body.

### 4. Size — what happens when the index outgrows the start-file limit

**O30** — The published size ceiling for a start-of-session instruction file is **lines**, and the strictest one I found is Claude Code's: "**Aim to keep CLAUDE.md under 200 lines by including only essentials.**" **quoted** [S3] · **my reading**: this is a primary-source corroboration of the 200-line figure in `Rd3.1`'s example, and it is the number `INDEX.md` would have to clear.

**O31** — The failure mode of overshooting is silent degradation, not an error. Anthropic: "**Bloated CLAUDE.md files cause Claude to ignore your actual instructions!**" and "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." Elsewhere on the same page: "If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise." **quoted** [S1]

**O32** — The vendor's own remedy for an oversized checked-in file is *pruning by a tool*, not splitting: "For a checked-in CLAUDE.md, run `/doctor` and Claude proposes cuts for content it can derive from the codebase." With the test to apply: "Keep it concise. For each line, ask: *'Would removing this cause Claude to make mistakes?'* If not, cut it." **quoted** [S1] · **my reading**: for a generated file, "cut it" is a change to the generator's rules (drop `covers`, shorten claims), which is a cheap response to `Rd3.1` — no structural change to `K6.1`.

**O33** — Cursor's ceiling is the same unit but larger, and it prescribes the other response — split and scope: "Keep rules under 500 lines / Split large rules into multiple, composable rules / Provide concrete examples or referenced files / … Reference files instead of copying their contents. This keeps rules short and prevents them from becoming stale as code changes." **quoted** [S20] · **my reading**: among the agents whose docs I read, 200 lines (Claude Code) is stricter than 500 lines (Cursor `.cursor/rules`), so `Rd3.1`'s "strictest limit" is the Claude Code figure on current published docs.

**O34** — The general pattern for "a file that must not grow past a budget" is progressive disclosure with a tiny always-loaded part. Agent Skills: "This filesystem-based architecture enables **progressive disclosure**: Claude loads information in stages as needed, rather than consuming context upfront", with the table giving Level 1 metadata "~100 tokens per Skill", Level 2 instructions "Under 5k tokens", Level 3 "None until accessed", and the conclusion "Progressive disclosure ensures only relevant content occupies the context window at any given time." **quoted** [S18] · **my reading**: the design's `INDEX.md` line is exactly Level 1 and the entry body is Level 2/3 — the design is already shaped like this; what is missing is any stated budget for the line.

**O35** — The other budgeted-index answer is *rank and select*, not truncate. aider: "Of course, for large repositories even just the repo map might be too large for the LLM's context window. Aider solves this problem by sending just the most relevant portions of the repo map… Aider optimizes the repo map by **selecting the most important parts of the codebase which will fit into the active token budget**", governed by `--map-tokens`, "which defaults to 1k tokens". **quoted** [S17] · **my reading**: selection needs a relevance signal, and the design already has three candidates in every header — `kind`, `status`, `covers` — which is what makes this option available at all.

**O36** — Hierarchical indexes are the fallback that keeps the root file small, and two independent vendors ship nesting as the answer. AGENTS.md: "**Large monorepo? Use nested AGENTS.md files for subprojects** — Place another `AGENTS.md` inside each package. Agents automatically read the nearest file in the directory tree, so the closest one takes precedence"; its FAQ adds "the main OpenAI repo has 88 AGENTS.md files". Cursor: "You can place `AGENTS.md` files in any subdirectory of your project, and they will be automatically applied when working with files in that directory or its children… Instructions from nested `AGENTS.md` files are combined with parent directories, with more specific instructions taking precedence." llms.txt specifies the same resolution rule for files: "A file covers the URLs under its path, and where more than one file applies, agents should use the most specific one." **quoted** [S16, S19, S20] · **my reading**: a second-level index (per kind, or per top-level path in `covers`) is the standard-shaped answer to `Rd3.1`, and both vendors place the precedence rule in the reader, not the generator.

**O37** — llms.txt adds a cheap convention for the "some entries matter more" case: "The `## Optional` section is used, by convention, for secondary information: **links an agent can skip when a shorter context is needed.**" **quoted** [S16] · **my reading**: a fixed-size file that keeps every entry but marks a demotable tail is an alternative to dropping entries, and it costs the generator one field.

### 5. Checking — how anyone can tell the index is in step

**O38** — The canonical check, implemented in a real repo, is *regenerate in a throwaway worktree at HEAD, then ask git whether anything changed*. Kubernetes' `kube::verify::generated` requires `kube::util::ensure_clean_working_dir`, then `git worktree add -f -q "${_tmpdir}" HEAD`, runs the generator (`"$@"`), then: `diffs=$(git status --porcelain | wc -l)` and, if non-zero, echoes the header, `git status`, `git diff`, and the tail, then `return 1`. **quoted** [S12] · **my reading**: this is `K6`'s "Fails if regenerating `INDEX.md` changes it" expressed as a shell function, and the worktree step means the check never touches the developer's dirty tree — which matters when several agents share a worktree's parent repo.

**O39** — The check carries the human's next action in its own output. `hack/verify-codegen.sh`: `kube::verify::generated "Generated files need to be updated" "Please run 'hack/update-codegen.sh'" hack/update-codegen.sh "$@"`. **quoted** [S13] · **my reading**: an index check that says only "out of date" costs a reader the derivation of the fix; naming the command is nearly free.

**O40** — The generator can also *be* the check, via a non-writing mode with a distinct exit code. doctoc: "Use the `--dryrun` option to not write changes to files but instead **return an exit code of 1 to indicate files are out of date and should be updated**. This is useful in CI environments where you want to check if your docs are up to date as part of your build process", with the exit-code table giving `1 | Document out of date | One or more files are out of date and need to be updated, but weren't updated because doctoc was run with --dryrun`. **quoted** [S9] · **my reading**: this makes "is the index in step" answerable by the same command that makes it, with no second implementation to keep in sync.

**O41** — The check belongs where the person who caused the drift cannot skip it — the commit. doctoc documents itself "as a [pre-commit](http://pre-commit.com) hook", terraform-docs documents a `terraform-docs-go` hook with `args: ["markdown", "table", "--output-file", "README.md", …]`. **quoted** [S9, S11] · **my reading**: with `K6.2` ("regenerated right after any decision or fact is written") implemented as an agent `PostToolUse` hook [S2], a commit-time check is redundant for agents but still needed for people, and bypassable via `--no-verify` [S4].

**O42** — The failing CI variant and the self-healing CI variant both exist, and the choice is policy, not fact. Compare O38 (`return 1`) with O20 (`git-push: "true"` onto the PR branch). **quoted** [S12, S11] · **my reading**: `K6`'s stated "Fails if" selects the first; `K6.2`'s "so the next session sees it" selects the second. I found no source that argues for one over the other, and I am not proposing one here.

**O43** — Validating the *header* is a separate check from validating the *index*, and the ecosystem's answer is a schema-validating linter over frontmatter. What I could verify is only the requirement, not the tool: Cursor's rule system silently ignores a file with no frontmatter [S20], and Agent Skills states hard field limits ("`name`: Maximum 64 characters"; "`description`: … Maximum 1024 characters"). **quoted** [S20, S18] · **my reading**: `W1.1`'s "Fails if a lint over `entries/` finds a missing field or section" has no named tool in the open-source world that I was able to read a primary source for (see "did not find" §3), so a generator that trusts the header will emit an index line with a hole in it unless the check is written.

## What I looked for and did not find

The README I read [S11] documents `output.mode` values `inject` and `replace` only. I did not read its user guide, so I make no claim that a check mode does or does not exist there.

## Gaps and disagreements between sources

**Lines vs bytes vs tokens.** Claude Code says 200 lines [S3]; Cursor says 500 lines [S20]; Agent Skills quotes token counts [S18]; aider quotes a token budget [S17]. No source converts between them. `Rd3.1` needs a single number to compare against, and none of these documents supplies one in a common unit. This is a disagreement in kind, not in degree, and it is unresolvable from the sources — it needs the measurement `SOURCE_OF_TRUTH.md` already anticipates ("where a limit applies, it is a comparison that measurement decides").

**Three different answers to "the file is too long."** Anthropic says prune, and ships a tool that proposes cuts [S1, O32]. Cursor says split into composable rules and nest [S20, O36]. Anthropic's costs page says move it out of context entirely into skills [S3]. For a *generated* file these are not equivalent: pruning changes only the generator's content rules, while splitting changes the generator's structure and therefore `K6.1` itself. No source I read addresses the generated case specifically.

**Fail the build, or fix the build.** Kubernetes' check returns 1 and names the command to run [S12, S13]. The terraform-docs action regenerates and pushes to the PR branch, passing [S11]. Both are committed generated files in real repos. The sources do not disagree on any fact — only on policy — and `SOURCE_OF_TRUTH.md` pulls in both directions: `K6`'s "**Fails if** regenerating `INDEX.md` changes it" argues for the first, `K6.2`'s "regenerated right after any decision or fact is written, so the next session sees it" for the second. I found no source that adjudicates.

**Hook coverage is narrower than its reputation.** `post-merge` "is not executed, if the merge failed due to conflicts" [S4], and client-side hooks "are not copied when you clone a repository" [S8]. So a git-hook trigger is, in my reading, necessary but not sufficient: it does not fire on the conflicted merges most likely to have left a shared generated file stale, and it does not fire at all for anyone who has not installed it — which, for "several agents at once, each on its own branch or worktree" [S4, W6.2], is everyone who has not run the installer. Agent-side hooks [S2, O17–O19] inherit the same gap: they cover agents, not people, and they need the agent to actually write through a tool the hook can see.

**Determinism is assumed by the tools, enforced by nobody.** terraform-docs documents `sort.by: name` [S11, O4] but nothing I read pins locale, and reproducible-builds names locale collation as the trap [S23, O6] in a document about binaries, not markdown. In my reading, nothing in the prior art stops a generator producing a byte-different index on a machine with a different locale, and a naive adoption of the Kubernetes check [S12] would report that as drift — which is exactly the failure `K6`'s "Fails if" clause would turn into a false alarm that trains people to ignore the check.

**"Checked in git" and "never edited by hand" are separate properties and the sources treat them separately.** Cargo says a generated file "should not be manually edited" and, separately, "check it into version control" [S21, O25]. Linguist/`gitattributes` adds a third, orthogonal property — collapse it in review [S14, S15, O22]. Nothing I read requires any of the three to imply the others, and nothing requires the file to be *reproducible*, which is the fourth and separate property from reproducible-builds [S22, O5].

**Escape hatches are all or nothing.** doctoc offers per-file skip [S9, O3] and terraform-docs offers `sections.hide`/`show` [S11]; neither offers a way to demote rather than drop, and llms.txt's `## Optional` is the only convention I found for the middle case [S16, O37]. If `Rd3.1` is ever hit, that is a discrepancy between what the design may need and what the tooling it would borrow offers.

# INDEX.md — proposal (codex)

## The algorithm

**My proposal; not measured.** Use one repo-local script, `scripts/memory_index.py`, to generate a tracked, flat `project-memory/INDEX.md`. Generation runs synchronously as part of writing memory and integrating branches. It has a write mode and a read-only check mode.

Finding prefixes refer to the reviews by [claude](../lit-review/claude.md) (`C`), [codex](../lit-review/codex.md) (`X`), and [opencode](../lit-review/opencode.md) (`O`). This proposal has not been implemented or tested.

1. **Record the actual reading limits.** Keep `project-memory/index-limits.json` in git. Whoever configures an agent’s session-start reading records its agent, loading route, limit value, unit, and supporting documentation or measurement. Each applicable limit is a separate constraint; bytes, lines and character counts are not converted into one guessed number. For a shared loading budget, record the other files charged to it so the check can count their current size too.

   The script supports physical lines, UTF-8 bytes, Unicode characters and UTF-16 code units. An unknown limit, unsupported measurement unit, missing profile or nonpositive ceiling produces an error. The design’s “about 24 KB and 200 lines” remains an example, not the configuration.

2. **Define the commands and their input snapshots.**
   - `python scripts/memory_index.py --write` reads the current worktree and updates its index.
   - `python scripts/memory_index.py --check` reads that worktree and compares without writing.
   - `python scripts/memory_index.py --check --staged` reads paths and blobs from Git’s staging area, including the staged limit configuration and index. It checks the proposed commit, rather than unstaged edits.

   These modes use the same parsing, filtering, ordering and rendering functions. Success returns `0`; any validation, overflow or freshness failure returns `1` with a diagnostic.

3. **Discover the authoritative files.** Enumerate the Markdown entry files directly inside `project-memory/entries/`, including untracked files in worktree mode and newly staged files in staged mode. Reject nested Markdown entry files, symlinks and unreadable inputs rather than silently excluding them. The expected directory must exist; an existing directory containing no entries produces an empty index.

   Inputs are the entries, the limit configuration and any files needed to calculate a shared loading budget. `INDEX.md`, `work/`, `journal/` and `.cache/` are outside entry discovery.

4. **Parse the fields needed for indexing.** Read each entry as UTF-8. Parse its opening `---`-delimited YAML header without executable constructors, rejecting duplicate YAML keys. Require a nonempty string `id`, a recognised `kind`, and a `status` of `active`, `superseded` or `retired`. Reject duplicate ids across entry files.

   A malformed header is an error, including on an inactive entry: otherwise the script cannot reliably determine its membership. This is indexing validation, not a claim that every W1 field or every entry’s meaning has been checked.

5. **Extract each active entry’s existing claim.** For `status: active`, take the body text after the YAML header and before the first section marker `**Why:**` at the beginning of a line. Confirm that a subsequent `**How to apply:**` section exists. A marker may be followed by its section’s text on the same line.

   The claim begins directly after the header; an entry title is not part of this serialization. Require a nonempty claim. Trim its edges and replace each run of Unicode whitespace with one ASCII space. Preserve the remaining text, including both sentences when present. Sentence count and whether the body contains one claim remain reviewer checks.

6. **Filter and render deterministically.** Include exactly the entries with `status: active`. Sort them by the UTF-8 byte sequence of their repo-relative paths, using `/` as the separator.

   Render a fixed generated-file comment, a fixed `# Project memory index` heading, a blank line, then one physical line per entry:

   ```markdown
   - [<id>](entries/<percent-encoded-filename>) — <kind>: <claim>
   ```

   Markdown-escape the id and claim as literal text. Percent-encode the UTF-8 filename for the relative link. Use UTF-8 without a byte-order mark, LF line endings and one final newline. The header identifies the write command and says the file is generated. Include no generation timestamp.

7. **Measure the complete candidate before writing.** Count the rendered header, blank lines, escaped text, links and final newline against every configured constraint. For a shared budget, add the current size of the other files charged to that budget.

   If the candidate exceeds a limit, report the reader and route, measurement unit, measured value and ceiling. Leave the existing index untouched and return failure. A leftover index is explicitly stale after such a failure; memory-dependent work and handoff wait for repair.

   The writer can correct unnecessarily long source wording while preserving its meaning. Duplicate consolidation or lifecycle changes follow the existing entry rules. If the complete active listing still cannot fit, EJ must decide a design change. The generator performs no automatic shortening, selection, retirement or restructuring.

8. **Publish only a successful complete result.** In write mode, compare the candidate bytes with the existing index. If identical, finish without rewriting. Otherwise write a temporary file beside `INDEX.md`, close it, then atomically replace `INDEX.md`.

   Parsing and size failures leave the existing file untouched. The temporary file is removed on failure. Each writer works in its own worktree and completes this synchronous command before its next memory mutation; this proposal adds no cross-process locking service.

9. **Run generation as part of the write operation.** The agent or person who creates or changes an entry runs `--write` immediately after saving its complete contents. For decisions and facts, this happens before the governed code is changed. Applying the same procedure to every entry change also covers lessons, retirement, supersession and completed decisions.

   Put that procedure in `AGENTS.md` and the human contribution instructions. The writer adds the entry’s required `changed:` line; the script changes only the generated index. A failed generation is a failed memory-write procedure, not a successful write awaiting a later repair. No watcher, background subagent or service is introduced.

10. **Commit the source and generated result together.** The writer stages the intended entry changes and corresponding `INDEX.md`, then runs `--check --staged`. The script itself stages, commits and pushes nothing.

    A staged check catches partial-staging mistakes: a correct worktree index can still disagree with the entries actually staged. A configured pre-commit hook may call this command, but the documented procedure and build check remain necessary because hooks can be absent or bypassed.

11. **Regenerate after branch integration.** The agent or person performing a merge, rebase or cherry-pick resolves authoritative entry conflicts first and stages those resolutions. Resolve conflicts in the generator or limit configuration before using them too.

    Then run `--write`, replacing any conflicted index wholesale with the result from the integrated entries. Stage that result and run `--check --staged` before completing the integration. Apply this procedure after clean textual integrations too: a clean merge does not establish index freshness or consistency between claims.

12. **Expose the freshness check wherever it is needed.** In check mode, compare the complete candidate byte-for-byte with the index from the same snapshot. A missing or different index fails with a unified diff and the write command.

    The build and CI run `--check` on the checked-out revision, including the integrated revision when that is what will land. The first session-start instruction runs `--check` before reading `INDEX.md`; failure triggers repair before relying on it. CI reports failure instead of pushing a repair commit.

    **Check authorship and limit:** this check would be written by the implementer of the proposed script; no such check was run for this report. Equality establishes agreement with that implementation. It does not independently establish correct extraction, truthful claims, complete reader-limit measurements or agreement with the code. Rd5 still governs checking memory before acting.

## Three supporting reasons

1. **The output can be reproduced without another summary-writing step.** Parsed metadata, explicit filtering and locale-independent ordering have concrete precedents. Skipping identical rewrites reduces needless file churn. Taking the authored body claim preserves this design’s source of truth; introducing a separate description would create another value to maintain. **My reading; the particular body-extraction rule is my proposal.** (findings: C2, C3, C5, X2, X3)

2. **Write-time generation and source-first merge resolution serve the accepted timing and clone requirements.** Regeneration inside a memory mutation has prior art, and generated artifacts have documented resolution procedures that rebuild from resolved inputs. Keeping the index tracked makes it immediately available in a clone; resolving entries before regenerating avoids treating either branch’s index as authoritative. **My reading.** (findings: X9, C22, X19, C39, O25)

3. **A complete failure is easier to diagnose than a plausible partial index.** Prior art supports refusing partial output and providing read-only regenerate-and-compare checks. Separate source validation matters because malformed content can reproduce perfectly. These mechanisms support a visible overflow error and a useful freshness check without implying semantic verification. **My reading.** (findings: C52, X31, X33, O39, O40)

## Six must-not-dos

1. **Users must not edit `INDEX.md` by hand.** Correct the entry and regenerate; generated-output edits cannot become a second authority. (finding: X19)

2. **The script must not omit an active entry to meet a size budget.** Deduplicating descriptions, ranking entries or dropping whole lines would break K6.1’s complete listing. (findings: C4, C46, X7)

3. **The script must not vary its output with locale, filesystem enumeration order, modification time or the current clock.** Identical authoritative inputs need identical output bytes for the freshness comparison. (findings: C2, C14, C15, X8)

4. **Users must not accept a `union` merge as the final index resolution.** It can reorder lines and silently restore a line removed through supersession. (findings: C35, C36)

5. **The script must not consume or delete entry files after generation.** Changelog tools sometimes remove processed fragments; this design retains entries under K4.1. (findings: X18, C23)

6. **Users must not rely on a Git hook as the sole regeneration trigger.** Hooks need installation, can be bypassed, and post-merge hooks miss conflicted merges. (findings: O13, O15, X14)

## Design changes

These are proposed changes or completions, not changes already accepted by EJ:

- **W1.2 — specify the header serialization:** opening `---`-delimited YAML, with duplicate keys rejected. The design names header fields but does not currently define their machine-readable serialization.
- **W1.3 — specify the extraction boundary:** the claim begins directly after the header and ends at the line beginning `**Why:**`; `**How to apply:**` follows. This makes body extraction explicit without adding a summary field.
- **K6 — complete the open tool and trigger:** name the single script and the writer’s synchronous invocation. Specify that regeneration failure blocks proceeding with the memory-write procedure until repaired. Running after every entry change extends the timing stated in K6.2.
- **Rd3.1 — separate the fit requirement from its build check:** define fit against every applicable, verified loading-route constraint. Record those constraints in the tracked configuration and make overflow an explicit failure.
- **W6 — complete the open merge responsibility:** whoever performs the integration resolves source conflicts and regenerates the index. Use separate worktrees for simultaneous writers so filesystem writes are isolated too.

**Requirement-check of Rd3.1:** source, can it fail, level, basis and links pass. **One thing fails:** fitting and checking are separate requirements. **Unit fails:** “strictest” does not define how different units or shared loading budgets are compared. **Weak words fails:** the example is approximate and the actual ceilings remain open. The revisions above separate the requirements and define the comparison; they do not supply unmeasured ceilings.

**Open question for EJ before implementation:** which agents and loading routes will read this project’s `INDEX.md`, and what verified limits apply to each? Missing limits remain open rather than becoming guessed defaults.

**Not measured:** this proposal’s generation latency, conflict frequency, practical corpus capacity and effect on agent recall. Review those after implementation with real entries and session-start reads.

## Where I disagree with the other reviews

- **Opencode O30/O33:** “aim under 200 lines” is guidance for a particular instruction file, not an established universal loading ceiling. Claude C44–C49 and codex X25–X26 distinguish limits by file and loading route.
- **Opencode O42:** immediate local regeneration and failing CI are compatible. K6.2 does not require CI to push repairs; they operate at different points in the procedure.
- **Opencode’s reported search gaps:** claude C5 and codex X3–X5 identify frontmatter-driven index generators; codex X19 identifies an explicit generated-memory merge policy. Those mechanisms were found across the combined reviews.
- **Overflow approaches in claude C46/C47 and opencode O35–O37:** selection, hierarchy and an optional tail do not preserve both a complete flat listing and a bounded file. For this proposal, overflow is a reported failure requiring repair or an explicit design decision.
