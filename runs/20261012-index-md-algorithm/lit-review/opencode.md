## Findings

### 1. Building the lines — what is read, what is written, the order, and stability

**O1** — The dominant prior-art shape is *injecting a delimited region into a hand-written file*, not writing a whole separate file. Both tools I read mark the generated region with HTML comments: doctoc — "The pragma is the opening and closing comment blocks to mark the location of the doctoc contents, i.e. `<!-- START doctoc ... -->`"; terraform-docs ships this as its default `output.template`: `<!-- BEGIN_TF_DOCS -->` / `{{ .Content }}` / `<!-- END_TF_DOCS -->`, with `mode: inject`. **quoted** [S9, S11]

**O2** — The marker doubles as the machine-readable "do not hand-edit" rule, written into the file itself. doctoc emits, inside the region: `<!-- DON'T EDIT THIS SECTION, INSTEAD RE-RUN doctoc TO UPDATE -->`. **quoted** [S9]

**O3** — Two escape hatches exist for individual files: an explicit skip marker (`just add <!-- DOCTOC SKIP --> to the top of the file you wish to ignore`) and a configurable insertion marker (mdbook-toc's `marker`, default `<!-- toc -->`, with GitLab and GitHub markers supported). **quoted** [S9, S10]

**O4** — Order is a declared, versioned configuration value in real tools, not an accident of directory traversal: terraform-docs' config carries `sort:` / `enabled: true` / `by: name`. **quoted** [S11] · **my reading**: if the order is left unspecified, the same set of files can yield two different files after an unrelated filesystem change, which breaks any "regenerate and diff" check [S12].

**O5** — Bit-for-bit stability of a generated artifact is a named, defined property with a named verification method, not an aspiration. Reproducible Builds: "A build is reproducible if given the same source code, build environment and build instructions, any party can recreate bit-by-bit identical copies of all specified artifacts" and "The reproducibility of artifacts is verified by bit-by-bit comparison." **quoted** [S22] · **my reading**: `K6.1`'s "never edited by hand" is the weaker half of this; the stronger half, that the generator is a pure function of `entries/`, is what makes `K6`'s "Fails if regenerating `INDEX.md` changes it" a usable check.

**O6** — The specific way sorting breaks determinism is collation order. Reproducible Builds, on locale: "tools which output is influenced by the current locale can make locale a source of reproducibility issues"; "Common sorting functions are affected by the `LC_COLLATE` environment variable, which can be overridden by `LC_ALL`. Some locales can be quite surprising" — demonstrated with `LC_ALL=fr_FR.UTF-8 sort` yielding `a B c` and `LC_ALL=C sort` yielding `B a c`, because "The C locale will sort according to the byte values and is always available". **quoted** [S23] · **my reading**: this is the failure that turns a "check" into a false alarm, and no tool I read pins locale.

**O7** — The same page names the other three volatile inputs a generator must not absorb: time format (`LC_TIME`), default character encoding (`LC_CTYPE`), and system timezone/`TZ`. **quoted** [S23] · **my reading**: an index that embeds a generation timestamp or a "generated at" line is non-deterministic by construction.

**O8** — There is a direct format precedent for "one line per item, with a short label": llms.txt's file list is "a markdown list, containing a required markdown hyperlink `[name](url)`, then optionally a `:` and notes about the file." **quoted** [S16] · **my reading**: `K6.1`'s "id, kind and one-line claim" is the same shape with a link replaced by an id.

**O9** — The agent-facing index standard states the size property of the index file explicitly, and locates the detail elsewhere: "Agents are expected to view or search llms.txt to find the information they need, then follow the relevant links… **The file itself stays small enough to fit in context. The detail lives behind the links, and is fetched only when needed.**" **quoted** [S16]

**O10** — Treating the header as a machine-readable contract is universal across agent tools, which is what lets a generator rely on it. Cursor: "Each rule is an `.mdc` file… A plain `.md` file in `.cursor/rules` is ignored by the rules system because it has no frontmatter to specify `description`, `globs`, and `alwaysApply`." Agent Skills require YAML frontmatter with `name` and `description`. **quoted** [S18, S20] · **my reading**: `W1.2`'s field list is the same kind of contract, but unlike these tools nothing in the design currently *validates* it — see O42.

**O11** — The closest tool I found to "generate a table of one line per source item from parsed attributes" is terraform-docs, which renders per-item rows for inputs, outputs, modules, providers, requirements and resources through named template variables (`{{ .Inputs }}`, `{{ .Outputs }}`, …). **quoted** [S11] · **my reading**: its input is code, not markdown files with headers; I did not find a tool that does the latter (see "did not find" §1).

### 2. When it runs and what runs it

**O12** — The in-repo, no-service trigger is the git hook. `pre-commit`: "This hook is invoked by `git commit`, and can be bypassed with the `--no-verify` option… Exiting with a non-zero status from this script causes the `git commit` command to abort before creating a commit." **quoted** [S4]

**O13** — The catch that makes hook-only designs fragile: hooks live outside version control. `githooks(5)`: "By default the hooks directory is `$GIT_DIR/hooks`, but that can be changed via the `core.hooksPath` configuration variable." Pro Git is blunter: "**It's important to note that client-side hooks are not copied when you clone a repository.** If your intent with these scripts is to enforce a policy, you'll probably want to do that on the server side". **quoted** [S4, S8]

**O14** — The established fix for O13 is a hook manager whose configuration is a committed file. Lefthook: "A Git hooks manager for Node.js, Ruby, Python and many other types of projects… Configure your hooks, install them once and forget about it: rely on the magic underneath", with the config in a committed `lefthook.yml` and activation by `lefthook install`. Both tools I read ship a literal in-repo pre-commit block as the documented install path (doctoc and terraform-docs). **quoted** [S9, S11, S24] · **my reading**: I did not verify in Lefthook's README how it points git at the committed scripts; `core.hooksPath` [S4] is git's own mechanism for that and I did not confirm Lefthook's use of it from the page I read.

**O15** — "At merge" has a native hook with exactly one limitation that matters here. `post-merge`: "This hook is invoked by `git merge`, which happens when a `git pull` is done on a local repository… This hook cannot affect the outcome of `git merge` and is not executed, if the merge failed due to conflicts." **quoted** [S4] · **my reading**: a `post-merge` regeneration is skipped on precisely the conflicted merges where the shared generated file is most likely stale, so `post-merge` cannot be the only trigger.

**O16** — `post-checkout` has broader reach: it fires on `git checkout`/`git switch`, and "It is also run after `git clone`, unless the `--no-checkout` (`-n`) option is used", and likewise for `git worktree add`. **quoted** [S4] · **my reading**: given W6.2 (each agent on its own branch or worktree), this is the one git hook that fires for every kind of branch movement in this design, and it is the only one that also fires on a fresh clone.

**O17** — "At session start" is a first-class, agent-side trigger point. Claude Code's `SessionStart` event: "When a session begins or resumes", with matcher values `startup`, `resume`, `clear`, `compact`, `fork`. The same doc's worked example for "a linting script only when Claude writes or edits a file" uses `PostToolUse` with `matcher: "Edit|Write"` — which is the shape of `K6.2`'s "regenerated right after any decision or fact is written". **quoted** [S2] · **my reading**: `PostToolUse`/`Write|Edit` + a path filter is the mechanism that matches K6.2 most literally, and it fires in worktrees because hooks run with `cwd` following the session [S2].

**O18** — There is a hook that fires *when an instruction file is loaded into context*, which is the exact moment Rd2.1 cares about: `InstructionsLoaded` — "When a CLAUDE.md or `.claude/rules/*.md` file is loaded into context. Fires at session start and when files are lazily loaded during a session", matcher values `session_start`, `nested_traversal`, `path_glob_match`, `include`, `compact`. **quoted** [S2]

**O19** — The vendor's own position is that a hook, not an instruction, is what guarantees a start-of-session read: "Hooks run scripts automatically at specific points in Claude's workflow. Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." **quoted** [S1] · **my reading**: this is external support for the design's premise in Rd2.1 that "agents skip optional reads", and against `AGENTS.md` text alone as the enforcement mechanism.

**O20** — In CI the common pattern for a committed generated file is to *push the regeneration back onto the PR branch* rather than fail. terraform-docs' documented GitHub Actions workflow: `on: - pull_request`, `output-method: inject`, `git-push: "true"`. **quoted** [S11]

**O21** — Read-time generation is also a supported mode, and a real one: mdbook-toc is an mdBook preprocessor, so the index is produced by `mdbook path/to/book` at build time, not at commit time; doctoc additionally offers `-s/--stdout` and `--dryrun`. **quoted** [S9, S10] · **my reading**: read-time generation is incompatible with `Rd1.2` (fresh clone, no cache) and with `Rd2.1` (every agent reads a file at session start).

### 3. Git — committed or not, and parallel branches

**O22** — Generated files are conventionally *marked* so review tooling collapses them. Linguist: `linguist-generated` → "Excluded from stats, hidden in diffs", and "unlike vendored and documentation files, these files are suppressed in diffs". GitHub Docs: "you can mark them with the `linguist-generated` attribute in a `.gitattributes` file… to mark or unmark paths that you would like to be ignored for the repository's language statistics and hidden by default in diffs". **quoted** [S14, S15]

**O23** — Git already ships merge semantics for "a file that cannot be line-merged". The built-in `binary` driver: "Keep the version from your branch in the work tree, but leave the path in the conflicted state for the user to sort out. This is suitable for binary files that do not have a well-defined merge semantics." Setting the `merge` attribute unset gives: "Take the version from the current branch as the tentative merge result, and declare that the merge has conflicts." **quoted** [S5] · **my reading**: "take one side, mark the path unresolved, regenerate" is already a coherent git-native policy; the design's `INDEX.md` is a candidate for `merge=binary`.

**O24** — The opposite driver is documented as unsafe for exactly this case. `union`: "Run 3-way file level merge for text files, but take lines from both versions, instead of leaving conflict markers. **This tends to leave the added lines in the resulting file in random order and the user should verify the result.**" **quoted** [S5] · **my reading**: a union merge on a generated index preserves deleted entries as stale lines and can reorder them, so it turns a mechanical problem into a silent-correctness one — the opposite of K6's "Fails if".

**O25** — The commit-or-not decision has a documented rule of thumb from a project with the same shape of problem (a machine-written file that must be readable from a clone). Cargo: "Cargo.lock contains exact information about your dependencies. **It is maintained by Cargo and should not be manually edited.**" and "**When in doubt, check Cargo.lock into the version control system (e.g. Git).**" **quoted** [S21] · **my reading**: `Rd1.2` (a fresh clone can read it, no cache) forces the commit side of this trade-off; the cost is exactly the merge handling in O23–O24.

**O26** — Repeated identical conflicts can be *learned* rather than resolved by hand: `git rerere` "assists the developer in this process by recording conflicted automerge results and corresponding hand resolve results on the initial manual merge, and applying previously recorded hand resolutions to their corresponding automerge results", and `git merge` "automatically invokes `git rerere` upon exiting with a failed automerge". **quoted** [S6] · **my reading**: this is what makes "resolve by regenerating" affordable across many parallel branches touching the index the same way. Its stated limit: "'git rerere' relies on the conflict markers in the file to detect the conflict."

**O27** — Git explicitly forbids the obvious shortcut of hiding local edits to a tracked file. `git update-index(1)`: "**Users often try to use the assume-unchanged and skip-worktree bits to tell Git to ignore changes to files that are tracked. This does not work as expected**, since Git may still check working tree files against the index when performing certain operations. **In general, Git does not provide a way to ignore changes to tracked files, so alternate solutions are recommended.**" And on `--assume-unchanged`: "Git will fail (gracefully) in case it needs to modify this file in the index e.g. when merging in a commit". **quoted** [S7]

**O28** — If the index is produced *by a git filter* rather than committed directly, git has a setting for the resulting spurious conflicts: "by setting the `merge.renormalize` configuration variable… Git can be told to run a virtual check-out and check-in of all three stages of each file that needs a three-way content merge… **This prevents changes caused by check-in conversion from causing spurious merge conflicts** when a converted file is merged with an unconverted file." **quoted** [S5] · **my reading**: the design says nothing about a clean/smudge filter for `INDEX.md`; this is the documented cost of that route if stage 2 picks it.

**O29** — `.gitattributes` is the only per-path, versioned, in-repo mechanism git provides for file behaviour, and it is designed to be shared: "Attributes which should be version-controlled and distributed to other repositories (i.e., attributes of interest to all users) should go into `.gitattributes` files." **quoted** [S5] · **my reading**: whatever git-side policy is chosen for `INDEX.md` (O22, O23, O28) is expressed there, so it is itself subject to merge — but a one-file attributes entry is a far smaller conflict surface than the index body.

### 4. Size — what happens when the index outgrows the start-file limit

**O30** — The published size ceiling for a start-of-session instruction file is **lines**, and the strictest one I found is Claude Code's: "**Aim to keep CLAUDE.md under 200 lines by including only essentials.**" **quoted** [S3] · **my reading**: this is a primary-source corroboration of the 200-line figure in `Rd3.1`'s example, and it is the number `INDEX.md` would have to clear.

**O31** — The failure mode of overshooting is silent degradation, not an error. Anthropic: "**Bloated CLAUDE.md files cause Claude to ignore your actual instructions!**" and "If Claude keeps doing something you don't want despite having a rule against it, the file is probably too long and the rule is getting lost." Elsewhere on the same page: "If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise." **quoted** [S1]

**O32** — The vendor's own remedy for an oversized checked-in file is *pruning by a tool*, not splitting: "For a checked-in CLAUDE.md, run `/doctor` and Claude proposes cuts for content it can derive from the codebase." With the test to apply: "Keep it concise. For each line, ask: *'Would removing this cause Claude to make mistakes?'* If not, cut it." **quoted** [S1] · **my reading**: for a generated file, "cut it" is a change to the generator's rules (drop `covers`, shorten claims), which is a cheap response to `Rd3.1` — no structural change to `K6.1`.

**O33** — Cursor's ceiling is the same unit but larger, and it prescribes the other response — split and scope: "Keep rules under 500 lines / Split large rules into multiple, composable rules / Provide concrete examples or referenced files / … Reference files instead of copying their contents. This keeps rules short and prevents them from becoming stale as code changes." **quoted** [S20] · **my reading**: among the agents whose docs I read, 200 lines (Claude Code) is stricter than 500 lines (Cursor `.cursor/rules`), so `Rd3.1`'s "strictest limit" is the Claude Code figure on current published docs.

**O34** — The general pattern for "a file that must not grow past a budget" is progressive disclosure with a tiny always-loaded part. Agent Skills: "This filesystem-based architecture enables **progressive disclosure**: Claude loads information in stages as needed, rather than consuming context upfront", with the table giving Level 1 metadata "~100 tokens per Skill", Level 2 instructions "Under 5k tokens", Level 3 "None until accessed", and the conclusion "Progressive disclosure ensures only relevant content occupies the context window at any given time." **quoted** [S18] · **my reading**: the design's `INDEX.md` line is exactly Level 1 and the entry body is Level 2/3 — the design is already shaped like this; what is missing is any stated budget for the line.

**O35** — The other budgeted-index answer is *rank and select*, not truncate. aider: "Of course, for large repositories even just the repo map might be too large for the LLM's context window. Aider solves this problem by sending just the most relevant portions of the repo map… Aider optimizes the repo map by **selecting the most important parts of the codebase which will fit into the active token budget**", governed by `--map-tokens`, "which defaults to 1k tokens". **quoted** [S17] · **my reading**: selection needs a relevance signal, and the design already has three candidates in every header — `kind`, `status`, `covers` — which is what makes this option available at all.

**O36** — Hierarchical indexes are the fallback that keeps the root file small, and two independent vendors ship nesting as the answer. AGENTS.md: "**Large monorepo? Use nested AGENTS.md files for subprojects** — Place another `AGENTS.md` inside each package. Agents automatically read the nearest file in the directory tree, so the closest one takes precedence"; its FAQ adds "the main OpenAI repo has 88 AGENTS.md files". Cursor: "You can place `AGENTS.md` files in any subdirectory of your project, and they will be automatically applied when working with files in that directory or its children… Instructions from nested `AGENTS.md` files are combined with parent directories, with more specific instructions taking precedence." llms.txt specifies the same resolution rule for files: "A file covers the URLs under its path, and where more than one file applies, agents should use the most specific one." **quoted** [S16, S19, S20] · **my reading**: a second-level index (per kind, or per top-level path in `covers`) is the standard-shaped answer to `Rd3.1`, and both vendors place the precedence rule in the reader, not the generator.

**O37** — llms.txt adds a cheap convention for the "some entries matter more" case: "The `## Optional` section is used, by convention, for secondary information: **links an agent can skip when a shorter context is needed.**" **quoted** [S16] · **my reading**: a fixed-size file that keeps every entry but marks a demotable tail is an alternative to dropping entries, and it costs the generator one field.

### 5. Checking — how anyone can tell the index is in step

**O38** — The canonical check, implemented in a real repo, is *regenerate in a throwaway worktree at HEAD, then ask git whether anything changed*. Kubernetes' `kube::verify::generated` requires `kube::util::ensure_clean_working_dir`, then `git worktree add -f -q "${_tmpdir}" HEAD`, runs the generator (`"$@"`), then: `diffs=$(git status --porcelain | wc -l)` and, if non-zero, echoes the header, `git status`, `git diff`, and the tail, then `return 1`. **quoted** [S12] · **my reading**: this is `K6`'s "Fails if regenerating `INDEX.md` changes it" expressed as a shell function, and the worktree step means the check never touches the developer's dirty tree — which matters when several agents share a worktree's parent repo.

**O39** — The check carries the human's next action in its own output. `hack/verify-codegen.sh`: `kube::verify::generated "Generated files need to be updated" "Please run 'hack/update-codegen.sh'" hack/update-codegen.sh "$@"`. **quoted** [S13] · **my reading**: an index check that says only "out of date" costs a reader the derivation of the fix; naming the command is nearly free.

**O40** — The generator can also *be* the check, via a non-writing mode with a distinct exit code. doctoc: "Use the `--dryrun` option to not write changes to files but instead **return an exit code of 1 to indicate files are out of date and should be updated**. This is useful in CI environments where you want to check if your docs are up to date as part of your build process", with the exit-code table giving `1 | Document out of date | One or more files are out of date and need to be updated, but weren't updated because doctoc was run with --dryrun`. **quoted** [S9] · **my reading**: this makes "is the index in step" answerable by the same command that makes it, with no second implementation to keep in sync.

**O41** — The check belongs where the person who caused the drift cannot skip it — the commit. doctoc documents itself "as a [pre-commit](http://pre-commit.com) hook", terraform-docs documents a `terraform-docs-go` hook with `args: ["markdown", "table", "--output-file", "README.md", …]`. **quoted** [S9, S11] · **my reading**: with `K6.2` ("regenerated right after any decision or fact is written") implemented as an agent `PostToolUse` hook [S2], a commit-time check is redundant for agents but still needed for people, and bypassable via `--no-verify` [S4].

**O42** — The failing CI variant and the self-healing CI variant both exist, and the choice is policy, not fact. Compare O38 (`return 1`) with O20 (`git-push: "true"` onto the PR branch). **quoted** [S12, S11] · **my reading**: `K6`'s stated "Fails if" selects the first; `K6.2`'s "so the next session sees it" selects the second. I found no source that argues for one over the other, and I am not proposing one here.

**O43** — Validating the *header* is a separate check from validating the *index*, and the ecosystem's answer is a schema-validating linter over frontmatter. What I could verify is only the requirement, not the tool: Cursor's rule system silently ignores a file with no frontmatter [S20], and Agent Skills states hard field limits ("`name`: Maximum 64 characters"; "`description`: … Maximum 1024 characters"). **quoted** [S20, S18] · **my reading**: `W1.1`'s "Fails if a lint over `entries/` finds a missing field or section" has no named tool in the open-source world that I was able to read a primary source for (see "did not find" §3), so a generator that trusts the header will emit an index line with a hole in it unless the check is written.

## What I looked for and did not find

1. **No tool that generates an index of many small frontmatter-carrying markdown files, one line per file, committed to git and verified in CI.** I found index generators that read *one* file's headings (doctoc [S9], mdbook-toc [S10]), injectors that read *code* (terraform-docs [S11]), and a standard that specifies an index's *format* (llms.txt [S16]). None combines "read N headered files" → "write one committed index file". I did not search exhaustively; this is what four rounds of targeted fetching found.

2. **No primary source for a documented merge policy for a committed generated index shared across many parallel branches.** I found every underlying git mechanism (merge drivers [S5], `rerere` [S6], `linguist-generated` [S14, S15], `merge.renormalize` [S5], and the explicit prohibition in O27 [S7]) but no write-up that assembles them into a policy, and no tool docs that discuss parallel branches touching their generated output. The closest real-world behaviour is Kubernetes' verify script [S12], which sidesteps conflict resolution entirely by regenerating in a fresh worktree and asserting zero diff.

## Gaps and disagreements between sources

**Lines vs bytes vs tokens.** Claude Code says 200 lines [S3]; Cursor says 500 lines [S20]; Agent Skills quotes token counts [S18]; aider quotes a token budget [S17]. No source converts between them. `Rd3.1` needs a single number to compare against, and none of these documents supplies one in a common unit. This is a disagreement in kind, not in degree, and it is unresolvable from the sources — it needs the measurement `SOURCE_OF_TRUTH.md` already anticipates ("where a limit applies, it is a comparison that measurement decides").

**Three different answers to "the file is too long."** Anthropic says prune, and ships a tool that proposes cuts [S1, O32]. Cursor says split into composable rules and nest [S20, O36]. Anthropic's costs page says move it out of context entirely into skills [S3]. For a *generated* file these are not equivalent: pruning changes only the generator's content rules, while splitting changes the generator's structure and therefore `K6.1` itself. No source I read addresses the generated case specifically.

**Fail the build, or fix the build.** Kubernetes' check returns 1 and names the command to run [S12, S13]. The terraform-docs action regenerates and pushes to the PR branch, passing [S11]. Both are committed generated files in real repos. The sources do not disagree on any fact — only on policy — and `SOURCE_OF_TRUTH.md` pulls in both directions: `K6`'s "**Fails if** regenerating `INDEX.md` changes it" argues for the first, `K6.2`'s "regenerated right after any decision or fact is written, so the next session sees it" for the second. I found no source that adjudicates.

**Hook coverage is narrower than its reputation.** `post-merge` "is not executed, if the merge failed due to conflicts" [S4], and client-side hooks "are not copied when you clone a repository" [S8]. So a git-hook trigger is, in my reading, necessary but not sufficient: it does not fire on the conflicted merges most likely to have left a shared generated file stale, and it does not fire at all for anyone who has not installed it — which, for "several agents at once, each on its own branch or worktree" [S4, W6.2], is everyone who has not run the installer. Agent-side hooks [S2, O17–O19] inherit the same gap: they cover agents, not people, and they need the agent to actually write through a tool the hook can see.

**Determinism is assumed by the tools, enforced by nobody.** terraform-docs documents `sort.by: name` [S11, O4] but nothing I read pins locale, and reproducible-builds names locale collation as the trap [S23, O6] in a document about binaries, not markdown. In my reading, nothing in the prior art stops a generator producing a byte-different index on a machine with a different locale, and a naive adoption of the Kubernetes check [S12] would report that as drift — which is exactly the failure `K6`'s "Fails if" clause would turn into a false alarm that trains people to ignore the check.

**"Checked in git" and "never edited by hand" are separate properties and the sources treat them separately.** Cargo says a generated file "should not be manually edited" and, separately, "check it into version control" [S21, O25]. Linguist/`gitattributes` adds a third, orthogonal property — collapse it in review [S14, S15, O22]. Nothing I read requires any of the three to imply the others, and nothing requires the file to be *reproducible*, which is the fourth and separate property from reproducible-builds [S22, O5].

**Escape hatches are all or nothing.** doctoc offers per-file skip [S9, O3] and terraform-docs offers `sections.hide`/`show` [S11]; neither offers a way to demote rather than drop, and llms.txt's `## Optional` is the only convention I found for the middle case [S16, O37]. If `Rd3.1` is ever hit, that is a discrepancy between what the design may need and what the tooling it would borrow offers.
