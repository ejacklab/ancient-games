# Review of proposals/claude.md (opencode)

## Verdict

**ACCEPT WITH FIXES.** The shape is right — one deterministic standard-library script, a committed file, a check against the staged snapshot, and no overflow mechanism until one is needed — and nothing I found requires changing that shape; but the commit-time guarantee is overstated (rebase and cherry-pick never run the hook), the parser has a few uncovered inputs, and one cited finding does not say what the proposal says it says.

## What holds up

- **Reading git objects instead of the working tree is the strongest single decision in the proposal.** It closes the unstaged-entry leak, and it is why a partial `git commit project-memory/entries/E.md` — which stages the entry but not the regenerated `INDEX.md` — is caught rather than silently wrong. That is a better position than C54's, which regenerates at `HEAD` and so cannot see a staged entry at all.
- **Byte-level determinism is spelled out, not implied**: code-point sort, no timestamps, no locale, LF, one trailing newline, no date/count line. Every one of those is traceable to a finding rather than to taste, and the "leave it alone when byte-identical" rule follows directly.
- **Not truncating and not building an overflow mechanism yet is the right call here.** Every available answer (Qwen's drop, mdsmith's refusal, Repomix's split, ranking, nesting) breaks K6.1 or changes what Rd2.1 loads, and Rd3.1 explicitly says the numbers come from measurement. Failing the check and stopping is the behaviour that keeps K6.1 true while the question stays open.
- **K6.2's rewrite to "any entry, same commit"** closes a real hole: a lesson, an observation, or a `status: superseded` change all alter the index, and the second commit is a window in which a branch carries an entry but not its line.
- **Must-not 6 is correct and correctly sourced.** The 10,000-character `SessionStart` cap is exactly the kind of thing a design gets wrong by assuming hook output and loaded context are the same channel.
- **The git-manual quote is verbatim correct.** I checked `githooks(5)` locally (git 2.43): a merge that stops on conflicts does not run `pre-merge-commit` but does run `pre-commit`. The proposal quotes it accurately and reaches the right conclusion about which two commits the two hooks cover.
- **The `tools/` assumption is right**: this repo has `tools/` (with `export_skills.py`) and no `scripts/`, and `project-memory/` does not exist yet, so nothing in the layout changes today.
- **The omissions are deliberate and each has a reason** — no merge driver, no CI, no session-start regeneration, no agent hook, no `rerere`, no `merge=binary`. That is what the owner's "a mechanism that is not needed is removed" asks for, and each omission is argued rather than asserted.
- **The `agy` claim checks out**: `state.md` records EJ stopping agy after stage 1 ("ok stop the agy one") and bringing it back only for stage 3.

Nothing wrong found under: Reason 2 (deterministic generator, one script for both modes — the reasoning is sound and each citation checks), must-not 1 (`merge=union`), must-not 3 (no truncation), design change 3 (`INDEX.md` never hand-merged, correctly scoped to `INDEX.md` only and correctly leaving W6 open for entry files).
