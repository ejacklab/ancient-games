# 孫子 (Sun Tzu) — five open points in the memory design

## Answer

Treat A–E as one fault — a fact written in two or three places — and give each fact one home and one reader: **A** keep a removed `covers` path removed by merging `covers` by change, not union; **B** carry `tools/memory_index.py` and `docs/index-md/` in the kit; **C** record the readers' limits once in `project-memory/limits.json`, which the tool reads; **D** count only the agents whose session start loads `INDEX.md`; **E** build the tool's reader in its own run and measure the engines later, with the example marked interim until a row is measured.

## How I decided

1. **A — keep the removal.** W6.3a says whoever merges keeps “both sides”, but its own `fails_if` names “a `covers` path that one side **added**” (YAML:450–463). A union of the paths does not keep both sides: it keeps one branch's addition and discards the other branch's removal. It also leaves the entry pointing at a file that is gone, while the removal's `changed:` line still says it went (K4.3, YAML:522–534). My #6 — 「是故智者之慮，必雜於利害」 (quoted) — weighs the benefit and the harm: the benefit people want from a union, keeping both additions, is already kept by the two `changed:` lines and the two links; the stale pointer is a new harm. My #16 puts an unclear order on the one who gives it, not on the one who follows: a merger should not have to invent the case for a path only one side touched. So `covers` merges by change, not by union; a same-path clash goes to the project owner, as W6.3a already sends two supersessions of one entry.

   **Wording:** in W6.3a, replace “and every `covers` path either side wrote” with “and every `covers` path either side added or corrected. `covers` merges by change, not by union: a path one side removed or replaced stays removed when the other side did not change it, and its `changed:` line is kept; when both sides changed the same path, the merge reports the clash in the task's `state.md` and the project owner decides.” Add to its `fails_if`: “or the merge restores a `covers` path one side removed, or a same-path `covers` clash is decided by the merger without being reported.”

2. **B — carry the tool.** The records with `check: tool` (about a dozen, including K6.2 at YAML:594–604) name a check that must exist in the adopting project. The tool is one file of 561 lines and imports only the standard library (`tools/memory_index.py:1–22`), so carrying it costs a copy, not an install. My #2 says: 「故用兵之法，無恃其不來，恃吾有以待之；無恃其不攻，恃吾有所不可攻也。」 (quoted) — do not rely on each project installing the right tool; rely on the kit having it. My #3's whole-over-broken preference applies to the kit itself: a kit that leaves out its own checker ships MUSTs whose named check is absent. I would carry the whole `docs/index-md/`, not two files, because its documents cite each other and the `(v)` source in its header would dangle otherwise (my reading).

   **Wording:** `kit` becomes: “These files travel together as one kit: `SOURCE_OF_TRUTH.md`, this file, `CACHES.md`, `vision-statements/`, `tools/memory_index.py`, and `docs/index-md/`. The first four sit beside this file; `tools/memory_index.py` and `docs/index-md/` sit at the repository-root paths named. The tool is part of the kit: every `check: tool` record rests on it.” The prose list at `SOURCE_OF_TRUTH.md:166–167` is removed and points to `kit`. (The `kit` text is generated by `runs/20261014-sot-yaml-review/build_requirements.py:62`, so change it there and rebuild.) A project without `python3` is not supported as written; if EJ wants one, `check: tool` needs a named fallback (my reading).

3. **C — one record the tool reads.** The numbers sit in Rd3.1a, Rd3.1b and `tools/memory_index.py:35–36`; B4.1 in `docs/index-md/REQUIREMENTS.md` repeats the example too. Copies of a number that must agree drift — a second copy of the YAML already sits at `memory_check/guidelines/SOURCE_OF_TRUTH_REQUIREMENTS.yaml` and its W3.6 text is the older one (diff checked 2026‑10‑17; my reading: that is what copies do). My #9 — 「故善戰者，致人而不致於人。」 (quoted) — the tool should come to the one record, not keep copies in step by hand. My #12 — 「故善戰者，求之於勢，不責於人，故能擇人而任勢。」 (quoted) — change the ground the tool reads, not the owner's diligence. My #1's chain — 「地生度，度生量，量生數，數生稱，稱生勝。」 (quoted) — a limit is a comparison with a unit and a measurement. The research found Qwen's 25,000 is UTF‑16 code units, not bytes, and Claude's “25KB” is not stated as 25,000 or 25,600, so one byte constant cannot express the readers' limits.

   **Choice:** one JSON file, `project-memory/limits.json`, because the tool is standard-library-only and `json` is standard library, while YAML would need PyYAML or a hand-written parser (my reading of the imports). Each row: agent, start file, limit and unit (`lines`, `utf8_bytes`, `utf16_code_units`), scope (`index` or `whole_start_load`), `source` and `date` of the measurement, and `measured: true|false`; a row with no measurement holds the example and is marked `interim: Rd3.1b`. A reader with no stated limit gets a measured value from its behaviour, so the set stays complete (my reading).

   **Wording:** Rd3.1a becomes: “`INDEX.md` fits every start-file limit recorded for the agents whose session start loads it, in `project-memory/limits.json`. Each row names the agent, its start file, the limit and its unit (lines, UTF-8 bytes or UTF-16 code units), whether the limit covers the index alone or the whole start load, and the source and date of the measurement; a row with no measurement holds the example in Rd3.1b and is marked `interim`. The tool checks the index against every row in that row's own unit, fails on the first row it exceeds, and every size report prints the binding row, its unit, and whether it is measured or interim.” Rd3.1b's last sentence becomes: “`tools/memory_index.py` holds the example only as the fallback for a row with no measurement.” B4.1 points to the file instead of restating the numbers.

4. **D — the readers, not the roster.** Rd3's title and the prose say “agents that read it”; Rd3.1a says “agents that work on the project” (YAML:709–724; `SOURCE_OF_TRUTH.md:157`). A start-file limit is a property of the load path, not of being on the project: an agent that never loads `INDEX.md` at session start puts no start-file limit on it. My #4 — 「知彼知己，百戰不殆」 (quoted) — know the other; here the other is each reader's start-file rule, not the project's headcount. My #19 says name the ground by the condition that makes it, then act as prescribed: the condition is “session start loads `INDEX.md`”. A project that routes every agent to read it at start ends with every agent in the set — the wording handles that itself.

   **Wording:** Rd3 title: “`INDEX.md` fits every agent whose session start loads it”; prose at `SOURCE_OF_TRUTH.md:157`: “the strictest start-file limit of the agents whose session start loads it”; Rd3.1a: “among the agents whose session start loads `INDEX.md`”; `who_decides`: “project owner: which agents load `INDEX.md` at session start, and so the strictest limit.”

5. **E — build the reader, measure later.** The run already records Q3: “a tool build is its own later run” (`state.md`, Log 2026‑10‑17). That settles when the build runs, not whether C's file gets read. The change is small: read the file when present, fall back to the example, print the binding row and its source, compare each row's unit, and name a malformed row instead of crashing. Without it, C is another file nobody reads. My #8 — 「故兵聞拙速，未睹巧之久也。」 (quoted) — do the small certain step, not a six-engine campaign. My #2 again: do not rely on a docs page; keep the fallback and measure. My #17 — 「故策之而知得失之計，作之而知動靜之理，形之而知死生之地，角之而知有餘不足之處。」 (quoted) — probe the engine and read its truncation notice; a page is not a measurement. Measurement is later, before the first project's real INDEX relies on the limit, on the installed versions of that project's readers, and again when an engine is upgraded or a reader is added. Not now: there is no `project-memory/` here yet (`ls`, 2026‑10‑17), so there is no reader set to measure. Not never: a docs page is not a measurement of the installed version (research: “whether each docs page describes the installed version is not measured”).

   **Plan:** the tool run adds the `limits.json` reader with tests for: absent file (example, marked interim); a measured row (reported as measured); a code-unit row against a non-ASCII index; an over-limit file failing; a malformed row failing with its name, not a traceback. In `--check <rev>`, the file is read from that rev, so a past commit is judged by the record it had (my reading). The measurement run reproduces each engine's actual start load with a marker line at the end of a known-size index, records the largest size that arrives, and writes the command and date in the row.

6. **Proposed change to the pattern.** Generalize C: when a requirement's check reads a value, the value gets one machine-readable record and the check reads that record; no constant, prose copy, or second table. This is #9 and #12 applied to requirements, and it would have caught B, C and D before this review.

## What I need to know

- **B:** is a project without `python3` in scope? If yes, `check: tool` needs a named fallback and the kit wording changes; if no, the kit states `python3` once as a requirement.
- **E:** which project adopts the memory first, and when? If Ancient Games is next, its readers must be measured before its first real INDEX, which moves “later” into this work; if not, the example stays interim.
- **A:** is a person expected to merge, or should a `git` merge driver implement the three-way `covers` rule? If a driver, the rule needs code and tests, not only wording.

## Costs and risks

- **A** — a three-way `covers` merge is more work than a union and can stop on a real clash; the owner pays that decision. The union is cheaper but keeps a stale pointer (my #6: the harm you did not weigh is the one you keep; my #16: an unclear order becomes each merger's private rule).
- **B** — the kit grows by the tool and its docs (919 lines, `wc -l`, 2026‑10‑17); every project carries a tool it may not edit; an upgrade means recopying it into each project; `docs/index-md/` brings this repo's VISION and BACKLOG along; and a project with an existing `tools/memory_index.py` must merge or rename (my #3: the whole is kept only if the part that checks it is kept).
- **C** — a new file the owner can forget; JSON has no comments; a wrong unit or scope silently weakens the check; the schema and the tool must land together, or the tool reads nothing. A whole-load row is only true for the other start files as they were when measured (my #12: prepare the ground; my #1: a number without its unit is not a comparison).
- **D** — a narrower set lets INDEX grow past an on-demand reader's comfort, and the routing must be re-read when an agent joins. The limit is only as good as the owner's list of readers (my #4: know the reader, not the roster).
- **E** — measurement costs a run per engine and goes stale on upgrades; the research's reported 12,000-character agy figure (W‑4, reported) is below the interim 24,000 bytes, so the first measured row may fail an index that passes today. The tool change touches a check a dozen MUSTs rest on, so it needs its own tests and run (my #8: speed on the small certain step; my #1: the interim is marked, not believed).

## How we would know I was right

- **A:** two branches — one corrects `covers` P→Q with a `changed:` line, one adds a link; after the merge, Q is present, P is absent, both `changed:` lines and both links are kept. A P→Q against P→R on the two branches is reported in `state.md`, not silently merged.
- **B:** copy the kit into a fresh directory with nothing installed; `python3 tools/memory_index.py --check` runs on a sample `project-memory/entries/`, and every link inside `docs/index-md/` resolves.
- **C:** with no `limits.json`, a 201-line index fails and the report says “interim, Rd3.1b”; with a measured 150-line row, a 160-line index fails and the report names that row and its date; a 9,000-CJK-character index (27,000 UTF‑8 bytes, 9,000 UTF‑16 code units) fails a 24,000-byte row and passes a 25,000-code-unit row, so the unit is compared as recorded.
- **D:** an index that fits the session-start readers' limit but exceeds a non-reader engine's documented limit passes; routing that engine to load INDEX at start and adding its row makes the same index fail. The record and the file name the same set.
- **E:** the tool's tests pass; with the file absent every report says “interim”; after the first measurement every binding row has a command and date and the report says “measured”; on an engine upgrade the row is re-measured, not assumed.
- **Overall:** a reviewer reading only `project-memory/limits.json` and the tool's one report line can say what the limit is, whose it is, when it was measured, and whether it is still the example.
