# 老子 (Laozi) — five open points in the memory design's requirements

## Answer

**A — The merge keeps the removal.** A `covers` path one side removed, with a `changed:` line saying so, stays removed; the merge does not bring it back. Add to W6.3a after *"every `covers` path either side wrote"*: *"A `covers` path one side removed, with a `changed:` line saying so, stays removed: the merge does not bring it back. A path neither side wrote is not added by the merge."* — and to `fails_if`: *"or a merged entry carries a `covers` path a side removed with a `changed:` line."*

**B — The kit stays as it is; the tool is installed, and its absence is visible.** Append to `kit:`: *"A project that adopts the kit installs the tool at `tools/memory_index.py`; until it does, the records with `check: tool` are checked by the reviewer, as the secret scanner is."* The design already has this shape for the secret scanner, so it costs no new structure and closes a silent hole in about a dozen `check: tool` records.

**C — One file, in the design's own folder: `docs/memory-system/start-limits.yaml`.** One record per agent that works on the project: the agent; how `INDEX.md` reaches it (`@` import, the tool's own loading, a start hook); the start file; the limit; where that limit is written and the version read at; and `measured: false` until it is measured on that engine. Rd3.1a then reads: *"The project owner records the agents that work on the project and their limits in `docs/memory-system/start-limits.yaml`, one record each. The tool compares `INDEX.md` with the strictest recorded limit, counted as that engine counts the start file `INDEX.md` travels in; an agent that states no limit is listed and does not bind. While the file is absent the tool's limit is the example in Rd3.1b; a file that is present and unreadable fails the check."* No number moves into that file from me — the owner records each with its source, and the interim example stops applying the moment a record is there.

**D — "The agents that work on the project."** Rd3's title becomes *"`INDEX.md` fits every agent that works on the project"*, and the prose (`SOURCE_OF_TRUTH.md:157`) becomes: *"`INDEX.md` must fit the strictest start-file limit of the agents that work on the project, counted as each engine counts the file it travels in, with everything else in that file counted against it."* The narrower set cannot decide: Rd2.1 has every agent reading `INDEX.md` at session start, whichever route the engine takes, so "the agents that read it" is emptied by a tool's behaviour rather than by a fact.

**E — Yes to the tool change, in its own run, after the file has one hand-filled use; and measure, later, agy first.** A measurement run on every engine is not this run's work: the researcher's reading is that the interim example sits at or under every *verified* per-file figure, so nothing binds today except one reported conflict. Build the tool change when C's file exists and has been filled by hand once — that is when its shape is known rather than guessed — and take the agy 12,000-character figure (*reported*, not verified) first, because it is the only recorded number that would put `INDEX.md` over a real limit. One thing the change must not do: fall back quietly on a present-but-unreadable file. Absence falls back to Rd3.1b's example; a file it cannot read fails, or the gate passes on an example while the owner believes a measurement applies.

## Costs and risks

- **A — my #8**: the merged entry now differs from *both* sides, so a reviewer applying "keeps both sides" literally will read a correct merge as a violation. The wording must say which reading governs, or two reviewers will decide differently. Two removals of the same path are handled (removed), but that case is not written down and could be read either way.
- **B — my #4**: the tool is not versioned with the kit, so an old kit with a new tool, or a new kit read by an old project, is a mismatch. This is the price of not copying it; it is smaller than two copies of a script that changes.
- **B — the reviewer's checklist grows by one line** (my #19): a project that adopts the kit and installs nothing now has about a dozen `check: tool` records assigned to the reviewer. That is honest, and it is work.
- **C — my #15** (上善若水 … 處眾人之所惡, `quoted`), applied as my reading: the file is read by the check and the reviewer, not by agents, so no agent sees the gap at session start. It is visible in review only, which means it must be on the reviewer's checklist or it rots.
- **C — my #2**: the danger here is an interim number that is stopped at and never noticed. If C's file is never filled, the design's interim example becomes permanent while still reading as an example — worse than a fixed number, because it looks temporary.
- **D — my #2**: the broader set can pull the limit below what a given agent would ever hit, if that agent's engine loads `INDEX.md` by a route the owner has guessed wrong. Over-strict is cheap here; the tool never cuts to fit (B4.3).
- **E — my #7**: the tool change runs on every commit. A bug in it blocks work, which is why it wants its own run, its tests, and a printed fallback — and why a malformed limits file must fail loudly rather than pass on the example.
- **E — deferring the measurement leaves the interim example in place.** The design marks it as an example, and the research found nothing verified that exceeds it, so the price is that the design is defensible, not measured.

## How we would know I was right

- **A** — a merge test: branch one removes a `covers` path with a `changed:` line, branch two adds a link and a `changed:` line. The merged entry has the link, has no stale path, and the tool's check passes on it. The mirror — a path removed with no `changed:` line — is caught by K4.3's `check: git`, not by the merge clause, which is what I claimed.
- **B** — a folder holding the four kit files and no `tools/`: the reviewer's checklist shows every `check: tool` record assigned to the reviewer, with no record left silently unchecked.
- **C** — the file exists; every line names an agent, a route, a start file, a limit and where that limit is written, and `measured:` distinguishes the two kinds of figure. Then: raise one recorded limit below the current index size and `--check` fails without touching the tool's constants. That single test shows whether the check reads the file.
- **D** — add an engine whose recorded limit is tighter and the effective limit moves with no code change; remove it and the limit moves back. And an engine that states no limit is visible in the file with `measured: false` and a GAP note, rather than absent.
- **E** — after the change, the tool's output names the limit it used and where it came from, and a malformed file exits non-zero with a message that says which file and why. The agy measurement either confirms 24,000 bytes for the installed version or gives a lower figure; either result ends the interim example for that engine, and the second case is the one my answer was betting on.
