# N1 — Acceptance tests for two new features (test writer)

You write acceptance tests from a spec. The script under test, `tools/memory_index.py`, is **not** in this workspace,
on purpose: write the tests from the spec alone. Do not look for the script anywhere else.

## The spec

- `docs/index-md/REQUIREMENTS.md` — the criteria. New or changed: **B2.8** (a known credential in an entry is an
  error), **B2.5** and the **B2 Fails if** (B2.8 joins them), **B4.1** (limits from
  `project-memory/start-limits.json`), **B4.2** (what every run prints), **B4.5** (a bad limits file), and the **B4
  Fails if**.
- `docs/index-md/DESIGN.md` steps 5 and 7.
- `docs/memory-system/SOURCE_OF_TRUTH_REQUIREMENTS.yaml` W3.2 and Rd3.1a, which the spec cites.

## What to do

Change only `tests/test_memory_index.py`. Keep every existing test as it is, unless the spec now changes what it
expects; say which, and why, in your result.

1. **B2.8, known credentials.** For each kind the spec lists, a line holding a value of that form is an error: exit 1,
   `<file name>: possible credential (` in the output, the line number, **the matched value nowhere in the output**,
   no `Traceback`, `INDEX.md` unchanged. In the header and in the body; in an active, a superseded and a retired
   entry; in write and check mode (the way `snapshot_args` runs both). Build each test value in the test from parts,
   so the test file itself never holds a whole credential-shaped string (for example `"AKIA" + "A" * 16`). Also: a
   value one character short of a form passes; a private-key header with no body (or a body shorter than the spec's
   length) passes; text that only mentions a prefix (`the ghp_ prefix`) passes.
2. **B4.1, the limits file.** With `project-memory/start-limits.json` present and valid, the smallest `limit` per unit
   applies: an index over the file's `lines` limit fails `--check` and warns in write mode (B4.3), an index under it
   passes even when it is over the example; the same for `bytes`, and for `characters` (count code points: use a
   multi-byte character so bytes and characters differ). A unit with no row keeps the example. Two rows for one unit:
   the smaller applies.
3. **B4.2, the printed lines.** With the file: the size line, plus `, <c>/<limit> characters` when a `characters`
   limit applies, and the line `limits: project-memory/start-limits.json`. With no file: the size line against the
   example and the line `limits: the design's example (no project-memory/start-limits.json)`.
4. **B4.5, a bad limits file.** Each of these is an error in both modes, with
   `project-memory/start-limits.json: ` in the output, exit 1, nothing written: not JSON; not an object; no `limits`;
   an empty `limits`; a row missing each field; `limit` 0, negative, a float or a string; an unknown `unit`; an unknown
   `basis`. And in check mode the file is read from the snapshot: a valid file staged with a bad copy in the working
   tree passes; a bad file staged with a valid copy in the working tree fails; with `--check <rev>`, the file in that
   commit is the one read.
5. **Every new test's docstring cites its id** (B2.8, B4.1, B4.2, B4.5), in the file's style. Every fixture id stays
   in W1.1's form (`checks/fixture_ids.py`).

Match the file's helpers, parametrize use and docstrings. No new dependencies.
