# 老子 (Laozi) — five decisions to finish the memory design

## Answer

**D1** `project-memory/start-limits.txt`, the project's own, beside the `INDEX.md` it bounds, in the line format the tool already reads: blocks of `key: value` lines, blank line between rows, `#` for a comment, five keys — `agent`, `limit`, `unit`, `basis`, `source`.
**D2** The example ends **per row, not per file**: a row with `basis: measured` or `documented` ends it for that agent; a row with `basis: example`, or an agent with no row, holds the Rd3.1b example for that agent. Missing file → the example applies and every run prints that it is the example; a file the tool cannot parse, or a row missing `limit`, `unit` or `basis`, is an **error** — never a silent fallback.
**D3** Keep both new paths, choose neither, and report the clash in the task's `state.md` and to the project owner, as in Rd5.3 — that is what W6.3a's existing text already says once read strictly, so the change is one added clause, not a new rule.

## Costs and risks

- **The line format is mine to defend.** A hand-rolled `key: value` reader has no schema, no type errors and no version field; JSON's silence about duplicate keys and TOML's 3.11 floor are known costs, and this is an unknown one. Cost paid by the tool, not by the owner (my #16). If EJ prefers a documented format, JSON is the one the standard library reads — at the price of no comments (the `basis` note becomes a field) and no trailing commas (my #8: a hand-edited row with one is an error, not a surprise).
- **The example outliving the file** (D2) means the tool can enforce a number nobody measured. My #8 is the mitigation and the price: it is written down, printed on every run, and ends per row. Cost: the size check is weak for as long as the rows are `documented`.
- **A completeness check the tool cannot make** (D2) leaves a gap no `check: tool` closes — an agent added to the project with no row is invisible. Cost: the reviewer's attention, named in the record rather than assumed. My #2's price: knowing what is enough here is a judgment, not a measurement.
- **Both paths kept** (D3) leaves an entry covering two files for one change, and the tool cannot see it (`covers` paths are not checked for existence by the tool — *not measured* here). Cost: a state.md line and the owner's judgment later (my #12).
- **Reviewer-only on W3.2** (D4) is a check that is not repeatable and does not run in the pre-commit hook, so a credential in `entries/` is found only if a person reads it. Cost of (c) now: a real leak can sit in git until the owner's scan. That is why the ending is written, not why it is never built. Cost of the alternative now: a prefix-only check whose false-positive rate on this repo is unmeasured, blocking commits on quoted example keys (*research*: gitleaks allowlists 16 Google example keys; AWS's own docs use `AIDACKCEVSQ6C2EXAMPLE`).
- **Never measuring** (D5) leaves agy's12,000-versus-24,000 conflict unresolved, and the tool holds the example under two readings at once (`CACHES.md:495`). Cost accepted: the index is small, and nothing is cut to fit (B4.3).
