## Findings — in criteria
- F1 [severity: high] files/memory_index.py:176 — `for number, line in enumerate(lines[:40], start=1):` — B2.7 says "No entry holds a line that starts with `<<<<<<<` or `>>>>>>>`", in the header or the body, with no limit. An entry whose marker comes after file line 40 passes. I ran it: a marker at file line 44 gives `errors=[]`; one at line 68 also gives `errors=[]`. A conflicted long rationale after `**Why:**` is the likely case. The "Fails if" says "an entry with a conflict-marker line passes". The 40 is also an invented number: REQUIREMENTS says "There are no fixed numbers", and the function's docstring (`:174-175`) does not mention it. Fix is to scan all of `lines`.
- F2 [severity: medium] files/test_memory_index.py:457-476 and files/test_memory_index_unit.py:137-148 — `location` in `["header", "claim", "after-why"]` — every marker test puts the marker within about 10 lines of the top (`ENTRY_TEXT` is 7 lines). No test has a marker past line 40, so the F1 defect cannot show. The cap is also invisible to a later maintainer. Needs one test with a long body and a late marker, in write and check mode.
- F3 [severity: low] files/memory_index.py:198 — `f"id {entry.entry_id!r} is not in the form DD-MM-xxxxxx-YYYY"` — correct and matches DESIGN step 5, but `xxxxxx` is not defined in the message. A writer with `A1B2C3` or a 5-character id has to look up W1.1 to learn it means six lowercase letters or digits (B2.3's own words).
- F4 [severity: low] files/memory_index.py:58-60 — `# marker, so the middle character of the three is not in the class.` / `CONFLICT_MARKER = re.compile(r"^(?:<{7}|>{7})")` — there is no character class in this regex (it is an alternation), and "the middle character of the three" is unclear. A maintainer may think a `[<>]` class was left out. The regex plus `^` plus `.match` also does what `line.startswith(("<<<<<<<", ">>>>>>>"))` does. The house style at `:141` is `line.startswith(WHY)`, and `ENTRY_NAME` is an unanchored `fullmatch`.
- F5 [severity: low] files/memory_index.py:178-179 — `entry.errors.append(f"unresolved conflict marker on line {number}: …"); return` — one error per file, though DESIGN step 5 says "Collect every problem and report them all". A real conflict has `<<<<<<<` and `>>>>>>>` lines. I ran a file with both and it reported only the first (line 8).
- F6 [severity: low] files/test_memory_index_unit.py:43, :51-52, :90 — `"id:  'D-1'  "`, `parse_header(["id: x"])`, `b"---\nid: x\n\xff\n"` — fixture ids not in the form, in tests that are not about the id. Item 7 asks for every fixture id in form unless the test is about the id. The other fixtures were converted and these were missed. They pass, because `parse_header` and the UTF-8 path never look at the form.
- F7 [severity: low] files/test_memory_index_unit.py:123 — `assert entry.errors == [f"id {entry_id!r} is not in the form DD-MM-xxxxxx-YYYY"], (entry_id, status)` — pins the exact message text, which no spec line gives. The same applies to `:132` `== ["empty id"]` and its docstring "not a form complaint about `''`". The spec asks for an error, not for wording.
- F8 [severity: low] files/test_memory_index.py:362 and :473 — `assert "D-bad-id.md: " in output(result)` / `assert "D-conflict.md: " in output(result)` — these only show that some error was reported for the file.
