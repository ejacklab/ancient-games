# Step 4 (Size) — adversarial review

## 0. RESTATEMENT

Step 4 sizes a task after the algorithm is written. With three or fewer steps, and no unclear spot other than a decision that carries a stated default answer, the task is one piece: a prompt file, those decisions as questions at the top. A spot of kind information or unknown, or a missing or incomplete blueprint section, forces a workflow design at any size. Past three steps, look for a second piece, but split only if each part keeps its own check and the split changes how the work is done. Risk is separate: a small task whose failure is late, irreversible or wide gets one independent check. A workflow design then starts from the category table's defaults; only a written, reviewed ≥20%-cheaper claim at equal coverage replaces one.

**Decision it is meant to produce:** prompt file *or* workflow design, and if a design, which pieces the workflow runs. The packaged rule exists because trial 1 (n=1, `runs/20260920-readme-test-count/`, ~309k tokens for a one-line README fix) miscounted checks and hand-off as steps and pushed a trivial task onto the expensive branch.

## 1. VERDICT

**UNSOUND.** Two independent blockers: the >3-steps branch of §3.4 has no terminal route, and the challenger gate compares two numbers the challenger wrote itself.

## 4. STRONGEST COUNTEREXAMPLE

**The 5-step task that must not be split.** EJ says: *"every ledger row says 'no token roll-up for DSH subagents' — make the run's actual cost measurable, so a challenger can ever be reconciled."*

Step 3.2 writes five steps, each with a nameable check: (1) find every place a subagent call is wrapped; (2) read the DSH transcript format and what the parser needs; (3) extend `scripts/harvest_run.py` to read it; (4) re-derive the seven rows' Actual cost; (5) say in the ledger which rows change. One deliverable: a measurable actual cost. Unclear spots: step (2) is arguably an information spot — if so, step 4's first bullet answers it, "a spot of kind information … **always** means a workflow design". If not, it is a decision with an obvious default, and the task is 5 steps.

Now step 4, following the text exactly. Not ≤3 steps, so not a prompt file. ">3 steps → consider a new piece. Split only if each part keeps its own check **and** splitting changes how the work is done." Split test: (3)+(4) share one check — does the ledger's `Reconciled` column flip to yes — and both are the same edit session in the same two files, so splitting changes nothing about how the work is done. **Split test fails.** Step 4 then says nothing further. The reader is holding a one-piece task with five steps and no route; the diagram confirms the dead end (`SPLIT` has no outgoing edge).

Two competent readers diverge. Reader A: one piece, one deliverable, a script check that already exists — prompt file, done in one session, the trial-1 route. Reader B: ">3 steps means design", §2's tiny test fails on "being wrong would show itself at once", so workflow design: a research node, a designer, a builder, a script gate, a blind reviewer, a canary. Same failure mode, same shape, and the same ~309k token price trial 1 already paid for a strictly easier instance. Nothing in step 4 breaks the tie, and F6 makes it worse: if reader A counts the parser work as a step and the ledger write as a step, A's own count moves and A becomes a designer.

This is not a corner case. It is the modal outcome for a task between four steps and a full pipeline, and step 4 is the only step that decides it.
