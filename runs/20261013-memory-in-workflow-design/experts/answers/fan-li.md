# 范蠡 (Fan Li) — Do agents use memory well alone, and should the method say how?

## Answer
**Question 1: partly.** The harness forces some reads, and those happen. Everything the model decides for itself, such as opening an optional file, choosing what to keep or rewriting what it kept, is unreliable or *not measured* (report §1, §2).

**Question 2: yes, one small change.** It is smaller than Linus's O6. In method §4, replace the three-file project-memory paragraph (L494–510) with a pointer to `docs/memory-system/SOURCE_OF_TRUTH.md`, plus O1's one sentence: *"a node's must-read memory reaches it through its brief, an import or a start hook, never as a request to read it."* Wait on O3–O5 until EJ's own runs show the harm they would fix.

On EJ's premise, I agree that memory matters. My rules say its value is in **regulating** it, meaning what reaches which node and when. **Filling** it, meaning loading more, is not where the value is.

## How I decided
1. **Split the question into what the harness does and what the model does** (my #1, "Heaven's time and human affairs together"). I read Heaven's time as what the engine does whatever the model decides: the forced index reads in T1, T2, T4, T5 and T7. I read human affairs as what the designer delivers on purpose. The model's own mid-task judgement is neither. Report §1's "across the tools" paragraph shows every vendor forces the index read and leaves only the rest to the model. That is the vendors themselves not trusting the model's timing. So my answer to question 1 is "partly". *My reading* of how #1 maps onto engines.
2. **Give each part the job it is better at** (my #14, "say who is better at what"). The harness is better at certain loading; the model is better at judging content once it has it. E1 (*reported*): a loaded index reached 100%, while the skill left to the model was never invoked in 56% of cases. T6 (*reported*): Codex keeps must-follow rules out of memories. So the method should give timing to the harness and the brief, and leave content judgement to the model. That is O1.
3. **Push back on "memory is the most important factor"** (my #2): 「天道盈而不溢」 — "Heaven's way is full but does not overflow" (*quoted*). I see more memory as keeping the full (持盈), and memory delivered at the right time as regulating affairs (節事). The report's evidence on more memory is all negative: E4 (context files, cost up over 20%), E5 (add-all worse), E6 (collapse from 18,282 to 122 tokens) and E7 (context rot), all *reported*. The report's "On EJ's premise" paragraph already says this. What I add is the consequence: anything the method adds about memory should **narrow** what a node gets, never widen it. That is why I prefer a shorter change than O6 (step 6).
4. **Decide the design before the run, not during it** (my #5, "the plan does not shift"): 「夫謀之廊廟，失之中原，其可乎？」 — "To plan it in the temple hall and lose it on the central plain — can that be right?" (*quoted*). Which memory a node reads is a design-time decision, made at court. Leaving it to the model mid-task is losing it on the battlefield. This supports O1.
5. **The time for the pointer has come, so act and finish** (my #4): 「得時無怠」 — "Having got the time, do not slacken" (*quoted*). Two documents now prescribe project memory in contradictory ways (report §4, *verified*: method §4 L494–503 against SoT, accepted 2026-10-12). S1 L90 (*verified*) says that given conflicting instructions, "Claude may pick one arbitrarily". The contradiction is already here, so EJ should not wait to fix it. (Linus reaches the same point through his own rules. My reason is the timing, not the documents' status.)
6. **Do not make the change bigger than the problem** (my #13, "contention is the last of affairs"; my #10, 「究數而止」, "stopped when the count was exhausted", *quoted*). Linus's O6 asks every node to state its memory inputs, delivery, timing, outputs, write timing and checks. But SoT already fixes the timing and the checks: Rd2.1 lists the reads at session start and Rd5.1 says check before acting (*verified*, SoT L344, L383). The node fields already carry inputs and writes: SKILL.md L82–85, where State is "what it reads from the state file before starting and what it writes back" (*verified*). Repeating SoT's rules in every node is a second copy. So my change is the pointer plus one sentence, not a per-node contract. *My reading*: this is where I disagree with Linus. Since SoT governs timing and checks, the contract he wants already exists, once.
7. **Point at the accepted design, do not copy it in, because it is not proven yet** (my #16). Fan Li moved Ji Ran's method to his household only *after* 「越用其五而得意」, "Yue used five of them and got what it wanted" (*quoted*). SoT is accepted but not built: `ls project-memory` in the repo returns "No such file or directory" (I checked this myself). Pasting SoT into the method would spread an untried design further. A pointer keeps one copy, and that copy can change once it has been used.
8. **Wait on O3, O4 and O5** (my #9, 「逆節萌生。天地未形」, "Rebellion against order is sprouting. Heaven and Earth have not yet taken visible form", *quoted*; my #7, 「王無蚤圖」, "Do not plan early", *quoted*). The only evidence that built-in memory interferes with designed memory is #40272, which is *unproven*. That is a sprout, not a visible form. On this I agree with Linus, by a different rule: he asks for evidence of a problem; my #9 says act when the problem takes visible form. Step 9 names what that form would look like.
9. **Something the report misses: a sprout in this repo** (my #12, "cross-check before engaging"). I checked two things myself:
   - `AGENTS.md` here is a words-only pointer: "The instructions for this folder are in `CLAUDE.md` … Read it first". For Codex and opencode nodes, the folder rules therefore reach the agent only if the model decides to open `CLAUDE.md`. That is the M1 / T1 L435 pattern, inside EJ's own repo.
   - Some of EJ's working rules live only in the main session's Claude auto memory (`~/.claude/projects/-home-smoke01-dev-ancient-games/memory/`, 36 index lines). Method App. B says of auto memory: "Only Claude Code reads it". Grepping `AGENTS.md`, `CLAUDE.md` and `docs/` for "Stay in own scope" finds nothing.

   So a non-Claude node gets neither of these by load. This is the O4 gap made concrete. Per #12 I would still not engage until it is cross-checked: has a non-Claude node actually broken a rule that lived only there? *Not measured.* What the check establishes: the files say what I quote. What it does not establish: that any node has failed because of it.

## Costs and risks
- **The pointer depends on a design that has not been built** (from my #16). Until `project-memory/` exists, a designer following the pointer finds rules and no store. Price: one interim line, or a short gap.
- **Delivering memory does not mean the agent follows it** (from my #1). Human affairs without Heaven's response do not succeed. E4 shows loaded files are followed (`uv` used 1.6 times against under 0.01), but nothing measured shows that following them improves outcomes. Price: the sentence may cost brief tokens and buy nothing. *Not measured.*
- **A start hook per engine where a brief cannot carry the file** (from my #14). This is setup and upkeep for each engine, and the engines' memory features changed within the last year (report O5 cost).
- **Waiting on O4 has a price too** (from my #4, 「天予不取，反為之災」, "what Heaven gives and you do not take turns into disaster", *quoted*). If the gap in step 9 is already causing silent rule breaks, every run until it is noticed pays for it. Watching for the sign is cheap, but someone has to look.
- **Being smaller than O6 means some nodes' memory needs go unstated** (from my #13 and #10). If SoT's Rd2.1 reads turn out to be too coarse for a node, for example a verifier that must *not* get certain entries (M13), the State and Context fields have to carry it case by case. The method will not prompt for it.
